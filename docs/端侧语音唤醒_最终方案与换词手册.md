# 端侧语音唤醒：最终方案与换词手册

> 目标变了：这套东西最终要合进设备，不是留在 PC 上跑。所以评价标准从
> 「PC 上能不能跑」切换成「端侧能不能落」。
>
> 本文记录 2026-10-28 的全部进一步实验（含失败）、三套可落地方案的横向比较、
> 以及一套自己就能操作的换唤醒词流程。前置数据见
> `docs/免费ASR模型横评_唤醒词实测.md` 和 `docs/唤醒词识别_音频优化实验结论.md`。

---

## 一、结论先行

**没有单一模型能同时满足「端侧可跑」和「任意唤醒词都灵」。** 必须分两件事来看：

| 需求 | 能用的方案 | 代价 |
|---|---|---|
| 唤醒词固定、要求低功耗常开 | **专用 KWS 模型**（4.8MB int8） | 只对「模型熟悉的音素组合」灵 |
| 唤醒词任意、要求高准确 | **VAD + 小 ASR + 模糊匹配**（60~135MB） | 功耗高一个数量级，需要 Cortex-A7 双核以上 |

而本次实测证明了一件事：**在用户的声音 + 录音链路上，3.3M KWS 对「你好兮兮」「你好小智」都不可用，
且任何参数、变体、补偿手段都救不回来。** 所以如果坚持 KWS 路线，就必须换一个「模型熟悉的词」。

推荐落地架构（三级，见 §5）：

```
常开层   VAD (silero, 2MB) 或 KWS (4.8MB)     ← 极低功耗，只负责「有人在说话」
 ↓ 触发
确认层   小 ASR (60~135MB) + 带 1~2s 上下文 + 近音模糊匹配   ← 真正判定唤醒词
 ↓ 命中
业务层   呼出 / 弹 UI / 上云
```

**关键量化依据**：同一个小 ASR，单句识别 7/12，带上前后各一句上下文就变 10/12（§4.3）。
这个改动零成本、不增体积，收益比换模型大。

## 二、KWS 路线为什么判死（本轮新增实验）

### 2.1 先把「官方基线」跑出来

模型自带 7 个官方测试音频 + 官方关键词表，这是最能说明问题的对照 —— 排除自己代码写错的可能：

```bash
bash scripts/kws.sh ../../.tools/kws/test_wavs/*.wav \
  --keywords ../../.tools/kws/test_wavs/test_keywords.txt
```

```
0.wav  未检出     1.wav  未检出     2.wav  未检出
3.wav  ✅ 法国@5.30s
4.wav  ✅ 女儿@3.70s
5.wav  ✅ 周望军@1.50s  落实@2.80s
6.wav  未检出
统计: 检出 3 / 7 (43%)
```

**官方自己的验证集只有 43%。** 0/1/2.wav 对应的是「文森特卡索」—— 一个生僻音译词，三个文件全挂。

这个结果推翻了「官方发布就一定能在官方音频上过」的假设：官方从没宣称 100%，
而且**失败的正是一个生僻音节组合**，和「兮兮」「小智」的处境完全同构。

### 2.2 新模型（2025-12-20 中英双语）试过了，不可用

官方文档页列了 3 个 KWS 模型，其中
`sherpa-onnx-kws-zipformer-zh-en-3M-2025-12-20` 比现在用的 2024-01-01 版新两年，
且提供 chunk-8（160ms 延迟）/ chunk-16（320ms，精度更高）两种规格。

按官方推荐组合（int8 encoder + int8 joiner + fp32 decoder）组装后实测：

| 配置 | 官方中文测试集 |
|---|---|
| chunk-16（含英文关键词行） | **0 / 7** |
| chunk-16（纯中文关键词） | **0 / 7** |
| chunk-8（纯中文关键词） | **0 / 7** |

加载无报错、推理正常（RTF 0.09），但一条都不出。

**原因**：这个模型是 `phone + ppinyin` 混合词表，需要 `en.phone` 参与；
而 sherpa-onnx **2.0.1** 的 Python `KeywordSpotter` 没有暴露 `en.phone` 参数
（`from_transducer` 那套接口才有）。也就是说：

> 新模型在 C++/更新版 API 上应该可用，但在当前 Python 接口上是死路。

结论：**暂不采用**。要用得升级 sherpa-onnx 或改用 C++/Rust 接口 —— 而上板本来就要写 C++，
所以这条对最终产品仍然有效，只是不能在本阶段用 Python 验证。已记录为待办。

### 2.3 音素变体扩展：工业界常用做法，这次也无效

思路：KWS 把关键词当一条音素序列做 beam search，序列概率不够就永远过不了阈值。
写成多行近音变体等于扩大搜索面。已经沉淀成工具 `scripts/kw_variants.py`。

「你好小智」展开 9 条（`z/zh`、`s/x`、`i/í/ǐ/ì`、`n/l`、`ǎo/áo` 互换）：

```
n ǐ h ǎo x iǎo zh ì @你好小智      ← 原样
n ǐ h ǎo x iǎo z ì  @你好小智
n ǐ h ǎo x iǎo zh ǐ @你好小智
n ǐ h ǎo x iǎo zh í @你好小智
n ǐ h ǎo x iǎo zh i @你好小智
n ǐ h ǎo s iǎo zh ì @你好小智
n í h ǎo x iǎo zh ì @你好小智
l ǐ h ǎo x iǎo zh ì @你好小智
n ǐ h áo x iǎo zh ì @你好小智
```

实测：

| 数据 | 单变体 | 9 变体 |
|---|---|---|
| 手机录音 4 段「你好小智」 | 0/4 | **0/4** |
| Jabra 12 句「你好兮兮」（8 变体） | 0/12 | **1/12** |

变体把兮兮从 0 拉到 1，仍在噪声范围。**这条路对本案无效**，但工具保留 ——
换别的词时值得先试，成本几乎为零。

### 2.4 至此 KWS 的全部失败证据汇总

| 尝试 | 结果 | 结论 |
|---|---|---|
| 阈值 0.25 → 0.02 | 0 命中 | 不是门槛问题 |
| 加分 1.0 → 3.0 | 0 命中 | 不是 beam 激励问题 |
| 阈值 × 加分全网格 | 全表空 | 不是参数问题 |
| TTS 干净合成音 | 4/4、3/3 | 链路和词表都对 |
| TTS 加噪 12dB | 两词全挂 | 模型对噪声极敏感 |
| 音素变体 8~9 条 | 0/4、1/12 | 不是搜索面问题 |
| 高频补偿 +12/+18dB | 「你好」2/2，「你好小智」0/4 | 不是单纯带宽问题 |
| 拆词：`n ǐ h ǎo` | **10 次命中** | 模型认「你好」 |
| 拆词：`x ī x ī` / `x iǎo zh ì` | **0 次** | 病灶就在后两个字 |
| 换词（兮兮→小智） | 0/12 → 0/4 | 换词救不了 |
| 换新模型（2025-12-20） | 0/7 官方集 | Python 接口不支持 |

**判定：3.3M KWS 在「用户的声音 + 这段录音链路」上，对生僻二字组合不可用。**
不是参数、不是音频加工、不是词表拼写。是模型对这组音节的建模不够。

## 三、端侧方案横向比较

体积为实测文件大小；内存按「模型体积 ×1.5~2 + 运行时」估算（未逐项实测 RSS）。
召回为真人录音实测（A=手机 4 段「你好小智」，C=Jabra 12 句「你好兮兮」）。

| # | 方案 | 模型体积 | 估算内存 | 唤醒词可自定义 | A 组 | C 组 | RTF | 端侧可落 |
|---|---|---|---|---|---|---|---|---|
| 1 | KWS zipformer 3.3M (int8) | **4.8MB** | ~30MB | 需拼音素，且只对熟词灵 | 0/4 | 1/12 | 0.03 | ✅ 最优（功耗） |
| 2 | Zipformer-CTC-small-zh (int8) | 60MB | ~120MB | 完全自由 | 1/4 | **7/12** | 0.022 | ✅ |
| 3 | Dolphin-base (int8) | 99MB | ~180MB | 完全自由 | **2/4** | 1/12 | 0.018 | ✅ 但词汇弱 |
| 4 | Moonshine-base-zh | 135MB | ~250MB | 完全自由 | **3/4** | 3/12 | 0.033 | ⚠️ 需 A7 双核+ |
| 5 | SenseVoice-small (int8) | 228MB | ~400MB | 完全自由 | 2/4 | **9/12** | 0.036 | ⚠️ 需 A53 四核 |
| 6 | Paraformer-zh (int8) | 228MB | ~400MB | 完全自由 | 0/4 | 4/12（整条 10/12）| 0.024 | ⚠️ 强依赖上下文 |
| 7 | Qwen3-ASR 0.6B (int8) | 937MB | ~1.5GB | 完全自由 | **4/4** | 10/12 | 0.35 | ❌ 只能当服务端 |

### 3.1 端侧算力门槛（关键）

| 芯片档位 | 代表 | 能跑哪个 |
|---|---|---|
| Cortex-M4/M33，几百 KB RAM | STM32F4 | 只能跑 **DS-CNN / 自训 20KB 级 KWS**，通用模型全部不行 |
| ARMv6 单核 700MHz | 树莓派 1 B+ | 什么都跑不动（实测已有结论），只能跑 TinyML 级 KWS |
| Cortex-A7 双核 1.2GHz / 256MB | 全志 V3s、君正 X1000 | 方案 2/3（60~99MB），RTF 约 1~2 |
| Cortex-A53 四核 1.2GHz / 512MB | RK3308、全志 H3 | 方案 4/5/6，RTF 0.3~0.6 |
| A55 四核 1.5GHz / 1GB | RK3566 | 全部，含 Qwen3（慢） |

**换算关系**：PC 上 RTF 0.02 的模型，在 A7 上大约 ×15~30，在 A53 上 ×8~15。
方案 5（SenseVoice）在 A7 上会到 RTF 1 以上 → 实时跟不上，不能选。

### 3.2 关于 Vosk（未实测，仅列选型）

Vosk 中文小模型约 40~50MB，Kaldi 系流式，是端侧很主流的选择。
本项目没实测，不做结论；但如果方案 2 的体积仍嫌大，Vosk 是下一个该试的。
另有阿里 FunASR 的 paraformer-streaming ONNX 导出，量级与方案 6 相当。

## 四、在线方案横向比较

调试阶段先用免费额度即可；产品阶段要不要上云是个产品决策（隐私 / 联网 / 延迟）。

| 服务 | 免费额度（以官网当期为准） | 中文准确率 | 唤醒场景适配 | 备注 |
|---|---|---|---|---|
| 阿里云智能语音（一句话/实时） | 有试用额度 | 高 | 实时流式接口可用 | 与 FunASR 同源 |
| 讯飞开放平台 | 每日免费调用量较大 | 高 | 有专门的语音唤醒 SDK（离线+在线） | 唤醒 SDK 是其强项 |
| 腾讯云一句话识别 | 每月免费额度 | 高 | 需自己切句 | |
| 百度短语音识别 | 有免费额度 | 中高 | 需自己切句 | |
| 自建（服务器跑 Qwen3-ASR / Whisper） | 只有服务器成本 | 最高 | 完全可控 | 数据不出内网 |

**在线的真实优势不是准确率，而是「唤醒词随便改」。** 云端 ASR 认字，不需要拼音素，
写成「你好小智」「嗨小智」「小智小智」都能直接匹配 —— 而 KWS 每换一次词都要重拼音素 + 重测召回。

代价：① 必须联网 ② 常开上传音频有隐私顾虑 ③ 每次唤醒一次网络往返（200~500ms）。

**折中方案（推荐产品形态）**：端侧 VAD 常开 → 检测到说话才上传那 1~2 秒音频 → 云端识别判定。
这样既省流量也省隐私面，且唤醒词随便改。

## 五、推荐架构

### 5.1 纯端侧（无网、低功耗优先）

```
mic ──► VAD (silero-vad, 2MB)  ──有语音──►  RingBuffer 保留前 1.5s
                 │                              │
                 │ 无人说话：睡眠               ▼
                 │                     ASR (Zipformer-CTC-s 60MB 或 Moonshine 135MB)
                 │                              │
                 └──────────────────────► 文本 + 近音模糊匹配
                                                │ 命中
                                                ▼
                                        唤醒回调 → 呼出 / 弹 UI
```

要点：
1. **VAD 而不是 KWS 做常开层** —— VAD 不吃词表，换词零成本；KWS 只省一点功耗但锁死词表。
2. **必须带前 1.5 秒上下文**再送 ASR（§4.3 依据）。
3. 匹配用「编辑距离 + 近音表」，不要精确等于。

### 5.2 端 + 云（唤醒词随便改、准确率最高）

```
常开层（端侧）: VAD 或 KWS 4.8MB，只判「有没有人说话」
确认层（云端）: 上传 1~2s 音频 → 云 ASR → 文本匹配
```

### 5.3 本阶段（PC 调试，不花钱）

直接用现成脚本，都是免费的：

```bash
bash scripts/wake.sh --mic                       # VAD+ASR+模糊匹配，实时
bash scripts/wake.sh --wav <文件>                 # 离线跑
bash scripts/batch.sh <长录音> --repeat 5          # 一条长录音出逐词对比表
```

## 六、换唤醒词完整流程（自己就能操作）

**什么时候该换词**：现有词召回 < 70%，且已排除录音链路问题（先跑 `scripts/diag.sh`）。

### 第 1 步：选词（决定成败的一半）

| 原则 | 好 | 坏 |
|---|---|---|
| 音节高频，模型见过 | 小智、小爱、同学、天猫 | 兮兮、咕噜、吱吱 |
| 声母多样（n/h/x/zh 各不相同） | 你好小智 | 咪咪咪咪（全同音，易混） |
| 3~4 音节 | 你好小智 | 智（2 音节以下误报高） |
| 避免鼻音/擦音收尾密集 | 小智 | 心心（全是 x/x） |

**反例就是本案**：「兮兮」是两个 `x + ī` 叠音，KWS 拆词实测 `x ī x ī` **0 命中**，
而「你好」`n ǐ h ǎo` 命中 10 次 —— 生僻叠音是模型的盲区。

### 第 2 步：查音素是否齐备

```bash
# 音素写法：声母/韵母 + 声调符号，空格分隔。先去 tokens.txt 确认有没有。
python scripts/kw_variants.py --model-dir ../../.tools/kws \
    --pinyin "n ǐ h ǎo x iǎo zh ì" --check
```

输出 `✓ 音素齐备` 才能往下走；缺 token 直接换词，别硬拼。
常用音节对照：`小 xiǎo` = `x iǎo`，`智 zhì` = `zh ì`，`兮 xī` = `x ī`。

### 第 3 步：生成关键词文件（含音素变体）

```bash
python scripts/kw_variants.py --model-dir ../../.tools/kws \
    --word 你好小智 --pinyin "n ǐ h ǎo x iǎo zh ì" \
    --out ../../.tools/kws/keywords_myword.txt --limit 8
```

`--limit 8` 是变体条数。变体多 → 更容易命中但误报上升，实测收益有限，8 条足够。

### 第 4 步：先用合成音自检（30 秒）

```bash
# 合成 3 种语速
PY="/d/Program Files/anaconda3/envs/kws/python.exe"
for r in -3 0 3; do "$PY" scripts/tts_gen.py --text "你好小智" --out ../../.tools/tts/mine_r$r.wav --rate $r; done
bash scripts/kws.sh ../../.tools/tts/mine_r*.wav --keywords ../../.tools/kws/keywords_myword.txt
```

**这一步只能证明「词表拼对了」，不能证明「真人能唤醒」。**
合成音对什么词都是 4/4，别被它骗（本案教训）。

### 第 5 步：录真人样本（关键，5 分钟）

```bash
bash scripts/rec.sh --words 你好小智,小智小智,小智,你好兮兮 --repeat 5 --seconds 3
```

录音三条铁律：
1. 词内**连贯说完，绝不能停**（一停就被 VAD 切成两句，整词永不成立）
2. 词与词之间停 1 秒（给切句留边界）
3. 自然语速，别刻意放慢；离麦 20~30cm

没条件用电脑录，用手机录一条长音频也行（顺序固定、每个词 5 遍），
放 Downloads 后用 `batch.sh` 跑，会自动切句并分组。

### 第 6 步：跑横评，看召回

```bash
for w in 你好小智:xiaozhi 小智小智:zzzz 小智:zz; do
  bash scripts/kws.sh ../../.tools/rec/${w%%:*}/**/*.wav \
    --keywords ../../.tools/kws/keywords_${w##*:}.txt | tail -2
done

# 或者一条长录音直接出对比表
bash scripts/batch.sh <录音> --repeat 5
```

### 第 7 步：判定与调参

| KWS 召回 | 判定 | 动作 |
|---|---|---|
| ≥ 70% | 可用 | 跑 `--grid` 标定阈值，选「最高阈值 + 最低加分」还能命中的组合 |
| 40~70% | 危险 | 加变体、换更长/更常用的词；或直接上 ASR 方案 |
| < 40% | 弃用 | 换词，或改用 §5 的 ASR 架构 |

标定阈值：

```bash
bash scripts/kws.sh <样本> --keywords <kw文件> --grid \
  --grid-thrs 0.10,0.15,0.20,0.25 --grid-scores 1.0,1.5,2.0
```

### 第 8 步：实时验证

```bash
bash scripts/wake.sh --mic --words 你好小智,小智小智
```

**必须实机说三遍以上**，离线跑分再好也可能被 AGC/增益打翻。

### 第 9 步：先体检录音链路，再下结论

```bash
bash scripts/diag.sh <录音.wav>
```

看 1000–3000Hz 占比：**低于 15% 就是链路问题，不是算法问题**。
本案手机录音只有 5.0%（Jabra 是 29.1%），导致一度错判成「小智也不行」。

## 七、踩坑清单（本轮新增）

1. **官方验证集不是 100%**。3.3M KWS 官方 7 段只检出 3 段，失败的是生僻音译词。
   所以「官方发布肯定能过」这个假设不成立。
2. **新模型 ≠ 能用**。`zh-en-3M-2025-12-20` 需要 `en.phone`，sherpa-onnx 2.0.1 的
   Python `KeywordSpotter` 不暴露该参数 → 0/7 且不报错，容易误判成「模型差」。
3. **hf-mirror 上没有 KWS 模型仓库**，要用 GitHub release 直连
   （`releases/download/kws-models/`，注意不是 `asr-models`）。
   之前 502 是临时的，重试即通。
4. **模型文件名是硬编码的**。`kws_test.py` 里 `ENC/DEC/JOI` 写死了
   `encoder-epoch-99-avg-1-chunk-16-left-64.onnx`，换模型必须重命名文件，
   不能只改目录（sherpa-onnx 是按路径加载，文件名无所谓，但脚本按名字找）。
5. **zh-en 双语模型的 decoder 只有 fp32**，没有 int8。强行换 int8 会加载失败。
   官方推荐组合就是 int8 encoder + int8 joiner + fp32 decoder。
6. **变体不是万灵药**。9 条变体在手机录音上仍是 0/4，在 Jabra 上 0/12→1/12。
   别指望用变体救一个模型根本不熟的音节。
7. **`--segments` 与普通模式的输出格式不同**，用 `grep 统计` 会抓不到，
   要看 `tail`。
