# 语音唤醒：三个可立刻执行的方案实测

> 日期：2026-10-28　｜　环境：Windows + sherpa-onnx 2.0.1 (CPU, 2 线程)
> 动机：真实指令测试集（50~100 条）搭起来费时间，先把**不依赖新录音**的方案做掉。
> 本文只写跑出来的数，不写推测。

---

## 0. 结论速览

| # | 方案 | 结果 | 判定 |
|---|---|---|---|
| 1 | **官方量化版本 vs fp32 vs 自量化** | 官方 int8 与 fp32 在噪声三档 CER **逐位相同**（0.83/0.83/1.39），体积 3.18×↓、峰值内存 1.51×↓、RTF 快 15%；自量化精度不掉但 **RTF 慢 1.8×** | ✅ **用官方 int8，永不自己量化** |
| 2 | **热词提权 hotwords** | 强制 `modified_beam_search`；把"小致"纠成"小智"（0→25%），但把"西西"吞掉（33%→8%），score 1.5→6.0 无变化 | ❌ **判死**（净收益为负） |
| 3 | **同音字归一 + 锚点近音** | 兮兮 **0%→83%**、小智 **0%→100%**（Paraformer）；ZipCTC 60MB 也到小智 100% | ✅ **唯一有效手段，必须做** |

**最重要的一条**：过去所有方案都判死，根因不是"模型听不见"，而是"听见了但字写错"。
`你好小智` 被写成 `你好小致 / 你好小吃 / 你好想吃 / 那要小致`——音全对，字全错，而被"完全匹配"判据判成失败。

**选词结论**：`你好小智` 明显优于 `你好兮兮`（100% vs 83%）。
`兮兮` 是生僻词，ASR 语言模型不认，会强行输出常见词（西西/嘻嘻/谢谢/星星/学习）。

## 1. 实验一：官方量化版本（点名要做的那个）

### 1.1 三档同模型对照（ZipCTC 中文模型）

| 档位 | 文件 | 体积 | 峰值内存 | 加载 | 干净 CER | RTF |
|---|---|---|---|---|---|---|
| fp32 原始 | `m_zipctc_fp32/model.onnx` | 190.3 MB | 365 MB | 3.11 s | 1.67% (19/20) | 0.0289 |
| 自量化 int8 | `model_q.int8.onnx`（`quantize_dynamic` QUInt8/per_channel） | 59.6 MB | — | 3.29 s | 1.67% (19/20) | **0.0496** |
| **官方 int8** | `m_zipctc_s/model.int8.onnx` | 59.8 MB | **242 MB** | 3.32 s | 2.22% (18/20) | **0.0247** |

三个反直觉的点：

1. **自量化精度一点没掉**（1.67% 与 fp32 完全一致），但**慢了 72%**（0.0496 vs 0.0289）。
   自量化拿到的 int8 算子在通用 runtime 上走的是回退路径，没有针对硬件调优。
2. **官方 int8 比 fp32 还快 15%**，峰值内存从 365MB 降到 242MB（省 123MB）。
3. 官方 int8 在干净环境下比 fp32 差 1 个样本（`17.wav` 多吐一个"大"字，`把空调风速调到最大大`）。
   20 句的样本量下，这 1 个字的差异**没有统计意义**，不能据此说官方 int8 掉精度。

### 1.2 噪声档：量化误差会不会被放大？

同随机种子（按文件 hash 固定）注入白噪声，fp32 与官方 int8 逐档对比：

| SNR | fp32 CER | 官方 int8 CER | fp32 RTF | int8 RTF |
|---|---|---|---|---|
| clean | 1.67% | 2.22% | 0.0289 | 0.0247 |
| 20 dB | 0.83% | **0.83%** | 0.0258 | 0.0220 |
| 10 dB | 0.83% | **0.83%** | 0.0258 | 0.0222 |
| 5 dB | 1.39% | **1.39%** | 0.0273 | 0.0219 |

**20dB / 10dB / 5dB 三档 CER 逐位完全相同**。
噪声下两者的错误样本是同一批、错成同样的字——说明量化误差没有改变排序，也没有引入新的错误类型。

> ⚠️ 数据说明：20 句噪声档**没有统计意义**（20dB 的 CER 反而低于 clean，是随机噪声让 `17.wav` 那个多余的字消失造成的）。
> 这里能采信的只有 **fp32 与 int8 的相对关系**，不能采信绝对 CER 数值。要绝对值必须扩样本。

### 1.3 落地规则

```
有官方 int8  → 直接用，别犹豫
只有 fp32     → 先确认有没有官方 int8 发布（k2-fsa/sherpa-onnx releases → asr-models）
必须自量化    → 接受 RTF 变慢 1.7~1.8×，换取 3× 体积；只在 Flash 装不下时用
```

**原因**：`quantize_dynamic` 只做权重量化（MatMul/Conv 的权重转 int8），激活仍是 fp32，
算子融合 / 内存布局 / 指令调度全部没优化。官方 int8 是作者用 sherpa-onnx 自己的导出流水线
做的，能吃到 runtime 里的 int8 kernel。

**顺带一个坑**：`quant_pre_process`（onnxruntime 的符号 shape 推断）在 ASR 模型上必挂
（transducer 的 encoder/decoder/joiner 有动态 shape，推断不完整），别浪费时间。

## 2. 实验二：热词提权（hotwords）—— 判死

### 2.1 硬限制

`sherpa-onnx` 在**热词必须配 beam 搜索**，这条是硬报错，不是建议：

```
ValueError: Please use --decoding-method=modified_beam_search when using --hotwords-file.
            Currently given: greedy_search
```

也就是说热词的代价是**必须放弃 greedy**，付 beam 搜索的算力。端侧本来算力就紧，这是前置成本。

### 2.2 结果（24MB 流式模型，热词 = `你 好 小 智` / `你 好 兮 兮`）

| 配置 | 兮兮 12 句 | 小智 4 句 |
|---|---|---|
| greedy 基线（无热词） | 0/12 | 0/4 |
| beam + 热词 score=1.5 | 0/12 | 1/4 (25%) |
| beam + 热词 score=3.0 | 0/12 | 1/4 (25%) |
| beam + 热词 score=6.0 | 0/12 | 1/4 (25%) |
| **beam 无热词 + 同音归一** | 1/12 (8%) | 2/4 (50%) |

三个问题：

1. **score 从 1.5 拉到 4 倍（6.0）毫无变化**——说明 context graph 的 boost 根本没影响到这条路径，
   或者 boost 已经被 beam 的剪枝吃掉。
2. **热词确实纠对了一条**：`你好小致 → 你好小智`（这是它唯一的价值）。
3. **代价是"西西"消失了**：基线里 2 条 `西西`（同音归一后本可命中）在 beam 下变成 `厉害` 和空串。
   beam 追求全局似然最高，会把"低概率但正确"的串吞掉。

**净收益为负**：小智 +1 条，兮兮 −3 条，还要多付 beam 算力。判死。

## 3. 实验三：同音字归一 —— 突破

### 3.1 原理

唤醒判定不该要求"字符完全匹配"，而应该问：**识别出的音，是不是目标词的音？**

```
识别结果 你好西西  →  同音归一 你好兮兮  →  命中
识别结果 你好小致  →  同音归一 你好小智  →  命中
```

这张表是**纯字符串替换**，零算力、零模型改动，C 语言 20 行，可以直接搬到端侧。

### 3.2 规则设计：必须带锚点

第一版我做了裸替换（`想吃 → 小智`），**这是个会炸的坑**：
用户说"我想吃饭" → 变成"我小智饭" → 误唤醒。

改成**带锚点**（要求前面有"你好"/后缀完整）：

```c
/* 裸替换：这些串日常不会独立出现，安全 */
西西→兮兮  嘻嘻→兮兮  希希→兮兮  夕夕→兮兮  溪溪→兮兮  熙熙→兮兮
西嘻→兮兮  细细→兮兮  习习→兮兮
小致→小智  小治→小智  小志→小智  小知→小智  小至→小智  小制→小智
小值→小智  小只→小智  小止→小智  晓智→小智  筱智→小智  小秩→小智

/* 近音：必须带"你好"锚点，否则误唤醒 */
你好小吃→你好小智   你好想吃→你好小智   你好小气→你好小智
你好谢谢→你好兮兮   你行嘻嘻→你好兮兮   你好星星→你好兮兮
你好谢西→你好兮兮   你好学习→你好兮兮
```

### 3.3 全矩阵结果（原始 / 同音归一 / +锚点近音）

| 模型 | 体积 | 峰值内存 | 原始 | 同音归一 | +锚点近音 |
|---|---|---|---|---|---|
| ZipCTC (ctc) | 60 MB | 238 MB | 兮兮 0% / 小智 25% | 17% / 50% | **33% / 100%** |
| Dolphin (ctc) | 99 MB | 242 MB | 0% / 50% | 0% / 50% | 8% / 50% |
| SenseVoice | 228 MB | 366 MB | 0% / 75% | **75% / 75%** | **83% / 75%** |
| **Paraformer** | 228 MB | 382 MB | 0% / 0% | 33% / 75% | **83% / 100%** |
| 流式 zipformer | 24 MB | 380 MB | 0% / 0% | 17% / 50% | **33% / 100%** |

（兮兮样本 12 句、小智样本 4 句，均为真机录音）

几个关键读数：

- **同音字归一一步就把 SenseVoice 的兮兮从 0% 拉到 75%**（只用裸替换表，不需要近音规则）→ 最稳的组合。
  再加锚点近音能到 83%。
- **Paraformer 归一后能到 83%/100%**，代价是需要近音规则；它原始输出是 `你好谢谢 ×5`，全靠锚点规则救回来。
- **ZipCTC 只有 60MB，加规则后小智 100%**——这是端侧性价比最高的一条。
- **流式 24MB 也能小智 100%**，意味着"边听边判定"的实时形态成立（不用等整句录完）。
- **Dolphin 对兮兮无效**：它输出 `你好 嘻`（吞字），归一救不了吞字。

### 3.4 逐条看为什么失败

兮兮 12 句（SenseVoice，归一前）：

```
你行嘻嘻 / . / 你好，西西 / 你好，嘻嘻 / 你好，谢谢 / 你好，嘻嘻
你好，西西 / 你好，西嘻 / 你好，嘻嘻 / 你好亲 / 嘻嘻 / 你好，嘻嘻
```
→ 9 条是"嘻嘻/西西/西嘻"系全部命中，加锚点近音后"你好谢谢"也救回（83%），
真正听错的只有 2 条：空串、"你好亲"。

小智 4 句（ZipCTC，归一前）：
```
你好小志 / 你好小吃 / 你好想吃 / 那叫小智
```
→ `小志/小吃/想吃` 全是"小智"的近音，1 条本来就对。**4 条没有一条是真听错，全是字写错。**

### 3.5 误唤醒

用 20 句无关智能家居指令（`打开客厅的灯`/`把温度调到二十六度`…）做负样本，四条管线全部 **0/20 误唤醒**。

> 这个测试偏容易（负样本里没有近音词）。真正的难度在"你好小爱/小度小度"这类**近音唤醒词**，
> 需要合成音才能测，见 §5 待办。

## 4. 选型建议

| 场景 | 推荐 | 理由 |
|---|---|---|
| 产品唤醒词 | **你好小智** | 大/小模型都能到 100%；"兮兮"最好只有 83% |
| 端侧 ≤64MB 预算 | ZipCTC 60MB + 同音归一 + 锚点近音 | 小智 100%，峰值 239MB，RTF 0.024 |
| 端侧实时（边听边判） | 流式 zipformer 24MB + 同音归一 | 小智 100%，流式形态不需要整句 |
| 精度优先（有 228MB 预算） | SenseVoice + 同音归一 | 兮兮 83% / 小智 75%，裸替换档已到 75%，最稳 |
| 量化 | 官方 int8 | 与 fp32 等价，体积 1/3，更快 |

**"先把词定下来"的答案**：不是重选生僻词，而是**换成"你好小智"**。
生僻音（兮兮 xi-xi）在 ASR 的语言模型里没有先验，模型会强行往常见词上靠，这个偏差任何后处理都补不回来。

## 5. 端侧可直接用：C 实现（已编译验证）

同音字归一是**纯字符串操作**，不需要模型、不需要算力，所以我直接写成了可上板的 C：

| 文件 | 行数 | 说明 |
|---|---|---|
| `scripts/wake_norm.h` | 48 | API 声明 |
| `scripts/wake_norm.c` | 167 | 规则表 + 归一 + 判定 |
| `scripts/test_wake_norm.c` | 75 | 16 条用例（全部取自真实识别结果） |

设计上做了三个决定：

1. **等长字节替换**：所有规则都是「2 个汉字 → 2 个汉字」，UTF-8 下都是 6 字节，
   所以可以 `memcpy` 原地覆盖，**零分配、零额外内存**、缓冲区不增长。嵌入式最友好。
2. **两级规则**：`RULES_HARD`（裸替换）+ `RULES_SOFT`（必须带「你好/你行」锚点）。
3. **判定前先去标点**：`，。！？` 会让锚点规则失配。

```c
#include "wake_norm.h"

static const char *const WORDS[] = {"你好小智", "小智"};

/* 识别结果回来之后 */
if (wake_is_wake_any(rec_text, WORDS, 2)) {
    app_sip_call();          /* 接到现有的 LVGL demo 唤醒回调 */
}
```

编译与验证（MSYS2 gcc 16.2）：

```bash
export PATH=/c/msys64/mingw64/bin:/c/msys64/usr/bin:$PATH
cd scripts
gcc -O2 -std=c11 -Wall -Wextra -o test_wake_norm.exe test_wake_norm.c wake_norm.c
./test_wake_norm.exe
# RESULT: pass=16 fail=0
```

**测试覆盖**：小智 4 条真实误听全中 + `我想吃饭`/`打开客厅的灯` 不误触发 +
兮兮的 `你好，西西。`/`你好，嘻嘻。`/`你行嘻嘻。`/`你好，谢谢。` 全中 + `你好，亲。`/空串/纯标点 不误触发 +
长句中间夹唤醒词命中。

### 5.1 写这份 C 时踩到的两个坑（都是真 bug，不写下来会再踩）

**坑 1：规则顺序 —— SOFT 必须先跑。**
第一版我先跑 HARD 再跑 SOFT，结果 `你行嘻嘻` 永远救不回来：
HARD 先把里面的「嘻嘻」改成「兮兮」，等到 SOFT 找「你行嘻嘻」时原文已经不存在了。
规则表越长，这类**前缀被短规则吃掉**的问题越隐蔽。

同一类坑还有第二形态：`您好 → 你好` 看似是裸替换（HARD），但它必须放在
**SOFT 表第一位**。因为 SOFT 整体先于 HARD 跑，放 HARD 里就永远晚于锚点规则一步
（实测 2/2 漏判：`您好学习` 归一成 `你好学习` 时，`你好学习 → 你好兮兮` 已经跑完了）。

**坑 2：标点 —— 归一前必须先去标点。**
`你好，谢谢`（带中文逗号）匹配不上锚点规则 `你好谢谢`，直接漏判。
Python 侧因为先 `norm()` 去标点才没暴露，C 侧第一版没做就翻了。
现在 `wake_is_wake_any()` 内部先 `strip_punct()` 再归一；
`wake_norm_inplace()` 保留"不处理标点"的原地语义，头文件里已注明。

## 7. 复现

```bash
PY=python3   # 需已安装 sherpa-onnx；脚本只用标准库，不依赖 numpy

$PY scripts/eval.py scan                                     # 列出可用模型与体积
$PY scripts/eval.py cer m_zipctc_s                           # 指令集 CER + RTF + 峰值内存
$PY scripts/eval.py cer m_zipctc_fp32 --file model.onnx --snr 20,10,5   # 噪声档
$PY scripts/eval.py quant                                    # 量化三档对照
$PY scripts/eval.py stwake asr --norm --fuzzy                # 流式唤醒 + 归一
$PY scripts/bench.py                                         # 全矩阵 → .tools/wake_matrix.json
$PY scripts/fa.py m_zipctc_s asr_sv m_paraformer asr         # 误唤醒 → .tools/false_accept.json

# C 版（端侧交付）
export PATH=/c/msys64/mingw64/bin:/c/msys64/usr/bin:$PATH   # 缺这段 gcc 会静默退出 1，不报错
cd scripts && gcc -O2 -std=c11 -Wall -Wextra -o test_wake_norm.exe test_wake_norm.c wake_norm.c
./test_wake_norm.exe                                        # RESULT: pass=16 fail=0
```

产出数据：`.tools/quant3.json`、`.tools/wake_matrix.json`、`.tools/false_accept.json`、
`.tools/cer_fp32_snr.json`、`.tools/cer_int8_snr.json`

**环境注意**：本机 `pip` 装不了任何包（PyPI 不可达），所以 `scripts/eval.py` 全部改成**纯标准库**实现
（`wave` + `array` + `struct` 读写音频、自算编辑距离、`ctypes` 读峰值内存），不依赖 numpy。
噪声注入用"12 个均匀分布求和"近似高斯，按文件名 hash 固定种子，**同一文件每次噪声完全一致**，可比。
