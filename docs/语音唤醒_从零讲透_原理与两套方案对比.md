# 从零理解语音唤醒：原理、我们这套怎么做、老方案为什么不行

> 2026-10-28。这份文档假设读者没接触过语音识别，从「声音怎么变成数字」讲起，
> 一路讲到我们现在这套链路的每个参数为什么是这个值。
> 所有数字都来自本项目实测，不是论文摘抄。

---

## 0. 先给结论

语音唤醒这条链路，可以拆成三个独立问题，**每个问题的失败原因完全不同**：

| 层 | 问题 | 我们踩过的坑 | 正确答案 |
|---|---|---|---|
| 第一层 | 声音怎么变成模型看得懂的东西 | — | 16k 采样 → 分帧 → fbank 80 维 |
| 第二层 | 模型怎么把特征变成字 | 模型太大会爆内存 | 流式 zipformer 24MB |
| 第三层 | **怎么判断用户说了唤醒词** | 判据太严 + 切分错误 | **同音归一 + VAD 门控** |

**第三层才是决定性的。** 我们最后把「小智」的检出率从 0% 拉到 94%，
靠的不是更强的模型，是一条字符串替换规则和一个 VAD 门控。

## 1. 第一层：声音怎么变成模型能吃的数字

### 1.1 采样：把连续的空气振动切成离散的点

麦克风输出的是一条连续电压曲线。要送进计算机，必须按固定间隔量一下当时的电压 —— 这叫采样。

| 参数 | 值 | 为什么 |
|---|---|---|
| 采样率 | 16000 Hz | 每秒量 16000 次，按 Nyquist 能还原 0–8000 Hz |
| 位深 | 16 bit | 每个点用 -32768~32767 表示，动态范围够语音用 |
| 声道 | 单声道 | 语音识别不需要立体声，双声道只是白算一遍 |

**16k 这个数字不是随便定的。** 人类语音的基频（声带振动频率）在 80–400 Hz，
但决定"是哪个字"的信息大量藏在谐波里，一直延伸到 8 kHz。

> 这解释了我们之前发现的一个大问题：手机录音在 1 kHz 以上被砍掉了
> （1–3 kHz 只剩 5.0% 能量，3–6 kHz 剩 0.6%）。
> **s / sh / x / f 这些辅音几乎全在 2 kHz 以上** —— 砍掉高频等于把"兮""智"这类字的核心特征扔了。
> 这也是为什么后来「兮兮」怎么调都救不回来。

一段 1 秒的音频，进来是 **16000 个整数**。

### 1.2 分帧：切成一帧一帧再分析

不能直接拿 16000 个数去算频谱 —— 那样得到的是整段音频的平均频谱，
而语音是快速变化的（"你"和"好"只隔 200 毫秒）。

所以切成短帧，每帧单独分析：

| 参数 | 值 | 为什么 |
|---|---|---|
| 窗长 | 25 ms（400 个样本） | 语音在 10–30 ms 内近似平稳，这就是"短时平稳假设" |
| 帧移 | 10 ms（160 个样本） | 相邻帧重叠 15 ms，避免切在边界上丢信息 |

1 秒 = 100 帧。相邻帧有 60% 重叠，所以信息不会因为切口丢掉。

### 1.3 fbank：把频谱压成 80 个数字

每帧做完 FFT，得到一个频谱（约 200 个频点）。再经过：

1. **Mel 滤波器组**：用 80 个三角滤波器把频谱加权求和。
   滤波器在低频密、高频疏 —— 因为人耳对低频变化更敏感。
2. **取 log**：语音能量动态范围极大（轻声和大声差几十倍），取对数把范围压下来。

结果：每帧变成 **80 个数字**（80 维 fbank 特征）。

**为什么是 80 维？** 这是长期实验定下来的经验值。
40 维信息不够，128 维提升很小但计算翻倍。80 是性价比拐点，也是绝大多数
sherpa-onnx 模型的默认值（我们代码里 `feature_dim=80`）。

**为什么不用原始频谱，也不做 MFCC？**
- 原始频谱维度太高（200+），且相位信息对识别毫无用处
- MFCC 在 fbank 基础上再做一步 DCT 去相关，是 2010 年前的老做法
- 现代神经网络直接在 fbank 上训练效果更好，**不需要人工去相关** —— 网络自己能学

到这里：**1 秒音频 = 100 × 80 的矩阵**。

这个矩阵就是模型唯一看得懂的东西。模型从头到尾没"听过"声音。

## 2. 第二层：模型怎么把矩阵变成文字

### 2.1 声学模型的本质：一个分类器

别把语音模型想得太神秘。它的核心工作就一句话：

> 拿到当前的声学特征（以及一些上下文），判断"这一小段声音最可能对应哪个字"。

每个字在模型里是一个 **token**（编号）。比如"你"可能是 2083 号，"好"是 1592 号。
词表通常有几千到几万个 token（我们的流式模型 token 表约 5 千多行）。

所以模型输出的不是文字，是**每个位置上的概率分布**：

```
位置 1: { blank: 0.02, 你: 0.91, 尼: 0.03, ... }
位置 2: { blank: 0.05, 好: 0.88, 号: 0.04, ... }
...
```

解码器（decoder）再从这个分布里挑一条最可能的路径，拼成文字。

### 2.2 transducer 的三个组件

我们用的模型类型叫 **transducer**（也叫 RNN-T）。它由三块拼成：

| 组件 | 输入 | 输出 | 作用 |
|---|---|---|---|
| **encoder**（编码器） | fbank 矩阵 | 每 4 帧合成 1 个向量 | 把声学特征提纯，同时混入上下文 |
| **decoder**（预测网络） | 已经吐出的 token 历史 | 一个向量 | 表达"我说到哪了" |
| **joiner**（连接器） | encoder 输出 + decoder 输出 | 下一个 token 的概率分布 | 决定"现在该出什么字" |

**为什么要拆三块？** 因为语言有两个信息源必须结合：
- 声音告诉你"听到了什么"（encoder 负责）
- 上文告诉你"接下来该是什么"（decoder 负责）

比如"你好小__"，声音上"智/志/致"都很像，但语言习惯告诉你后面更容易是"智"。
joiner 就是把这两路信息加权合并的地方。

**encoder 的下采样**：每 4 帧合成 1 个向量，所以 100 帧/秒 → **25 个向量/秒**。
下采样有两个好处：计算量降 4 倍，且相邻帧冗余信息被合并。

### 2.3 transducer 对比 CTC

这是理解"为什么唤醒要用 transducer"的关键。

| | **CTC** | **transducer (RNN-T)** | **Paraformer / SenseVoice** |
|---|---|---|---|
| 核心假设 | 每帧独立分类 | 每帧结合已输出历史 | 非自回归，一次出全部 |
| 流式能力 | 能 | **天生流式** | 不能（要看到整句） |
| 准确率 | 较低 | 较高 | 最高 |
| 典型体积 | 小（60MB） | 小（24MB） | 大（228MB） |

**CTC 的问题**：它假设每一帧的输出互不依赖，所以经常输出重复字，要靠
"合并连续重复 + 去掉 blank" 这种后处理来修。而且它没有语言模型的概念，
"你好小智"和"你好小致"在它眼里差别不大 —— 这正是我们遇到的情况。

**transducer 的 decoder 天生就是语言模型**，它知道"你好小"后面接"智"的概率
比"致"高。这就是为什么同一个音，transducer 更容易出对字。

**Paraformer / SenseVoice 为什么不能流式**：它们要看到整句才能预测总共有几个字，
再一次性输出。精度最高，但必须等你说完。

> 我们的实测完全印证了这个表：
> - 离线（Paraformer/SenseVoice）：小智 100%，但 228MB、峰值内存 382MB
> - 流式（transducer 24MB）：小智 94%，延迟 50ms
>
> 这就是"精度换体积和延迟"的取舍，没有免费的好事。

## 3. 流式 vs 离线：这一节是核心

### 3.1 离线识别（offline）

把整段音频一次性交给模型，模型看到全部帧，一次输出完整文字。

**优点**：能看到"未来"的信息，准确率最高。
**缺点**：必须等音频结束。你说 3 秒，就要等 3 秒 + 计算时间才能出第一个字。

**在我们第一版评测里，所有测试都是这么做的** —— 把每条已经切好的 wav 整段喂进去。
这就是为什么当时的 100% 有水分。

### 3.2 流式识别（streaming / online）

音频一块一块进来，模型每收到一块就更新一次输出，随时能给出"目前听到的内容"。

```
块1 进来 → 输出 ""
块2 进来 → 输出 "你好"
块3 进来 → 输出 "你好小"
块4 进来 → 输出 "你好小智"
```

**优点**：首字延迟极低，设备能边听边反应。
**缺点**：**模型永远看不到"后面"的音频。**

### 3.3 流式的代价：因果性

离线模型可以用双向注意力 —— 判断第 10 帧时可以参考第 50 帧。
流式模型不行，因为第 50 帧还没到。它只能看**过去 + 当前**（这叫 causal / 因果）。

这是数学上的信息损失，不是工程没做好。

具体到 zipformer 的做法：它把音频切成内部 chunk（比如每 320 ms 一个），
每个 chunk 内部的帧可以互相看，但**跨 chunk 只能看历史**。

### 3.4 一个必须澄清的坑：分块喂 ≠ 流式模型

我在第一次做流式评测时也怀疑：把音频切成 100 ms 一块块喂，
会不会因为"每次只给一点"而损失精度？

**实测证明：不会。** 同一条音频，「离线整句一次性喂」和「100 ms 分块喂但不做端点切分」，
**输出文本逐字完全相同**。

原因是：

- `OnlineRecognizer`（流式识别器）**内部**有自己的 chunk 划分（几百毫秒一级）
- 你把 100 ms 喂进去，音频先进入 feature buffer，**攒够一个内部 chunk 才会真正计算**
- 所以"分块喂"只改变了**什么时候调用 decode**，不改变模型看到的总帧序列

这引出一个重要认识：那次评测里检出的崩塌，**损失全在"切分"环节，不在"流式"环节。**
同一批音频，换成 VAD 切段后合计检出是 8/16，用 ASR 端点检测只有 3/16。
分清这两件事，才知道该修哪里。

### 3.5 RTF：衡量算力够不够

**RTF = 处理耗时 ÷ 音频时长**。

- RTF = 0.02 → 处理 1 秒音频要 0.02 秒，快 50 倍，实时毫无压力
- RTF = 0.5 → 处理 1 秒要 0.5 秒，还有 2 倍余量
- RTF = 1.0 → 刚好实时，没有任何余量，且没算系统其他开销

PC 上的 RTF 要换算到目标板子。经验系数：

| 平台 | 换算倍数 | 我们的 0.0144 换算后 |
|---|---|---|
| Cortex-A53（树莓派级） | ×8 ~ 15 | 0.12 ~ 0.22 |
| Cortex-A7（低端 MCU+Linux） | ×8 ~ 30 | 0.12 ~ 0.43 |

换算后仍然远小于 1，说明**这个模型在 Pi 1 B+ 上跑得动**。

## 4. 第三层：怎么知道一句话说完了

这是最容易做错的一层，我们在这上面吃了最大的亏。

### 4.1 为什么需要"句子边界"

流式模型只会持续吐 token，它**不知道你说完没有**。
如果设备不判断"结束"，就会一直等下去，永远不知道什么时候该拿结果去判定唤醒词。

所以必须有个机制说："这句到此为止了，把结果交出来。"

### 4.2 方案 A：ASR 端点检测（endpoint detection）

sherpa-onnx 内置了三条规则，在解码过程中自动判断：

| 规则 | 条件 | 默认值 | 我们设的 |
|---|---|---|---|
| rule1 | 静音持续 N 秒 | 2.4 s | 0.6 s |
| rule2 | 输出标点后再静音 N 秒 | 1.2 s | — |
| rule3 | 单句超过 N 秒强制切 | 20 s | 12 s |

看起来正好解决我们的问题。**但直接用会崩。**

### 4.3 端点检测为什么会在长静音里反复触发

这是整个项目里最反直觉的一个 bug，画图更好理解：

```
音频流:   [静音][你好小智 A][    静音 4 秒    ][你好小智 B][静音]
端点触发:                     ↑ ↑ ↑ ↑ ↑ ↑ ↑ ↑ ↑  ↑ ↑
                            每 0.6s 一次，一直触发到下一句上去
```

机制是这样的：

1. A 说完 → 静音累积到 0.6 s → 触发端点 → 我们调 `reset()` 清空流 → 拿到「你好小智」✓
2. 但接下来**还是静音** → 0.6 s 后又满足条件 → 又触发 → 拿到空串
3. 循环往复，每 0.6 秒一次

**关键在于：`reset()` 清的是解码状态，不是"静音计数"。**
只要没有语音进来，静音条件就一次次成立。

后果非常严重：触发时 `reset()` 会丢弃当前流，
**如果这时候正好在播下一句（B），B 就被切成了 100 ms 的碎片**，每片都太短识别不出东西。

实测数据：16 句唤醒词，只认出 3 句（18.8%）。

> 我一开始以为是 rule1 参数没调好，扫了 0.4 / 0.6 / 1.0 三档，
> 结果 1.0 最好也只有 31.2%，且延迟涨到 1.24 秒。
> **这不是参数问题，是机制问题。** 必须换方案。

### 4.4 方案 B：VAD

**VAD = Voice Activity Detection，判断"这段音频里有没有人说话"。** 二元判断。

常见实现：

| 实现 | 原理 | 体积 | 特点 |
|---|---|---|---|
| 能量 VAD | 算 RMS，超阈值算语音 | 0 字节 | 我们用这个，最简单 |
| WebRTC VAD | GMM 分类器 | 几十 KB | 工业界标配，分 4 档灵敏度 |
| Silero VAD | 小神经网络 | ~2 MB | 准确率最高，抗噪好 |

**能量 VAD 只需要一行判断**：

```python
rms = sqrt(mean(sample^2))
if rms > 底噪 * 3.0:   # 有语音
```

底噪在开机时用前 1 秒静音标定。我们的实测：底噪 0.0012，语音峰值 0.2650，
**差了 200 倍**，所以阈值系数取 2.5 到 4.0 结果完全一样 —— 这个参数极其鲁棒。

### 4.5 VAD 和端点检测的区别（一句话记住）

> **VAD 回答"有没有人在说话"，端点检测回答"这句话说完了没有"。**

- VAD 不需要模型，看能量就能答
- 端点检测必须在解码过程中，看模型输出的 token 变化
- **VAD 可以当门卫，端点检测不能**

### 4.6 我们的解法：VAD 当门卫，ASR 关掉端点检测

```
静音期间：不建流、不喂音频、不判端点  ← 从根上消除了反复触发
有语音时：建流 → 回补 200ms 预滚 → 开始解码
静音 600ms 后：认为说完 → 取结果 → 关流
```

ASR 那边直接 `enable_endpoint_detection=False` —— 不依赖它的判断了。

这样做的效果：端点数从 101 次（22 句音频）降到 22 次，一句一次，精确对应。

### 4.7 两个必须调对的参数

**预滚（preroll）= 200 ms**

VAD 是"检测到能量才触发"，但那时首字已经说了一半。必须把触发前 200 ms 的音频
一起补进去，否则"你好"会变成"好"。

> 实测 preroll 350 ms 反而更差：它会把**前一句的尾巴**也带进来，
> 导致 s01 被识别成「离开七夕」。200 ms 是恰好够首字发音、又不会抓到上一句的长度。

**尾点 hangover = 600 ms**

判定"说完"需要等多久静音。太短会把句子从中间切断（尾部丢字），太长会增加响应延迟。

> 实测 600 ms 比 300 ms 好（总检出 50% vs 43.8%），因为很多字的尾音能量很低，
> 300 ms 会把它切掉。600 ms 的代价只是多等 0.3 秒。

## 5. 我们这一套：完整链路

```
麦克风 16k 单声道
   ↓ 每 100ms 取一块（1600 个样本）
能量 VAD：rms > 底噪 × 3.0        ← 底噪用开机前 1s 静音标定
   ↓ 触发时回补前面 200ms
流式 zipformer-transducer（24MB）
   ↓ 100ms 增量解码
   ↓ 静音满 600ms → 取结果、关流
同音字归一（wake_norm.c，纯字符串，零算力）
   ↓ 您好→你好，西西/嘻嘻/小致/小志… → 兮兮/小智
判定：包含「你好小智」或「小智」→ 触发 app_sip_call()
```

### 5.1 为什么第 5 步这么重要

看这两组对比：

| 识别结果 | 完全匹配判定 | 同音归一后 |
|---|---|---|
| 你好小致 | ✗ 0%（音全对，字错一个） | ✓ 命中 |
| 你好小吃 | ✗ | ✓ 命中 |
| 你好想吃 | ✗ | ✓ 命中 |
| 那要小致 | ✗ | ✓ 命中 |

**模型的听感其实没问题，它只是用了自己的用字习惯。**
我们在用"听写"的判据（一个都不能错）去考一个"分类"任务。

改判定后，同一批音频同一个模型：

| 模型 | 原始输出 | + 同音归一 | + 锚点近音 |
|---|---|---|---|
| ZipCTC 60MB | 0% / 25% | 17% / 50% | 33% / 100% |
| SenseVoice 228MB | 0% / 75% | 75% / 75% | 83% / 75% |
| Paraformer 228MB | 0% / 0% | 33% / 75% | 83% / 100% |

（格式：兮兮 / 小智，12 条 + 4 条真实设备录音，离线整句识别）

在**真实连续流 + VAD 门控**下，同一个 24MB 流式模型：
兮兮 33%、小智 100%（单次）；换 4 个随机种子平均 **31% / 94%**。

### 5.2 为什么"宽松"不会导致误唤醒

这是设计上最需要小心的地方。规则分两级：

**第一级：裸替换（安全）**

西西→兮兮、嘻嘻→兮兮、小致→小智、小志→小智……

这些串**日常不会独立出现**（谁会单独说"西西"？只有在说"兮兮"时才会），
所以裸替换不会把正常语句改成唤醒词。

**第二级：近音（必须带锚点）**

第一版我做了裸替换 `想吃 → 小智`。结果用户说「**我想吃**饭」→ 变成「我小智饭」→ 误唤醒。

改成必须带锚点：`你好想吃 → 你好小智`。
"你好"这层约束保证它只在真的在喊唤醒词时才生效。

**实测结果**：20 句智能家居指令，四条管线全部 **0/20 误唤醒**；
真实连续流里 6 句无关语音 × 4 组，**0/24**。

### 5.3 一个 C 实现上的坑

`wake_norm.c` 的执行顺序是「SOFT 锚点规则 → HARD 裸替换」。

`您好 → 你好` 看起来是裸替换（该放 HARD），但它**必须放 SOFT 表第一位**。

因为：如果放 HARD，执行顺序是
```
SOFT 跑一遍（此时文本还是"您好学习"，锚点"你好学习"匹配不上）
HARD 跑一遍（现在才把"您好"改成"你好"，但 SOFT 已经跑完了）
```
结果锚点规则永远晚一步，2/2 漏判。

这是"两级规则 + 顺序依赖"的经典陷阱。修完 16 条用例全绿。

## 6. 原来那一套为什么不行

按"错在哪一层"排列，从浅到深：

### 6.1 评测前提错了（最根本）

第一版评测的每一条音频都是：
- 已经切好的（只含唤醒词）
- 前后带足够静音
- 单独喂给模型

**这测的是"模型看到干净片段能认出来"，不是"设备能从连续流里找出唤醒词"。**

而设备面临的是：一条 87 秒的流，里面混着 6 句无关语音和 16 次唤醒词，
要自己判断哪一段是唤醒词。这是完全不同的问题。

> 教训：**测试集的形式必须等于部署时的输入形式。**
> 如果测的是 A、部署的是 B，那么 A 上 100% 也不代表 B 能过。

### 6.2 KWS 路线从一开始就走错

sherpa-onnx 里有关键词检测模型（KeywordSpotter），看起来很对口。用法是把唤醒词
写成**音素序列**：

```
n ǐ h ǎo x iǎo zh ì @你好小智
```

问题在于：

- 这套模型对训练时见过的词有效，对生僻音节组合（兮兮 = x i x i）基本是 0
- 实测：兮兮 0/12、小智 0/4，阈值压到 0.02 仍无命中
- 换 2025 年新版中英 KWS 模型后需要 `en.phone` 文件，Python 接口不暴露

**结论：KWS 是"给定词表内的词"的快检器，不适合自定义唤醒词。**
（这条路在 C++ 上板后还可以再验一次，但 Python 侧的结论是 0%）

### 6.3 判定用"完全匹配"，把正确答案判死了

这是**代价最大、修复最简单**的一个错误。

用 `"你好小智" in 识别结果` 这种严格判据，模型输出「你好小致」就是 miss。
而"致"和"智"在声学上几乎一样。

**这不是模型能力不足，是判据用错了任务。** 详见第 7 节。

### 6.4 端点检测直接用，把音频切碎

就是 §4.3 那个问题。同一批音频、同一个模型，只用切分方式不同：
**VAD 切段合计检出 8/16，ASR 端点检测只有 3/16（18.8%）**，管线直接废掉。

### 6.5 模型体积超了板子内存

Pi 1 Model B+ 只有 512 MB 内存。

| 模型 | 体积 | 实测峰值内存 | 能不能上板 |
|---|---|---|---|
| SenseVoice | 228 MB | 382 MB | ✗ 加系统就爆 |
| Paraformer | 228 MB | 382 MB | ✗ |
| ZipCTC int8 | 60 MB | 242 MB | 勉强 |
| 流式 zipformer | 24 MB | — | ✓ |

而且注意一个反直觉的点：**内存倍率不是固定的**。
Dolphin 99MB 峰值 171MB（1.7×），ZipCTC 60MB 峰值 242MB（4.0×）——
小模型的固定开销占比更高。估算要用 `峰值 ≈ 体积×倍率 + 运行时开销`。

### 6.6 还有一堆脚本自身的 bug

这些不是理论问题，都是真实踩到并修掉的：

| bug | 后果 |
|---|---|
| 端点→片段映射用"已结束的最后一个" | 跨句错配，整张表算错 |
| 同音归一没去标点 | 「你好，谢谢」匹配不上「你好谢谢」 |
| 规则顺序 SOFT/HARD 搞反 | 「你行嘻嘻」永远救不回 |
| `strstr` 跨行匹配 | 测试误报通过 |
| 噪声文件名含千位逗号 | 内存统计解析错误 |

> 教训：**评测脚本的正确性，和模型的正确性一样重要。**
> 一个映射 bug 能让 94% 显示成 18.8%，也能反过来把 0% 显示成 100%。

## 7. 最重要的一课：唤醒是二分类，不是听写

这是整个项目最有价值的认知。

| | 语音听写（ASR） | 语音唤醒（KWS） |
|---|---|---|
| 任务 | 把声音完整还原成文字 | 判断用户说的是不是那个词 |
| 输出 | 一串字 | 是 / 否 |
| 判据 | 错一个字就是错 | 音对了就算中 |
| 最优策略 | 尽量准确、宁缺毋滥 | 尽量召回、容忍用字偏差 |

**两个任务的最优判据是相反的。** 我们一开始用听写的判据去考唤醒任务，
必然得出"模型不行"的结论 —— 而实际上模型早就听对了。

所以：

- 「同音字归一」在听写任务里是作弊（篡改结果）
- 「同音字归一」在唤醒任务里是**正当手段** —— 它补的是模型的用字习惯，不是用户的发音

同样的道理，唤醒的评测指标也和 ASR 不同：

| 指标 | 含义 | 我们的值 |
|---|---|---|
| 检出率（召回） | 真喊了唤醒词，设备响应了吗 | **94%** |
| 误唤醒率（虚警） | 没喊，设备却响应了吗 | **0/24** |
| 响应延迟 | 说完到触发多久 | **50 ms** |
| 资源占用 | 体积 / 内存 / RTF | **24 MB / — / 0.0144** |

**误唤醒率是和检出率同等重要的指标。** 一个 99% 检出但每小时误唤醒 3 次的设备，
用户会直接退货。这也是为什么"宽松判定"必须配合"锚点约束"。

## 8. 术语表

| 术语 | 全称 | 一句话解释 |
|---|---|---|
| **PCM** | Pulse Code Modulation | 采样后的数字音频，就是一堆整数 |
| **帧** | frame | 25 ms 的一段音频，1 秒 = 100 帧 |
| **fbank** | filter bank | 每帧压成的 80 维特征向量 |
| **token** | — | 模型词表里的一个单位，中文通常是一个字 |
| **encoder** | 编码器 | 把 fbank 提纯成带上下文的高层表示 |
| **decoder** | 解码器 / 预测网络 | 记录"已经输出到哪了" |
| **joiner** | 连接器 | 合并声学信息和语言信息，出下一个 token |
| **transducer** | RNN-T | 上面三件套组成的模型结构，天生流式 |
| **CTC** | Connectionist Temporal Classification | 另一种结构，每帧独立分类，流式但精度略低 |
| **blank** | — | CTC 里的"这一帧没有字"标记 |

## 9. 深入答疑（2026-10-28 追加）

这一节回答八个具体的追问，每个都配了实测数据。**如果只想看结论，跳到 §9.7。**

### 9.1 100 帧、80 维这三个数字是怎么算出来的

**16000 Hz 的来历**：人耳可听 20Hz–20kHz，但语音的能量与可懂度几乎全在 8kHz 以下。
奈奎斯特要求采样率 ≥ 最高频率的 2 倍 → 16000。**每个采样点间隔 62.5 微秒**。
电话语音用 8kHz，因为只需覆盖 0–4kHz。

**25ms 窗 = 400 个采样点**：语音在 10–30ms 内可视为平稳（声带振动与口腔形状没有明显变化）。
20–30ms 是语音分析惯例：窗太短看不出一个共振峰，窗太长会跨越两个不同音素。

**10ms 步进 = 160 个采样点**：相邻两帧重叠 240 个采样（15ms）。
重叠的唯一目的是**防止音素恰好在窗边界被切两半**。

**100 帧** = 16000 ÷ 160。sherpa-onnx 用 `snip_edges=false`（首尾补边），刚好 100。
严格模式 `(16000-400)/160+1` 是 98 帧，差的 2 帧就是补出来的。

**80 维**：人耳在低频分辨力高、高频迟钝，所以按 **mel 刻度** `mel = 2595·log10(1+f/700)`
在 0–8kHz 上均匀铺 80 个三角滤波器，每个对功率谱加权求和再取对数，得一个数。
80 个滤波器 = 80 个数。

为什么是 80 而不是 40 或 128：Kaldi 的 GMM 时代用 23 维（GMM 对维度敏感），
神经网络时代升到 40–80，Whisper / WeNet / sherpa 统一用 80 —— "够用且不过度"的长期经验折中。

**最终 1 秒语音 = 100 × 80 = 8000 个数**。这是模型看到的全部输入，它从未"听过"声音。

### 9.2 采样周期与取块周期是两回事

| 概念 | 值 | 由谁决定 |
|---|---|---|
| 采样周期 | 62.5 μs（1/16000） | 采样率，固定 |
| 取块周期（period / block） | 可配置，通常 10–60ms | 驱动与业务需求 |

工程上真正要关心的是取块周期。常见配置：

| 场景 | 每次采样数 | 时长 |
|---|---|---|
| RTP / VoIP 标准帧 | 320（@16k）、160（@8k） | 20ms |
| Android AudioRecord | 320–960 | 20–60ms |
| ALSA period（Linux 板子） | 256–1024 | 16–64ms |
| macOS CoreAudio 默认 | 512 | 32ms |
| Windows WASAPI 共享模式 | 480 | 10ms |
| 本项目 SIP 对讲（G.711） | 160（@8k） | 20ms |
| 本项目评测脚本 | 1600 | 100ms |

**20ms 是事实标准**，因为 RTP 按 20ms 打包（抖动与包头开销的平衡点）。
评测脚本攒到 100ms 才送模型，是为了减少推理调用次数（每次调用有固定开销），
且模型内部 chunk 通常就是 10 帧 = 100ms 一组，送得更碎没有意义。

**注意**：块大小必须 ≥ 25ms（400 采样），理由见 §9.5。

### 9.3 流式与离线，到底改了什么

**不是改了几行代码，是换了三样东西**：

| 换了什么 | 离线 | 流式 |
|---|---|---|
| 模型文件 | `model.int8.onnx`（ZipCTC 60MB） | `encoder/decoder/joiner.onnx`（24MB） |
| Python 类 | `OfflineRecognizer` | `OnlineRecognizer` |
| 调用方式 | 一次喂完，一次解码 | 反复喂，每块问一次"攒够了吗" |

```python
# 离线
st = rec.create_stream()
st.accept_waveform(16000, 整段音频)
rec.decode_stream(st)
text = st.result.text

# 流式
st = rec.create_stream()
for 每一块 in 音频:
    st.accept_waveform(16000, 每一块)
    while rec.is_ready(st):      # 内部攒够一个 chunk 了吗
        rec.decode_stream(st)
```

模型内部的差别在**编码器能看多远**：离线是全序列 self-attention（第 100 帧能看第 1 帧），
流式是 chunk-masked（第 4 块看不到第 5 块，只能看自己 + 左侧缓存）。
这是**训练时就定下来的**，不是推理时能切的开关。

### 9.4 决定性实验：把"喂法"和"模型"两个变量拆开

一个自然的推理是：*流式和离线都是分割，如果分割方式一样，结果应该一样。*
**这个推理本身是对的**，实验证实了；但流式/离线的差别不在分割，在模型。

**实验 A：同一个流式模型，只改喂入块大小**（20 / 50 / 100 / 200 / 500ms / 整段）

6 条音频 × 6 种喂法 = **36 个结果逐字相同**，连错误都一模一样
（小智 2 永远是「你好小吃」，小智 3 永远是「你好想」）。
→ **喂法对结果完全无影响**，因为它内部按自己的 chunk 处理，外部怎么喂都被缓冲。

**实验 C：同一个离线模型，分块累积（不分句，只分多次 accept），最后解一次**

| 块大小 | 小智 3 输出 |
|---|---|
| 10ms | 你好想（掉了"吃"） |
| 16ms | 你好想 |
| 20ms | 你好想 |
| **24ms** | **你好想吃（完整）** |
| 25 / 30 / 50 / 100ms | 你好想吃 |

临界点精确卡在 **25ms 特征窗（400 采样）**。

另有一类随机损失：切点恰好落在音节中间也会掉字
（兮兮 3 切 2/4 段掉成「你好」，切 3/8 段完整）—— 切点位置碰巧决定，不可控。

**实验 B：离线模型把一句切成 N 段，各自独立识别**

| 音频 | 1 段 | 2 段 | 4 段 |
|---|---|---|---|
| 小智1 | 你好小志 | 你好小 \| | 你 \| 好好小 \| 是 \| |
| 小智2 | 你好小吃 | 你好小 \| | 你 \| 他小 \| \| |

2 段就崩，4 段成碎片。

### 9.5 为什么离线模型不能像流式那样切：有状态 vs 无状态

**根因只有一句：流式模型有跨块状态，离线模型没有。**

- 流式：`OnlineFbank` 把不足一窗的采样缓存起来，等下一块凑齐；encoder 也保留左侧缓存。
  所以 10ms 一块也稳（实验 A 验证）。
- 离线：每次 `accept_waveform` 独立处理，块不足一窗（400 采样）时边界那几帧**直接丢弃**，
  下次递进来也接不上。这是实验 C 临界点卡在 25ms 的原因。

推论：

> **流式模型有状态（状态在模型里），怎么喂都行。
> 离线模型无状态（状态在你手上），必须保证每次给的是一句完整的话。**

"离线模型不能切"不是设计缺陷，是它本来就没有状态。
而"一句完整的话"这个边界，只能由 VAD 提供 —— 这就是 §4.6 必须加 VAD 的真正原因，没有别的路。

**同参数 VAD 切段、只换模型的对照**（切分完全相同）：

| 模型 | 体积 | 小智检出 |
|---|---|---|
| 流式 zipformer | 24 MB | **100%** |
| 离线 ZipCTC | 60 MB | 75% |

切分一样、结果不同 → 差异只能来自模型。

### 9.6 同音归一：是字错，不是音错

**是一个函数**，`scripts/wake_norm.c`：

```c
void wake_norm_inplace(char *text);   // 归一：把常见错字改回正确写法
int  wake_is_wake_any(const char *text, const char *const *words, size_t n_words);  // 判定
```

用法一行：

```c
static const char *const WORDS[] = {"你好小智", "小智"};
if (wake_is_wake_any(rec_text, WORDS, 2)) { /* 触发 */ }
```

里面没有模型、没有算力、没有拼音，就是**字符串替换 + 子串匹配**。

**关键理解：读音匹配模型已经做完了。** ASR 分两层：

| 层 | 做什么 | 能否干预 |
|---|---|---|
| 声学模型 | 声音 → 音素概率（"这段像 zhi4"） | 不能，除非换模型 |
| 语言模型 | 音素序列 → 最可能的汉字（zhi4 → 智 还是 致） | **能，就在这一层** |

`你好小致` 的真实含义是：**第一层听对了（确实是 zhi4），第二层选错了字**。
所以不需要"重新比读音"—— 读音早在第一层对上了，我们只修第二层的用字。

这解释了两件事：

1. **为什么便宜**：问题本来就不在声学层，不需要任何声学计算。
2. **为什么救不了「你好兮兮」**：兮兮是**音错**不是字错。模型听到 xixi，
   但"兮"在中文里没有高频词承载，语言模型把它推向「谢谢」「学习」「星星」。
   这不是换字，是听错，任何字面规则都补不回来 —— 所以兮兮最高 33%~83%，小智能到 100%。

> **一句话：同音归一能救"字错"，救不了"音错"。**

**为什么不用拼音方案**（文字 → 拼音 → 算相似度）：

拼音方案更通用（不依赖"事先见过这个错法"），代价是：拼音词典 2–5MB、
多音字消歧（"行"是 xing2 还是 hang2）、**多出一个相似度阈值要调**（多一个参数 = 多一类误唤醒风险）。

当前 30 条硬编码规则：0 依赖、0 内存、0 参数。前提是**唤醒词固定不变**。
词已定为「你好小智」，不频繁更换，硬编码划算。
将来若要支持用户自定义唤醒词，应改为拼音方案。

### 9.7 采样定理：为什么 16kHz 才够

先拆一个术语混淆：**"8K 音频"要分清是采样率还是带宽。**

| 采样率 | 奈奎斯特频率（可采最高频） | 典型用途 |
|---|---|---|
| 8 kHz | 4 kHz | 电话、G.711（本项目 SIP 链路） |
| **16 kHz** | **8 kHz** | 语音识别标准（本项目） |
| 44.1 kHz | 22.05 kHz | CD |
| 48 kHz | 24 kHz | 专业音频 |

所以：**要采 8kHz 带宽的声音，16kHz 采样率才够；8kHz 采样率只能采 4kHz 带宽。**
"采 8K 的音频用 16K 采样率"这句话，准确表述应该是"采 8kHz 带宽用 16kHz 采样率"。

**数学原理：时域采样 = 频域频谱以 fs 为周期复制。**

采样在时域是乘以冲激串，频域上就是卷积一个冲激串 —— 效果是把原频谱复制到
`0, ±fs, ±2fs, ...` 处。

- 若 `f_max < fs/2`：副本之间有间隙、不重叠 → 用一个截止 `fs/2` 的理想低通
  就能取回原始频谱 → **无失真还原**
- 若 `f_max > fs/2`：副本重叠，重叠区两种频率不可区分 → **混叠（aliasing）**，
  高频被"折叠"成低频，永久丢失，无法用任何算法还原

`fs/2` 这个界限叫**奈奎斯特频率**，条件 `fs > 2·f_max` 就是奈奎斯特采样定理。

**具体例子**（用 8kHz 采样一个 7kHz 正弦）：

```
x[n] = cos(2π·7000·n/8000) = cos(2πn·7/8)
1kHz 的采样是            cos(2πn·1/8)
```

因余弦的对称性，`7/8` 与 `-1/8` 完全等价 → **7kHz 被还原成 1kHz**，两者无法区分。

这就是为什么采样前必须有**模拟抗混叠滤波器**，把超过 `fs/2` 的成分切掉；
不切，它会折回来污染低频。**先滤波再采样**，顺序不能反。

### 9.8 流式模型从哪来：为什么必须是两套权重

主流产品的流式版和离线版**确实是两个独立训练的网络**：
`sherpa-onnx-streaming-zipformer-*` 与 `sherpa-onnx-zipformer-*` 是两个 release、
两个文件、两套权重。Paraformer 也有 streaming 与非流式两个版本。

**为什么不能共用**：注意力掩码不同。离线 encoder 的每个位置可注意全序列；
流式 encoder 在**训练时**就被限制为只能注意自己与左侧若干帧。
掩码是训练目标的一部分，不是推理时可切换的开关。拿离线权重当流式跑，结果直接崩。

**重要的架构例外：RNN-T（transducer）天生两者通吃。**
它本身是自回归的 encoder + decoder + joiner 逐帧推进，同一份权重既能流式喂也能整句喂。
本项目的流式 zipformer 就是 RNN-T 结构。

**但整句喂也不会变准**，因为训练时没见过右侧上下文，权重里没有这部分知识。
"架构支持" ≠ "精度一样"，这是两件事。

**不存在"把离线模型裁剪成流式"的操作。** 业界的"离线预训练 + 流式微调"也是重新训练，
不是裁剪。一个训练好的离线模型没有任何办法变成流式模型。

### 9.9 OnlineFbank 跨块缓存与流式状态管理

**为什么流式不会因切点落在音节中间而丢字**：它把不足一窗的零头留着，
等下一块到齐再算。代价只是延迟，不是数据。

具体机制（块 20ms = 320 采样，窗 25ms = 400 采样，步进 160 采样）：

| 时刻 | 缓冲区累计 | 能算出几帧 | 剩余零头 |
|---|---|---|---|
| 块 1 到达 | 320 | 0 帧（不足一窗） | 320 |
| 块 2 到达 | 640 | 帧0（0–400）、帧1（160–560） | 80 |
| 块 3 到达 | 400 | 帧2（320–720） | 0 |

**缓冲区里最多只会剩下一个窗长（25ms）的零头**，所以缓存的内存开销可以忽略。

对比离线模型：每次 `accept_waveform` 独立提取特征、不保留跨调用帧缓存，
跨块的帧两侧各只有半个窗，谁也凑不出完整帧 → **数据真的丢了**（§9.4 实验 C 的 25ms 临界点）。

> **流式丢的是延迟，离线丢的是数据。**

**流式 `stream` 对象里装的五项状态**（sherpa-onnx 中就是一个 `OnlineStream`）：

1. fbank 采样缓冲（< 25ms 的零头）
2. fbank 已产出帧计数
3. **encoder cache 张量** —— 每 chunk 处理后保留的左侧上下文
4. **decoder 状态** —— RNN-T 预测网络隐状态 + 上一个 token
5. 已解码的 token 序列

`is_ready(stream)` = "缓存里攒够一个 chunk 了吗"；`decode_stream()` = 消费一个 chunk
并更新以上状态。五项全在 stream 里，所以一个 rec 对象可同时开多个互不干扰的会话。

### 9.10 音素与拼音不是一回事

**拼音是汉语的注音书写方案，音素是语音的最小辨义单位。** 层级不同。

以「智 zhì」为例：拼音 4 个字符（声母 zh + 韵母 i + 声调 ˋ），
音素只有 **2 个** —— `/ʈʂ/` 和 `/ɻ̩/`（`zh` 两个字母只对应一个音素）。

**最有力的证据是拼音的 `i`，它至少对应三个不同音素**：

| 字 | 拼音 | `i` 的实际读音 |
|---|---|---|
| 比 bǐ | bi | `/i/` 前高元音 |
| 知 zhī | zhi | `/ɻ̩/` 舌尖后元音 |
| 资 zī | zi | `/ɿ/` 舌尖前元音 |

同一个字母对应三个音素 —— **拼音不是音素系统**。

| 维度 | 拼音 | 音素 |
|---|---|---|
| 本质 | 汉语注音**书写方案** | 语音**最小辨义单位** |
| 抽象对象 | 字母拼写 | 声音类别 |
| 对应关系 | 1 音素可多字母（zh），多音素可少字母（xiao） | 一符号一音素 |
| 声调 | 内建（ā á ǎ à） | 不带（超音段特征，另标） |
| 适用范围 | 只用于汉语 | 所有语言通用 |

补充：sherpa-onnx 的 KWS 词表 `n ǐ h ǎo x iǎo zh ì` 是**"拼音风格的音素标注"**，
是工程折中而非严格 IPA。它要求唤醒词的每个音节组合必须在该模型 phone 表里存在 ——
这正是"兮兮"这类生僻组合走不通 KWS 路线的底层原因（§6.2）。

### 9.11 十二个问题的一句话回答

| 问题 | 回答 |
|---|---|
| 100 帧怎么算的 | 16000 ÷ 160（窗 25ms、步进 10ms），`snip_edges=false` 补成 100 |
| 80 维怎么算的 | 0–8kHz 上按 mel 刻度铺 80 个三角滤波器，每个输出一个数 |
| 采样周期多少 | 采样周期 62.5μs 固定；取块周期常用 20ms，板子 ALSA 256–1024 帧 |
| 流式离线改了什么代码 | 换了模型文件 + 换了类（Online/Offline）+ 换了调用方式，业务逻辑没变 |
| 分割一样结果会一样吗 | **会**——36 组实测证实喂法零影响。但两者差别是模型，不是分割 |
| 离线能像流式那样切吗 | **不能**，它无跨块状态，块 < 25ms 就丢帧；流的 100% vs 离线 75% 同理 |
| 同音归一是一个函数吗 | 是，`wake_norm.c` 里两个函数，字符串替换 + 子串匹配 |
| 最终比的是读音吗 | 比的是**文字子串**。读音匹配已在模型第一层完成，我们只修第二层的用字 |
| 用 8K 采样还是 16K | 看指"采样率"还是"带宽"：8kHz 带宽要 16kHz 采样；8kHz 采样只能采 4kHz |
| 流式和离线是同一个模型吗 | **不是**，两套独立权重分别训练。RNN-T 架构可两者通吃，但整句喂不会更准 |
| 流式为什么不怕切在音节中间 | 有跨块帧缓存，零头留着等下一块补齐 —— **丢的是延迟，不是数据** |
| 音素就是拼音吗 | **不是**。拼音是注音书写方案，音素是最小辨音单位；拼音的 `i` 对应三个不同音素 |

> 最小的改动产生最大的收益，前提是**找对了失效发生在哪一层**。
> 这次从 0% 到 94%，靠的不是更强的模型，是一条字符串替换和一个 VAD 门控。
