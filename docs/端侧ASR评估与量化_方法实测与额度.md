# 端侧语音识别：评估方法、量化流程与成本

> 场景切换：原来打算「音频上云 → 云端大模型转文字 → 控制设备」。
> 换成端侧本地识别，链路短了、隐私好了、不用网了，但**准确率从云端大模型的 95%+ 掉到小模型的 90% 上下**。
> 所以问题变成：**怎么量化这个差距，值不值得换。**
>
> 本文给三样东西：① 评估指标体系与标准测试集 ② 量化实操 ③ 免费额度实测数字。
> 所有数据都是本轮在本机跑出来的，不是引用的。

---

## 一、先说最重要的一条：干净环境 CER 几乎没有区分度

我搭了 20 句智能家居指令测试集（`打开客厅的灯` `把温度调到二十六度` `播放下一首歌` …），
TTS 合成，跑六个模型算 CER：

| 模型 | 体积 | CER | 全对 | RTF |
|---|---|---|---|---|
| Paraformer-zh | 228MB | **0.00%** | 20/20 | 0.023 |
| Moonshine-zh | 135MB | **0.00%** | 20/20 | 0.032 |
| Qwen3-ASR 0.6B | 937MB | **0.00%** | 20/20 | 0.265 |
| Dolphin-base | 99MB | 0.80% | 19/20 | 0.017 |
| Zipformer-CTC-s | 60MB | 2.40% | 18/20 | 0.023 |
| SenseVoice-small | 228MB | 4.00% | 18/20 | 0.031 |

**五个模型里有三个全对，最大差距 4 个百分点。** 这个表用来选型等于没选 ——
因为干净 TTS 太简单，所有模型都饱和了。

> 这条比任何模型结论都重要：**如果你用合成音或者安静环境录音去评估端侧 ASR，会得到
> 「都差不多」的假结论，然后随便挑一个，上设备后发现不能用。**

## 二、真正有区分度的是噪声下的 CER

端侧的真实条件是：3 米远场、有空调/电视/人声、混响 0.3~0.6s。
所以我给测试集按固定随机种子混入白噪，扫 20/10/5dB 三档：

```bash
python scripts/asr_cer.py --models <模型目录...> --set ../../.tools/cer_set --snr 20,10,5
```

**实测（CER，越小越好）：**

| 模型 | 体积 | 干净 | 20dB | **10dB** | 5dB |
|---|---|---|---|---|---|
| **Zipformer-CTC-small** | **60MB** | 2.4% | 0.8% | **0.8%** | **2.4%** |
| SenseVoice-small | 228MB | 4.0% | 4.0% | 4.8% | 4.0% |
| Qwen3-ASR 0.6B | 937MB | 0.0% | 0.0% | 7.2% | 1.6% |
| Dolphin-base | 99MB | 0.8% | 2.4% | 4.0% | 12.0% |
| Moonshine-zh | 135MB | 0.0% | 4.8% | **13.6%** | **28.8%** |

### 三个反直觉结论

**1. 最小的模型抗噪最好。** 60MB 的 Zipformer-CTC 在 5dB（很吵）下 CER 只 2.4%，
比 228MB 的 SenseVoice 还稳。而 135MB 的 Moonshine 在干净环境是满分、10dB 就掉到 13.6%。

**2. 干净环境的排名和噪声下的排名完全无关。** Moonshine 干净时 0%、噪声下垫底；
Zipformer-CTC 干净时 2.4%（倒数第二）、噪声下第一。

**3. 大模型不等于鲁棒。** Qwen3 937MB 在 20dB 完美，10dB 掉到 7.2% ——
样本只有 20 句，这个跳变有采样噪声成分，但也说明它没有针对噪声做优化（它是通用 LLM，不是端侧方案）。

### 这条对选型的直接后果

之前我按「唤醒词召回」推荐 SenseVoice（兮兮 9/12）。现在按「噪声 CER」看，
**端侧正确答案是 Zipformer-CTC-small（60MB）**。两个指标测的是不同能力：

| 指标 | 测什么 | 谁赢 |
|---|---|---|
| 唤醒词召回（生僻词） | 词表覆盖、长尾音节 | SenseVoice 228MB |
| 指令 CER（常用词，带噪） | 声学鲁棒性 | Zipformer-CTC 60MB |

**你要做的是智能家居指令控制 —— 那是常用词 + 噪声场景，所以 60MB 的 CTC 才是对的选择。**
只有「必须支持生僻唤醒词」时才需要上 228MB。

### 三维综合表（准确率 / 内存 / 速度，都实测）

| 模型 | 体积 | 10dB CER | 峰值 RSS | RTF | 定位 |
|---|---|---|---|---|---|
| **Dolphin-base** | 99MB | 4.0% | **171MB** | **0.017** | 内存最省 + 最快，准确率中等 |
| **Zipformer-CTC-s** | **60MB** | **0.8%** | 197MB | 0.023 | 抗噪最好，但内存反而不是最低 |
| Moonshine-zh | 135MB | 13.6% | 215MB | 0.045 | 干净准、噪声崩，不推荐上板 |
| SenseVoice-small | 228MB | 4.8% | 333MB | 0.031 | 生僻词强，需 A53 四核 |
| Paraformer-zh | 228MB | — | 337MB | 0.025 | 强依赖上下文，实现复杂 |
| Qwen3-ASR 0.6B | 937MB | 7.2% | ~1.5GB | 0.265 | 只能做服务端 |

**权衡结论**：

- 芯片只有 **256MB RAM** → 选 **Dolphin（99MB / 171MB RSS）**，把 CER 的 3 个点换成能跑起来
- 芯片有 **512MB RAM** → 选 **Zipformer-CTC（60MB / 197MB RSS）**，抗噪多 3 个点更值
- 两者 RTF 都在 0.02 量级，A7 双核上折算 0.3~0.6，都能实时

**没有一个是「全面最优」。** 这就是端侧选型的常态 —— 不是挑最好的模型，
而是挑「在你的内存预算内，准确率最高的那个」。

## 三、评估指标体系（端侧专用）

通用 ASR 只看 CER 是不够的。端侧要同时看四组指标：

### 3.1 准确率

| 指标 | 定义 | 判据 |
|---|---|---|
| **CER** | 字级编辑距离 / 参考字数（中文按字） | <5% 直接可用；5~15% 需容错解析；>15% 不可用 |
| **句准率** | 完全正确的句子占比 | 语音控制场景要求 >70%，因为一条指令错了就是误操作 |
| **关键词召回** | 指令动词/名词是否被正确捕获 | 比 CER 更贴近业务：CER 10% 但「打开」听成「大的」就是灾难 |
| WER | 词级（英文用） | 中文一般用 CER |

**为什么语音控制要额外看「指令槽位准确率」**：
CER 是平均值，但控制指令是「动词 + 对象 + 数值」三元组。
`把温度调到二十六度` 听成 `把温度调到二十六度` 才对；错一个字（36 度）就是功能错误，
而 CER 只掉 8%。所以要看**三元组整体抽取正确率**，不是 CER。

### 3.2 速度

| 指标 | 定义 | 端侧判据 |
|---|---|---|
| **RTF** | 推理耗时 / 音频时长 | <0.5 可实时（留一半给业务）；0.5~1.0 勉强；>1.0 跟不上 |
| **首字延迟** | 说话结束到出第一个字 | <300ms 感觉自然；>800ms 用户会重复说 |
| 流式分片延迟 | 每片处理耗时 ≤ 片长 | 流式模型必须满足，否则积压 |

**PC 数据不能直接用。** 换算系数（经验值）：

| 目标芯片 | PC RTF 折算 |
|---|---|
| Cortex-A7 双核 1.2GHz | ×15~30 |
| Cortex-A53 四核 1.2GHz | ×8~15 |
| Cortex-A55 四核 1.5GHz | ×5~8 |
| Cortex-M7（无 NEON 加速） | 不要想，跑不动通用 ASR |

所以 PC 上 RTF 0.02 的模型，A7 上到 0.3~0.6 —— 勉强能实时。RTF 0.03 的 SenseVoice 到 A7 就 0.45~0.9，风险大。

### 3.3 内存

| 指标 | 说明 | 判据 |
|---|---|---|
| 峰值 RSS | 加载 + 推理峰值 | 必须 < 可用内存 × 0.6（留系统余量） |
| 常驻增量 | 相对空进程的净增 | 一般 ≈ 模型体积 × 1.5~2.5 |
| 冷启动时间 | 从进程启动到可识别 | <1s 无感；>3s 用户会觉得设备坏了 |

**注意**：估算「模型体积 ×2」是粗算法。Zipformer 系有 attention 缓存、CTC 有中间张量，
实测常到 2~3 倍。上板必须实测，不能估。

### 3.4 鲁棒性（端侧真正的门槛）

按优先级：

1. **噪声 SNR**：白噪 / 人声嘈杂 / 家电稳态噪声，10dB 是最常见的远场条件
2. **距离**：0.3m（近讲）/ 1m / 3m / 5m
3. **混响**：T60 0.3s（小房间）/ 0.6s（客厅）
4. **回声**：设备自己在放音乐时的 AEC 残留（智能音箱必测）
5. **口音/方言**：至少测普通话不标准的样本
6. **语速**：0.8× / 1.0× / 1.3×
7. **信道**：不同麦克风（手机录音的低通会毁掉高频，见另一份文档）

| 数据集 | 规模 | 特点 | 获取 |
|---|---|---|---|
| **AISHELL-1** | 178h，test 7176 句 | 学术标配，朗读、安静、近讲 | OpenSLR SLR33 免费 |
| **AISHELL-2** | 1000h | 更大，需申请 | 官网申请 |
| **WenetSpeech** | 10000h+ | **test_net / test_meeting 两套**，后者是会议远场，最接近端侧 | 官网申请 |
| **Primewords** | ~100h | 公开免费，质量一般 | OpenSLR SLR47 |
| **THCHS-30** | 30h | 老、小，只够冒烟 | OpenSLR |
| **SpeechIO Leaderboard** | 多场景 | 含小米音箱、白噪音等真实端侧场景 | 公开测试集 |

| **KeSpeech** | 方言 | 测方言鲁棒 | 开源 |

### 怎么用（务实版）

**调试阶段**：不用下载几个 G。按下面三条自建，2 小时搞定：

1. **指令集自建**：把你产品真正要支持的命令列 50~100 条（`打开客厅的灯` `把空调调到二十六度`），
   TTS 合成 + 真人各录一遍 → 这是**最贴合业务的评测集**，比任何公开集都有用
2. **噪声混入**：用 `asr_cer.py --snr` 扫档
3. **远场补测**：手机放 1m/3m 各录 20 条

**定标阶段**：跑一次 AISHELL-1 test（7176 句），得到与业界可比的 CER 基线，
用来判断「我的实现是不是有问题」——如果 AISHELL-1 test 上 CER 和论文差很多，是集成错了；
如果接近，那你的模型能力就是这么多。

**验收阶段**：WenetSpeech test_meeting（远场）+ 自己录的真实场景集。

### 一个必须避免的坑

**不要用 TTS 合成的干净音做最终结论。** 本轮实测：六个模型在 TTS 集上三个满分，
在 10dB 噪声下最大差距 13 个百分点。合成音只能验证「链路通不通」，不能验证「能不能用」。

同理，**不要用手机录音做评估**：手机录音 App 的低通会把 1kHz 以上砍掉
（实测 1–3kHz 只剩 5.0%，而正常是 29.1%），辅音信息全丢，结论会被带偏。

## 五、量化怎么做

### 5.1 三种方法，按投入排序

| 方法 | 需要什么 | 体积收益 | 精度损失 | 适用 |
|---|---|---|---|---|
| **动态 PTQ**（`quantize_dynamic`） | 只要 ONNX 文件 | 2~4× | 通常 <1% CER | **首选，10 分钟搞定** |
| **静态 PTQ**（`quantize_static`） | 500~1000 条校准音频 | 3~4× | <0.5% | 动态不够时上 |
| **QAT**（量化感知训练） | 训练环境 + 数据 + 算力 | 4× | 最小 | 前两者都不达标时才做 |

端侧 99% 的情况，**动态 PTQ 就够了**。因为 ASR 模型的算力瓶颈在 encoder 的矩阵乘，
权重 int8 化收益最大，激活值的动态范围问题影响较小。

### 5.2 动态量化：完整流程

```python
# 1. 装工具（sherpa-onnx 自带的 runtime 不暴露量化接口，要单独装）
#    pip install onnxruntime

from onnxruntime.quantization import quantize_dynamic, QuantType

# 2. 量化（一条命令的事）
quantize_dynamic(
    "model.onnx",              # fp32 输入
    "model.int8.onnx",         # int8 输出
    weight_type=QuantType.QUInt8,   # 权重 uint8，激活也量化
    per_channel=True,               # 逐通道，精度更好（推荐开）
    reduce_range=False,             # 非 VNNI CPU 上开 True 更稳
)
```

命令行等价：

```bash
python -m onnxruntime.quantization.preprocess --input model.onnx --output model_pre.onnx
python -m onnxruntime.quantization.quantize --input model_pre.onnx --output model.int8.onnx --per_channel
```

### 5.3 静态量化：需要校准集

```python
from onnxruntime.quantization import quantize_static, CalibrationDataReader, QuantType

class Reader(CalibrationDataReader):
    def __init__(self, feeds):        # feeds: list[dict[str, np.ndarray]]
        self.it = iter(feeds)
    def get_next(self):
        return next(self.it, None)

quantize_static("model.onnx", "model.int8.onnx", Reader(feeds),
                quant_format=QuantType.QInt8, per_channel=True)
```

校准集取 500~1000 条**真实录音**（不是 TTS），覆盖不同噪声档。太少会偏，太多没必要。

### 5.4 量化之后必须做的一件事：重测 CER

**量化一定掉精度，只是掉多少的问题。这个「多少」必须用同一套测试集量出来。**

```bash
# fp32 与 int8 用同一测试集、同一 SNR 档对比
python scripts/asr_cer.py --models ../../.tools/m_zipctc_fp32 ../../.tools/m_zipctc_s \
  --set ../../.tools/cer_set --snr 20,10,5
```

判定：**int8 相对 fp32 的 CER 上升应 <1 个百分点**。超过就要考虑静态 PTQ 或 QAT。

### 5.5 量化实操中的坑

1. **不是所有算子都能量化**。`QuantizeLinear` 不支持自定义算子；sherpa-onnx 的
   Zipformer 用了标准的 Conv/MatMul/Attention，没问题；但如果你自己的模型有自定义层，
   `quantize_dynamic` 会静默跳过该层（体积收益变小但不报错）。
2. **`.ort` 格式不能量化**。ONNX Runtime 的优化格式要先转回 onnx。
   sherpa-onnx 的 Moonshine 用 `.ort`，所以只能用它官方给的量化版，不能自己再压。
3. **`reduce_range` 在 ARM 上要注意**：老 ARMv7 没有 VNNI 指令，int8 的 `uint8` 范围问题
   可能导致精度异常，此时设 `reduce_range=True`（用 int7）。
4. **per_channel 必开**。逐 tensor 量化对 CNN 系精度损失明显，逐通道几乎无感。
5. **量化后一定要在目标硬件上验**。x86 的 int8 kernel 和 ARM 的 int8 kernel 实现不同，
   x86 上 CER 没掉，不代表 ARM 上没掉。

### 5.6 实测：fp32 → int8（本机亲手跑）

对象：`sherpa-onnx-zipformer-ctc-small-zh`（端侧最优候选），fp32 原版 190.3MB。

```python
from onnxruntime.quantization import quantize_dynamic, QuantType
quantize_dynamic("model.onnx", "model.int8.onnx",
                 weight_type=QuantType.QUInt8, per_channel=True, reduce_range=False)
```

**结果：**

| 版本 | 体积 | 10dB CER | 5dB CER | RTF |
|---|---|---|---|---|
| fp32 原版 | 190.3MB | 0.8% | 2.4% | 0.030 |
| **自己动态量化** | **59.6MB（3.19×）** | **0.8%** | 3.2% | **0.048** |
| 官方 int8 版 | 60.0MB | 0.8% | 2.4% | **0.022** |

（测试集 20 句 125 字，0.8% = 1 个字，这个量级的差异统计意义有限，只能说明「没有崩」）

**三个结论：**

**1. 精度几乎无损。** 10dB 下完全一致，5dB 下差一个字。这验证了「动态 PTQ 对 ASR 够用」。

**2. 体积压到 1/3.19。** 190MB → 60MB，这是能不能上 A7 级芯片的分水岭。

**3. 但我自己做出来的 int8 比官方慢一倍（0.048 vs 0.022）。**

第 3 条是最该记住的。原因不是量化本身，而是**图结构**：官方 int8 是「先做图优化（算子融合、常量折叠）再量化」，
我直接对原始 fp32 图量化，Q/DQ 节点插在一堆没融合的算子之间，运行时调度开销反而上升。

想复现官方的做法要加 `quant_pre_process`：

```python
from onnxruntime.quantization.shape_inference import quant_pre_process
quant_pre_process("model.onnx", "model_pre.onnx", skip_symbolic_shape=True)
quantize_dynamic("model_pre.onnx", "model.int8.onnx", ...)
```

**但在 ASR 模型上这一步会失败** —— 本机实测两种参数都挂了：

- `skip_symbolic_shape=False` → `Exception: Incomplete symbolic shape inference`
- `skip_symbolic_shape=True` → 直接崩，输出二进制乱码

原因是 ASR 模型带动态 batch/时间维，符号 shape 推断不完整。
（这块可以继续啃 onnx 的 shape_inference，但性价比低。）

### 5.7 所以量化的实操建议

**优先级从高到低：**

1. **官方有 int8 版就用官方的**。它们做过量化和图优化，速度和体积都是最优，
   自己重做大概率打不过（本轮实测：自己做的慢一倍）。
2. **官方只有 fp32 时**，直接 `quantize_dynamic` + `per_channel=True`。
   精度没问题（<1 个百分点），体积 3× 收益是实打实的，速度可能不升反降
   —— 但端侧瓶颈通常在内存带宽，体积降 3× 的收益大于 RTF 的小幅劣化。
3. **官方 int8 精度不达标时**，才上静态 PTQ（要 500~1000 条真实校准音）。
4. **QAT 基本不用考虑**。除非你在做产品级定制模型，否则投入产出不划算。

**每次都必做**：用同一套测试集、同一批噪声样本，对比 fp32 与 int8 的 CER。
不做这一步的量化等于赌博。

## 五·补、内存实测（独立进程，避免累积）

同一个进程里连续加载多个模型，RSS 会累积，测出来是假的。
必须每个模型单起一个进程 —— 下面的数字是这么测的：

| 模型 | 模型体积 | 实测峰值 RSS | RSS / 体积 |
|---|---|---|---|
| Dolphin-base | 99MB | **171MB** | 1.7× |
| Zipformer-CTC-small | **60MB** | **197MB** | **3.3×** |
| Moonshine-base-zh | 135MB | 215MB | 1.6× |
| SenseVoice-small | 228MB | 333MB | 1.5× |
| Paraformer-zh | 228MB | 337MB | 1.5× |

（RSS 含 Python 解释器 + sherpa-onnx 运行时约 70MB，C/C++ 实现会低 30~50%）

**两个反直觉点：**

**1. 模型体积排序 ≠ 内存排序。** Zipformer-CTC 体积最小（60MB），RSS 却比 99MB 的 Dolphin 还高 26MB。
原因是 CTC 的中间张量（encoder 输出序列很长）需要更多工作内存。
**所以「挑最小的模型」这个直觉在端侧是错的，必须实测 RSS。**

**2. 体积小的模型往往内存倍率高。** Zipformer-CTC 是 3.3×，大模型反而只有 1.5×。
小模型省的是磁盘/Flash，不一定省 RAM。

**上板时的估算公式**（比「体积 ×2」靠谱）：

```
峰值 RAM ≈ 模型体积 × 倍率 + 运行时开销
倍率：CTC 系 3.0~3.5，transducer 系 1.5~2.0
运行时开销：C++ 约 15~30MB，Python 约 70MB
```

按这个算 Zipformer-CTC-small 上 C++ 大概是 `60×3.3 + 25 ≈ 220MB` —— 这个数直接决定了
你能选什么档位的芯片（256MB 的 A7 芯片只剩 36MB 给系统，很紧张）。

## 六·补、端侧 vs 云端：到底快多少（这条可能反直觉）

你换本地的动机之一是「整套会更快」。**不一定成立**，要看芯片档位。

### 链路拆解

**本地（A7 双核，Zipformer-CTC 60MB）**

```
VAD 检出说话结束      100~200ms
ASR 处理 1.5s 音频    1.5s × RTF(板端 0.3~0.6) = 450~900ms
业务执行              50~100ms
─────────────────────────────────────
合计                  600ms ~ 1.2s
```

**云端**

```
VAD 检出              100~200ms
上传 1.5s 音频        24KB @ 4G 上行 ≈ 200~500ms
服务端识别            300~800ms（大模型反而更慢）
下发 + 执行           50~150ms
─────────────────────────────────────
合计                  650ms ~ 1.65s
```

**结论：在 A7 级芯片上，本地和云端基本打平（0.6~1.2s vs 0.65~1.65s）。**

本地的优势不是延迟，而是这三条：

| 维度 | 本地胜 | 云端胜 |
|---|---|---|
| 无网可用 | ✅ | ❌ |
| 隐私（音频不出设备） | ✅ | ❌ |
| 无月费/无调用量限制 | ✅ | ❌ |
| 准确率（生僻词、口音） | ❌ | ✅ |
| 换词/改需求 | ❌ 要重新验证 | ✅ 改 prompt 即可 |
| 首次延迟（冷启动） | ❌ 加载模型 1~3s | ✅ 无 |

**只有在 A53/A55 级芯片上，本地才明显更快**（RTF 降到 0.05 量级，ASR 只花 75ms，
整链路压到 300ms 以内）—— 那时候「本地比云端快一倍」才成立。

**所以真正的决策依据不是「快不快」，而是「能不能接受联网 + 隐私要求 + 月费」。**
延迟在 A7 档位差不多，别拿它当理由。

### 折中方案（多数产品的实际选择）

```
常开层（端侧）: VAD 2MB，判断「有没有人在说话」
唤醒判定（云端）: 只上传命中的 1~2 秒，其他时间不上传
指令识别（端侧）: 常用指令本地跑，生僻说法才上云
```

这样流量和隐私面都小，换词靠云端，常用指令不受网络影响。

## 七、三个问题的直接回答

**Q1：端侧 ASR 能力怎么评估？**

四组指标缺一不可：准确率（CER + **句准率** + 指令槽位正确率）、速度（RTF + 首字延迟）、
内存（峰值 RSS + 冷启动）、鲁棒性（**10dB SNR** + 距离 + 混响）。
**关键：干净环境的 CER 没有区分度**（本轮实测六模型三个满分），必须在 10dB 噪声下测。

**Q2：市面有哪些标准评估？**

AISHELL-1（学术基线，免费）、WenetSpeech test_meeting（远场，最接近端侧）、
SpeechIO Leaderboard（真实端侧场景）、Primewords（免费小集）。
但**最该用的不是它们**——把你自己产品的 50~100 条指令做成测试集，TTS + 真人各一遍，
这才是唯一能指导决策的评测集。公开集只用来定标「我的集成有没有问题」。

**Q3：量化怎么做？**

动态 PTQ 一条命令，10 分钟，体积降 2~4×、CER 通常掉不到 1 个百分点，99% 场景够用。
不够再上静态 PTQ（要 500~1000 条真实校准音）。QAT 是最后手段。
**量化后必须用同一测试集重测 CER**，而且要在**目标硬件**上测（x86 和 ARM 的 int8 kernel 不同）。
