# 唤醒词识别 · 音频优化实验结论

日期：2026-10-28
目标：验证「把输入音频优化成和测试样本一样的节奏、一样的音质」能否提升唤醒识别率。

---

## 一、一句话结论

**不能。这条路已经在四个维度上被证伪。**

同一段 40 秒录音、12 句「你好兮兮」、同一套模型：

| 处理方式 | 意图 | 唤醒召回 |
|---|---|---|
| 原声（基线） | 不改动 | **67%** |
| 匀速压缩到参考音时长 | 语速对齐 | 42% |
| DTW 逐帧压到参考音时长 | 节奏+时长全对齐 | **8%** |
| 保持原时长、只重排内部节奏 | 只对齐节奏结构 | 17% |
| 按参考音做逐频点 EQ | 音色对齐 | 75% / 58%（换参考音就回落） |
| 节奏 + 音色 | 最像参考音 | 8% |

**唯一"变好"的 EQ 组在交叉验证中站不住**：用 TTS 标准音做参考是 9/12，换成官方真人样本做参考就掉到 7/12，而基线两次都是 8/12 —— 平均值等于基线，是波动不是收益。

参考音本身是 TTS 合成（1.08 秒说完四个字），比真人自然语速快 40–55%。"向它对齐"等于把真人语音压成机器语速，方向就是反的。

## 二、实验设计

工具：`scripts/prosody_match.py`（配套 `scripts/prosody.sh`）

四件事在同一批句子上做完，模型和阈值完全不变，只变音频：

1. **切句**：`kws_test.split_speech` 按能量把 39.9 秒切成 12 句，逐句处理、逐句统计。
2. **节奏对齐**：40 维 log-mel（25ms 窗 / 10ms 步、逐句 CMVN）→ DTW（对角/水平/垂直三方向，欧氏距离）→ 得到双向映射。
   - `warp`：按「参考帧 → 源帧」把每句压成参考音的 1.08 秒（压缩比 ×0.50 ~ ×1.64）
   - `shape`：按「源帧 → 参考帧」× 尺度，把参考音的**音节相对比例**铺回源句总时长，总长不变
3. **音色对齐**：复用 `audio_bench.eq_curve_to_ref`，用参考音的长时平均语音谱做逐频点增益（限幅 ±18dB、5 点平滑），STFT 域施加。
4. **双模型判定**：
   - KWS：sherpa-onnx `kws-zipformer-wenetspeech-3.3M`，阈值 0.25 / 加分 1.0
   - ASR：`SenseVoice-small int8`，VAD 切句后整句识别，再做唤醒词模糊匹配

对照音频（28 秒，手机可直接听）：原声 9s → 节奏对齐 9s → 音色对齐 9s

## 三、结果明细

### 3.1 主实验（参考音 = TTS 标准音「你好兮兮」，1.08s）

```
组              KWS命中       SV唤醒
raw             0/12        8/12    你好西西 | - | 你好西西 | 你好嘻嘻
fast            0/12        5/12    你好谢谢 | - | 你好嘿呵 | 你好谢嘿
warp            0/12        1/12    你好西西 | - | 你看行行 | 你好谢谢
shape           0/12        2/12    你好谢嘻 | 我 | 你好谢 | 你好谢谢
eq              0/12        9/12    你好西西 | 好 | 你好欣星 | 你好嘻嘻
shape+eq        0/12        1/12    你好西嘻 | Oh | - | 你好谢谢
```

### 3.2 交叉验证（参考音 = 官方真人样本）

```
raw   8/12    fast 0/12    warp 1/12    shape 0/12    eq 7/12    shape+eq 0/12
```

基线两次完全一致（8/12），说明切句和判定链路稳定；`eq` 从 9 掉到 7，确认无真实增益。
节奏类处理两次都崩，确认有害是稳定的。

### 3.3 时间规整的实际强度

12 句里 11 句比参考音长，压缩比分布：

```
源时长   压到参考      保时长重排
1.30s → 1.08s ×0.83     1.30s ×1.00
2.18s → 1.08s ×0.50     2.19s ×1.00   ← 压掉一半
2.18s → 1.08s ×0.50     2.19s ×1.00
1.72s → 1.08s ×0.63     1.73s ×1.00
```

×0.50 意味着每个音素的时长被砍半，塞音和擦音的瞬态直接被吃掉 —— 这不是"更标准"，是**信息损毁**。

## 四、为什么方向是反的

1. **参考音是 TTS，不是"标准真人"。** SAPI 合成的「你好兮兮」是 1.08 秒匀速吐字；真人带停顿、拖音、重音，1.5–2.2 秒才是自然值。把真人往 TTS 上拉，等于学一个模型从没在训练集里见过的节奏。
2. **声学模型吃的是多样性，不是"标准"。** KWS/ASR 的训练数据里真人语速分布很宽，模型对自然语速鲁棒；对**局部变速**（DTW 的 ×2 / ×0.5 摆动）反而不鲁棒，因为变速会改变音素时长比例，破坏 fbank 特征的时序模式。
3. **EQ 只能改谱包络，改不了发音。** 音色对齐最多把频响拉近，但识别失败的主因在音素层面（见第五节），频谱整形碰不到。
4. **重采样实现细节也会引入失真。** `warp` 用整数索引抽样，压缩时直接丢样本，×0.50 相当于无抗混叠的抽取 —— 这一项本身就会制造噪声，所以 `warp` 的 8% 有一部分是加工副作用。但 `shape`（时长不变、抽样率 ≈1）同样是 17%，说明**即使排除重采样失真，节奏重排仍然有害**。

## 五、真正的瓶颈（此前已定位）

拆词验证是决定性的：

| 关键词 | KWS 命中 |
|---|---|
| `n ǐ h ǎo`（你好） | **10 次** |
| `x ī x ī`（兮兮） | **0 次** |
| `n ǐ h ǎo x ī` | 1 次 |
| `h ǎo x ī x ī` | 0 次 |

「你好」这一节模型是认识的，**卡在「兮兮」**。3.3M 参数的 KWS 模型对这个音节的建模几乎为零 —— 真人怎么念都不中，而 TTS 合成的同一句话 4/4 全中（因为 TTS 的音素时长规整，恰好落在模型稀疏覆盖的点上）。

所以：
- 不是麦克风问题（用户录音 1–4kHz SNR 38.1dB，比官方样本的 28.7dB 更干净）
- 不是发音问题（SenseVoice 12 句里 8 句听出「你好西西/嘻嘻」）
- 不是音频加工问题（本文档四组实验 + 之前的 11 种预处理全部无效）
- **是模型容量 + 唤醒词选词问题**

---

## 六、下一步（按性价比排序）

1. **换唤醒词**（最快、零成本）。工业界常规做法：唤醒词要选模型覆盖好的音节。「兮兮」是生僻拟声，换成「你好小智」「小智小智」「嗨小智」这类常见词，3.3M 模型大概率能稳定检出。
   验证方法：录一段包含 4 个候选词各 5 遍的音频，用同一套 KWS 跑对比表 —— 需要本人配合录音，**这是唯一能确证"换词有效"的实验**。
2. **用 SenseVoice 做唤醒**（已可用，当前 67%）。`scripts/wake_sv.py` 已跑通，RTF 0.018。代价是内存 239MB，上板需要算力评估。
3. **换更大的 KWS/ASR 模型**（sherpa-onnx 中文 KWS 只有一个 3.3M 模型，没有更大的可选；替代是流式 ASR + 关键词检索，等同第 2 条的重型版）。
4. **自训唤醒词模型**（成本最高，只在产品化阶段考虑）。

## 八、踩到的坑（供后续复用）

1. **`split_speech` 在 numpy int16 上溢出**：`v*v` 用 numpy int16 相乘会溢出成负数，`math.sqrt` 报 `math domain error`。已改成先 `float(v)`。用 `array('h')` 传入时不触发，用 `np.asarray(..., int16)` 传入时必崩。
2. **DTW 反查表会截断句首句尾**：用「参考帧 → 源帧」反查来生成"保时长"版本，只能覆盖 `m` 的值域，首尾整段丢失（第一版 `shape` 组掉到 17% 有这个成分）。正确做法是正向映射 `smap`（源帧 → 参考帧）再乘尺度。修完仍是 17%，才确认是真实现象。
3. **参考音必须是 16k 单声道 wav**：`kws_test.read_wav_mono16k` 只吃这个格式，mp3 要先过 ffmpeg。

## 九、换唤醒词验证（2026-10-28 下午）

用户决定把唤醒词从「你好兮兮」换成「你好小智」。这一节能做的都做了，
但**结论要等真人录音**，原因见 9.3。

### 9.1 词表拼接（已完成，可检出）

`tokens.txt` 是音素级（声母/韵母 + 声调），三个候选词的 8 个音素全部存在：

```
n ǐ h ǎo x iǎo zh ì        @你好小智     → 3/3 检出（SAPI 语速 -3/0/+3）
x iǎo zh ì x iǎo zh ì      @小智小智     → 1/1 检出
x iǎo zh ì                 @小智         → 1/1 检出
```

关键词文件：`.tools/kws/keywords_xiaozhi.txt` / `keywords_zzzz.txt` / `keywords_zz.txt`

### 9.2 压力测试：TTS 无法区分两个词

给合成音做变调（×0.80，模拟男声）与加噪（SNR 12dB），两词结果**完全一致**：

| 条件 | 你好小智 | 你好兮兮 |
|---|---|---|
| 干净（多种语速） | 3/3 | 4/4 |
| 变调 ×0.80 | ✅ | ✅ |
| 加噪 SNR 12dB | ✗ | ✗ |
| 变调+加噪 | ✗ | ✗ |

说明两件事：
1. KWS 对**噪声**敏感、对**音色/变调**不敏感（12dB 白噪直接打死，两个词一样死）。
2. **合成音在这个问题上没有区分度** —— 想用它证明"换成小智就能检出"是不成立的。

### 9.3 为什么必须真人录音

用户录音 SNR 38.1dB，比合成音加噪条件干净得多，所以「兮兮 0/12」不是噪声导致。
也不是音色（同一段录音里「你好」单独跑能中 10 次，证明说话人被模型覆盖）。
剩下的唯一变量就是**这个音节的发音本身在模型解码路径里能不能成立**，
而这一点 TTS 测不出来 —— 必须用同一个人的真实声音说「小智」。

### 9.4 录音采集工具（已就绪）

`scripts/wake_record.py` + `scripts/rec.sh`：按提示逐遍录音，一个词一个目录。

```bash
# 默认 4 个候选词 × 5 遍 = 20 条，每遍 3 秒，3 秒倒计时后自动开始
bash scripts/rec.sh

# 自定义
bash scripts/rec.sh --words 你好小智,小智小智,小智,你好兮兮 --repeat 5 --seconds 3
```

候选词设计有讲究，能同时回答两个问题：

| 候选词 | 音节数 | 想验证什么 |
|---|---|---|
| 你好小智 | 4 | 目标词，最常用形态 |
| 小智小智 | 4 | 叠词形态（唤醒词工业标准做法） |
| 小智 | 2 | 若 4 字不行而 2 字行 → 是长词解码发散 |
| 你好兮兮 | 4 | 对照基线，确认本次录音条件与上次一致 |

采集要求（脚本里也会提示）：自然语速、**连贯说完不要中间停顿**、离麦 20–30cm。
停顿会被 VAD/流式解码切成两段，整词路径永不成立 —— 这是之前踩过的坑。

### 9.5 录完之后的对比命令

### 9.6 SenseVoice 侧已同步支持

`wake_sv.py` 的匹配逻辑改成"整词命中优先，近音兜底"：


并新增 `--words 你好小智,小智小智` 参数。实测：
`你好小智` → 识别文本「你好小智」，★ 唤醒；
`你好兮兮` → 识别文本「你好西西」，仍能通过近音表唤醒（未破坏原行为）。

## 十、真人手机录音实测：「你好小智」也不行（2026-10-28 17:10）

用户手机录了一条 5.3 秒音频，连说 4 遍「你好小智」（词内连贯无停顿）。
文件 `.tools/rec/1028_2.m4a`（48kHz 立体声 AAC，转 16k 单声道后 5.31s）。

### 10.1 KWS 结果：0/4，且调参救不回来

4 遍连说被 VAD 并成 1 句，用 SenseVoice 的 token 时间戳精确切开（每遍 1.08–1.68、
2.04–2.58、2.94–3.48、3.90–4.50 秒），逐遍归一化后单独测：

```
阈值 0.25 / 加分 1.0    → 0/4
阈值×加分网格（阈值降到 0.02，加分到 2.0）→ 全表无命中
```

阈值压到 0.02 仍然 0 命中，说明**不是"差一点"，是解码路径根本没走到这个词**。

### 10.2 关键发现：手机录音把 1kHz 以上砍掉了

同一批音频的频谱体检，和之前 Jabra USB 麦克风录的同内容对比：

| 频段 | 手机录音 | Jabra 录音 |
|---|---|---|
| 100–300Hz | 47.6% | 30.0% |
| 300–1000Hz | 40.0% | 27.8% |
| **1000–3000Hz** | **5.0%** | 29.1% |
| **3000–6000Hz** | **0.6%** | 9.1% |
| **6000–7800Hz** | **0.0%** | 0.1% |

辅音信息（s/sh/zh/x 这些）几乎全部在 1kHz 以上，6000Hz 以上直接为 0 —— 典型的
手机录音 App「语音模式/降噪」硬低通。KWS 的 fbank 特征在 1–4kHz 基本是废的。

**这解释了为什么同一个人「你好」在 Jabra 录音里能中 10 次，在手机录音里只中 1 次。**

### 10.3 高频补偿实验：能救「你好」，救不了 4 音节词

按 900Hz 以上逐级提升（最多 +18dB）再测：

| 补偿 | 1–3kHz 占比 | 「你好」检出 | 「你好小智」检出 |
|---|---|---|---|
| +0dB | 8.2% | 1/4 | 0/4 |
| +6dB | 19.8% | — | 0/4 |
| +12dB | 38.3% | 2/2 | 0/4 |
| +18dB | 54.3% | 2/2 | 0/4 |

补偿确实提升了 KWS 能力（「你好」从 1/4 到 2/2），但**四音节的「你好小智」依然 0 命中**。
两条证据合起来：词不是瓶颈，模型对长词的解码能力 + 对这个说话人的适配才是。

### 10.4 同一批音频走 SenseVoice：3/4

逐段识别 + 近音容错后：

| 段 | 识别文本 | 唤醒 |
|---|---|---|
| p01 | 你好小智 | ★ |
| p02 | 你好小智 | ★ |
| p03 | 你好小**志** | ★（近音容错） |
| p04 | **那要**小志 | ✗ |

而**整条不切段**跑 SenseVoice 时是 **4/4 全对**（`你好，小智你好，小智你好，小智你好，小智。`）。
说明切段会丢上下文，长句识别比短句准 —— 实时场景要用"攒够一拍再识别"而不是切得太碎。

### 10.5 结论

1. **换词救不了 KWS**。「兮兮」0/12 换成「小智」0/4，且阈值 0.02 也无命中。
2. **录音链路是隐藏变量**。手机录音 App 的低通会把 1–4kHz 掐掉，KWS 直接废掉。
   以后任何录音测试都要先跑 `scripts/diag.sh` 看频段占比，别把链路问题当成算法问题。
3. **产品化上板不受这条影响**（板子用自己的 ADC + 麦克风），但**用手机录样本做验证会严重低估**。
4. 能用的是 SenseVoice：同一条"高频被砍"的录音整条识别 4/4 全对。

### 10.6 仍待确认

- SenseVoice 整条 4/4 vs 切段 3/4，说明"少切、多攒"能进一步提升。
- 「小智」两音节单独说的检出率还没测（本次录音里没有独立说「小智」的段）。
