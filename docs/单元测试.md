# 自研代码的单元测试

> 84 个用例，零依赖，`make ut` 一条命令跑完。
> PC 和板子上跑的是**同一份**用例 —— 板子的字节序、int 宽度、浮点行为都可能和 PC 不同。

---

## 1 为什么这个项目需要 UT

不是因为"应该有"。这个项目有三类代码，出错后的表现形式都是"看不出来"：

| 代码 | 出错后看到的现象 | 实际原因 |
|---|---|---|
| `sip_md5.c` | 服务器回 401/403，"账号密码明明对" | 摘要算错，没人会先怀疑它 |
| `g711.c` | 声音"有点闷"、偶发咔哒 | 查表差一个量化级 |
| `sdp.c` | 手机点呼叫就挂 / 能听到声音看不到画面 | m-line 少一条、pt 没回显 |
| `h264_depack.c` | 画面花屏、绿块 | FU-A 分片少拼一个字节 |
| `wav.c` | 录音能播但音调不对 | 头里 rate/ch/bits 写错 |
| `oem.c` | 屏幕上是蓝色的，客户要的是墨绿 | ini key 拼错一个字母，静默用默认值 |

这六类问题有共同点：**编译通过、运行不崩、日志不报错**。
它们只在"对端"或"客户"那里暴露，而那时候设备已经装在墙上了。

## 2 框架设计

一个 `.h` + 一个 `.c`，没有第三方依赖。取舍：

**① 为什么不用 Unity / CMocka**
目标机（RK3308）上要能跑同一套用例。凡是要 cmake 拉包、要额外运行库的，
交叉编译时都是一堆新问题。这里的框架只有一个头文件和一个源文件。

**② 一个用例失败不终止进程**
C 里最烦的是"第一处失败就 abort，后面 20 个用例根本不知道有没有问题"。
框架记录失败后继续跑，最后汇总。同一用例最多打印 10 条失败 —— 循环里断言失败
会刷几百行，把真正有用的第一条挤没影。

**③ 接 SIGSEGV**
解析器类用例很容易踩野指针。默认行为是整个测试进程死掉，后面的用例全白写。
框架用 `signal + longjmp` 把崩掉的用例标成 CRASH 然后接着跑下一个。

**④ 用 `__attribute__((constructor))` 自动注册**
不用维护一张用例表。漏注册是最常见的"测试写了但没跑"，自动注册从根上避免。

```c
UT_TEST(sdp, echoes_offered_video_pt)
{
    sdp_local_t L = { "1.2.3.4", 5000, 5002, 102, NULL };
    char buf[1024];
    UT_ASSERT(sdp_build(&L, buf, sizeof(buf)) > 0);
    UT_ASSERT(strstr(buf, "a=rtpmap:102 H264/90000") != NULL);
}
```

新增一个 `ut_xxx.c` 就自动被 GLOB 收进构建（`CONFIGURE_DEPENDS` 让新增文件自动触发重配）。

## 3 覆盖清单

| 模块 | 用例 | 重点 |
|---|---:|---|
| `g711.c` | 14 | **双射性**（256 码字→256 个唯一电平）、符号对称、幂等、满幅正弦 SNR ≥ 35dB |
| `sip_md5.c` | 5 | RFC 1321 七条标准向量、**padding 边界**（55/56/63/64/119/120）、含 NUL 的二进制 |
| `sdp.c` | 14 | m-line 条数与顺序、port=0 拒绝、**pt 回显**、rtpmap 权威性、往返一致性 |
| `h264_depack.c` | 12 | FU-A 三分片逐字节重组、丢首片、**序列断裂回退**、STAP-A 拆分、超长拒收 |
| `wav.c` | 9 | data 长度写 0 / 写 0xFFFFFFFF、奇数块填充、fmt 带 cbSize、8bit/双声道字段 |
| `oem.c` | 8 | accessor 与 profile 一致、切 profile、未知 profile 不改状态、布局非负 |
| `yuv2rgb.c` | 22 | 等比适配 7 种比例×4 种框、**标准三原色/黑白**、越界夹取、最近邻采样位置、linesize、U/V 半分辨率偏移、越界写 |
| **合计** | **84** | |

`yuv2rgb` 那 22 条是给"视频上屏"兜底的：上屏这一路的故障（偏色、斜切、只画半边）
在小屏上都像"信号不好"，只能靠逐像素比。用例里的期望值刻意用 **BT.601 标准色**
（纯黑 Y=16 / 纯白 Y=235 / 三原色）而不是自己算的值 —— 系数抄错时，
自算期望值会跟着一起错，测不出来。

`app_sip.c`（状态机、Digest 拼装）和 `app_audio.c`（SDL 设备）还没有 UT ——
前者依赖 socket 和 oSIP 全局状态，后者依赖声卡。这两块用端到端测试覆盖
（`make duo` / `make duo-video` / `make duo-disp`），属于"集成测试"而非单元测试。

## 4 怎么跑

```bash
make ut                 # 全部
bash scripts/dev.sh ut g711      # 只跑 suite 名含 g711 的
bash scripts/dev.sh ut -v        # 打印每个用例耗时
```

输出长这样：

```
  [g711]
    ✓ alaw_codes_map_to_distinct_levels
    ✓ alaw_is_sign_symmetric
    ...
────────────────────────────────────────────────────────
总计 84 用例    通过 84    失败 0    崩溃 0
✅ 全部通过
```

退出码：0 全过，1 有失败/崩溃，2 没有用例匹配。**可以直接挂进 CI**。

## 5 板子上跑

```bash
cmake -S tests -B build-ut-arm -DCMAKE_C_COMPILER=arm-linux-gnueabihf-gcc
cmake --build build-ut-arm
scp build-ut-arm/ut root@board:/tmp/ && ssh root@board /tmp/ut
```

这是"UT 独立成工程"最重要的理由：主工程的 CMakeLists 里有
`find_package(SDL2 REQUIRED)`，交叉编译时直接把 configure 挡住 ——
但"UT 能在目标机上跑"恰恰是最有价值的部分。

`g711.c` 的 SNR 用例会用到 `log10`，交叉编译时记得 `-lm`（CMakeLists 里已处理）。

## 6 UT 抓到的真 bug（这是它存在的证明）

### 6.1 `strstr` 找 rtpmap 会跨行 → 视频 pt 拿错

```c
/* 真实 offer：m=video 5006 RTP/AVP 96 102
             a=rtpmap:96 VP8/90000
             a=rtpmap:102 H264/90000        */
while ((rm = strstr(rm, "a=rtpmap:")) != NULL) {
    if (strstr(rm, "H264/90000")) { ... }    /* ← 搜到字符串结尾！ */
}
```

检查 `a=rtpmap:96 VP8/90000` 这一行时，`strstr` 会一路搜到下一行的 `H264/90000`，
于是把 VP8 的 96 当成 H.264 的 pt。后果是所有视频包被 pt 校验丢弃 ——
**但端到端测试发现不了**，因为用 ffmpeg 推流时 pt 恰好是 96，撞对了。

修法：把搜索限制在当前行内（到 `\r\n` 为止）。

### 6.2 `oem_select` 里的死代码

```c
memset(s_text_overridden, 0, sizeof(s_text_overridden));   /* 先清零 */
for (int i = 0; i < OEM_TXT_COUNT; i++) {
    if (s_text_overridden[i]) s_cur.text[i] = s_text_buf[i];   /* ← 永远不成立 */
}
```

清零之后才检查标志。功能上没错（后面的 `apply_ini()` 会把 ini 覆盖重新挂上），
但这个循环是纯死代码，留着只会让后来的人以为流程有玄机。清理掉，注释说明原因。

### 6.3 我自己写错的测试（也是收获）

第一版 `ut_g711.c` 断言"A-law 码字单调递增"，跑挂了。查证后发现：
**A-law 的码字本来就不单调**（`0x80→5504, 0x81→5248, 0x82→6016`）——
XOR 0x55 就是为了让相邻码字对应幅度接近的值，这样误翻转 1 位时误差最小。
是我的假设错了，实现是对的。

改成真正恒成立的判据：**双射性**（256 个码字 → 256 个互不相同的电平）和**符号对称性**。
前者比单调性更强，却不依赖任何顺序假设。

> 这件事本身说明了一件重要的事：写测试时会不自觉地把"我以为的规格"当成规格。
> 测试跑红的第一步不是改代码，是去查标准。

## 7 写用例的三条约定

1. **断言关系，不断言数据。** 比如不断言"主色是 0x1B5E20"（客户随时会改配色，
   改了测试就红 = 假失败），而是断言"accessor 与 profile 一致""切 profile 会变"。
2. **一个用例只验一件事。** 失败信息要能直接定位。`ut_xxx.c:104 期望 nal_len == 301，实际 298`
   比"重组测试失败"有用一百倍。
3. **失败后 `return`，别继续跑。** 数组已经越界了还往下走，只会把 CRASH 掩盖成
   "断言失败"，反而更难查。
