# 丢包恢复：策略、实现与验收

> 目标：**丢包之后宁可黑一下，也不给人看两秒垃圾。**门口机上的画面是用来认人的，
> 糊成一片的"在动"比冻结的"看得清"更糟。
>
> 验收命令：`make loss`（约 70 秒，全自动，需要 Python 和 ffmpeg）

---

## 1 为什么丢了几个包就必须整帧丢掉

H.264 的 P 帧只编码"和参考帧的差异"，而参考帧又参考上一帧 —— 一条链。

```
I ──► P ──► P ──► P ──► P ...        （I 帧重置参考链，GOP 通常 2 秒一个）
      ▲
   这里丢了一个包
```

链上任何一帧缺数据，后面所有 P 帧都建立在错误的基准上。表现不是"缺一块"，
而是**从丢包点开始持续花屏，直到下一个 IDR**。GOP=60 @30fps 就是 2 秒烂画面。

所以正确的做法不是"尽量把残缺的帧解出来"，而是三步：

1. **停手** —— 丢包之后的帧一帧都不喂解码器；
2. **要关键帧** —— 发 RTCP PLI，请对端立刻补一个 I 帧（不然只能干等下一个）；
3. **见到 IDR 再恢复** —— 先 `vdec_flush()` 甩掉错误状态的参考帧，再从 I 帧重来。

等待期间画面**停在最后一帧好帧上**（冻结），不是黑屏也不是花屏。

## 2 丢包信号从哪来：三个都要接

| 信号 | 出处 | 能发现什么 |
|---|---|---|
| RTP 序号断档 | `h264_depack` 的 `gap` | 整包丢失（含中间片丢失：**时间戳不变，靠 ts 发现不了**） |
| 整帧被判数据不全 | `h264_depack` 的 `au_dropped` | FU-A 断片、STAP-A 长度字段坏了 |
| 解码器报错 | `vdec_get()` 返回负数 | 码流内部损坏（解包看不出来的那种） |

只接第一个是不够的：FU-A 序列断裂时序号可能连续（丢了整段分片但序号跳变恰好被补上），
而它们都算"这帧废了"。三个信号统一汇到 `on_loss_detected()` 一个入口。

`gap` 的判据必须写成 `seq != (uint16_t)(last + 1)`：16 位序号回 21 分钟就回绕一次
（50pps），而门口机是 7×24 开着的。误判的后果是**每隔 21 分钟黑一下**，
这种"定时发作"的问题最难查。

## 3 状态机（`src/media/resync.c`）

```
                 ┌──────────────── 丢包 ────────────────┐
                 │                                      ▼
   FEED ─────────┴─────────────────────────────► WAITING
    ▲                                              │  │
    │  AU 带 IDR（RESUME）                          │  │ 每 500ms 重发 PLI
    └──────────────────────────────────────────────┘  │
                                                      │ 超过 giveup（默认 3s）
                                                      ▼
                                                   GIVEUP（喂帧，画面花但能动）
```

三个参数，都有依据：

| 参数 | 默认 | 依据 |
|---|---|---|
| PLI 重发间隔 | 500 ms | 一个 RTT 内没反应就重发；对端每收一次 PLI 要编一个 I 帧（5~10 倍大小），不能刷 |
| 放弃超时 | 3000 ms | 常见 GOP 2 秒，留一倍余量。真等到 3 秒还没 IDR，说明对端不响应 PLI 且 GOP 很长 |
| 放弃后行为 | 喂帧 | 花的画面能动 > 长时间黑屏。3 秒黑屏对"谁在门口"这个用途是不可接受的 |

**恢复耗时从第一次丢包算起**，等待中再丢包不清零。否则连续丢包会把"等了多久"
一直重置，指标永远好看，而用户实际看到的是长时间卡住 —— 指标骗人的典型方式。
（UT 里有一条专门钉这个：`recover_time_counts_from_first_loss`）

模块不读时钟，`now_ms` 全部由调用方传 —— 测试才能精确推进 1ms 或 10 秒。

## 4 RTCP PLI：加速器，不是通路

`rtcp.c` 只做一件事：拼一个 12 字节的 PLI 包（`RFC 4585 §6.3.1`）。

```
V=2 P=0 FMT=1  PT=206  length=2
sender SSRC | media SSRC
```

两个工程决定：

- **端口用 RTP 端口 +1**（RFC 3550 §11）。对端若用 `a=rtcp:` 指定了别的端口，
  这一版没解析该属性 —— 收到 PLI 不响应也不影响解码，只是恢复慢。
  真联调时如果对端不响应，第一件事就是抓包看 PLI 发到哪去了。
- **发送失败只计数不报错**。RTCP 挂了不该让通话挂：它是加速器，不是通路。

## 5 怎么验：注入 + 指纹，不靠"看着还行"

### 5.1 可控故障注入

等"真实网络抽风"是验不了的 —— 你不知道它什么时候丢、丢在哪、丢完多久能恢复。
`scripts/udp_loss.py` 坐在 ffmpeg 和室内机中间，按**包序号**丢指定段：

```
ffmpeg ──► udp/16064（代理，丢 60:6 和 690:8）──► udp/6064 室内机
```

选丢包位置的纪律：**丢在 GOP 中段，离前后两个 IDR 都远**（见 §7 第一个坑）。

### 5.2 为什么改用 CRC 指纹而不是逐帧对齐比像素

`make duo-video` 用的是"逐帧对齐比像素"，但那套在这里**不成立**：
恢复会故意跳帧，落盘文件的第 N 帧早就不对应参考文件的第 N 帧，按位置比会
从丢包点开始整体错位 —— 满屏差异，其实一帧都没错。

要验的问题也变了：

> ~~第 N 帧对不对~~ → **写出去的每一帧，是不是都完好**

所以用内容指纹（CRC-32）：
1. 参考 YUV 逐帧算 CRC，得到"合法指纹集合"；
2. 室内机每解出一帧就把 CRC 写进 sidecar 日志；
3. 每一帧的 CRC 必须能在集合里命中。

单向性保证不会假绿：**完好帧的 CRC 一定在集合里，被污染的解码结果一定不在**。

### 5.3 一正一反才算证明

`make loss` 跑两遍：

| 轮次 | 配置 | 期望 | 实测 |
|---|---|---|---|
| 对照 | `SIP_VIDEO_RESYNC=0` | **脏帧 > 0** | 77 脏帧 |
| 正式 | 默认（恢复开启） | **脏帧 = 0**，且有跳帧 | 145 帧全干净，跳 2 段 |

只跑正式那遍，万一注入器没生效、一个包都没丢，结果也是"全对"—— 那种全绿什么也
证明不了。对照组就是给结论上保险的。

## 6 实测（`make loss`，8 秒 640×480，注入 2 段共 14 包）

```
注入器: received=1199 forwarded=1185 dropped=14

──── 关闭恢复（对照）────
写入 222 帧：干净 145，脏 77
参考帧号 0 → 239，中途跳过 2 段
  ✅ 关掉恢复后出现 77 个脏帧 —— 这就是开恢复要消除的东西

──── 开启恢复 ────
写入 145 帧：干净 145，脏 0
参考帧号 0 → 239，中途跳过 2 段
  最大一次跳帧：跳过 50 帧（参考帧 9 → 60）
丢包事件 2 次，成功恢复 2 次，跳过 88 帧，最坏等待 1516 ms，放弃 0 次，PLI 6 次
  第 1 次恢复：跳过 44 帧，耗时 1516 ms
  第 2 次恢复：跳过 44 帧，耗时 1454 ms
  ✅ 写出的每一帧都完好（0 个脏帧）
  ✅ 确实丢了 2 次包（注入生效，不是假绿）
  ✅ 中途跳过 2 段帧（说明等 IDR 期间确实停了解码）
  ✅ 帧号严格递增（没有拼错顺序）
  ✅ 2 次全部等到 IDR 恢复
```

`145 + 77 = 222`：对照组把脏帧也写出去，正式组一帧都不写，所以总帧数少 77。
**恢复的代价就是这 77 帧对应的 1.5 秒画面**（冻结，不是花屏）。

## 7 踩的坑

### 7.1 测试把恢复用的 IDR 打掉了

第一版注入位置写成 `60:6 300:8`。丢包在 frame 13，下一个 IDR 在 frame 60 ——
本该 1.6 秒恢复，实际却"超时放弃、喂了 15 帧脏数据"。

查下去：**300 号包恰好落在 frame 60 那个 IDR 上**。唯一的恢复希望被自己打掉了，
下一个 IDR 要等 3.5 秒，而放弃超时是 3 秒 —— 差 0.5 秒，于是走超时分支。

看起来像"恢复策略失效"，其实是测试选错了位置。这也是**为什么超时分支必须存在**：
真实链路上"请求的 I 帧也丢了"是常态，不能假设一次 PLI 就一定有响应。

### 7.2 注入器一收包就崩

`g_rx += 1` 在函数里赋值 → Python 把它当局部变量 → `UnboundLocalError`。
现象很有迷惑性：代理打印了 `ready`、ffmpeg 正常推流、接收端一个包没有 ——
看起来像网络不通或端口配错。修法是 `global g_rx, g_fwd, g_dropped`。

### 7.3 客户端 `SIP_VIDEO_SINK=drop` 导致 offer 里没有视频

视频 m-line 是按**接收能力**生成的：`sink=drop` 等于"我不收视频"，于是 offer 里
根本没有 `m=video`，室内机拿到的 `remote_v=0`，视频端口不建立。

日志里就一行 `[rtp] video: 未建立（local_v=6064 remote_v=0）`，
而根因在一个和丢包毫无关系的地方。测试脚本里客户端必须 `SIP_VIDEO_SINK=file`。

### 7.4 `last_skipped` 从来没被赋值

日志打出 `resync done: skipped=0 waited=1516ms` —— 1.5 秒里不可能一帧没跳。
`resync_gate` 只加了累计的 `skipped`，忘了本轮的 `last_skipped`。
补了赋值，并加了一条 UT 钉住（`last_skipped_resets_per_round`）。

> 这类"统计数字不对"的 bug 不会让功能失效，但会让人**误判功能失效** ——
> 三条日志里两条对不上，第一反应一定是"恢复逻辑坏了"，然后去查错的地方。

## 8 未做

| 项 | 现状 | 影响 |
|---|---|---|
| RTCP Receiver Report / 丢包率统计 | 没做 | 无法量化链路质量，只能看恢复次数 |
| NACK（选择性重传） | 没做 | 丢一两个包也得等 IDR；局域网场景其实重传更划算 |
| 解析 `a=rtcp:` 属性 | 没做 | 对端用非 +1 端口时 PLI 发不到，退化成"等下一个 IDR" |
| FIR（Full Intra Request） | 只发 PLI | 个别老设备只认 FIR |
| 上屏侧的"冻结画面"标识 | 没做 | 用户不知道画面是冻住的（应叠加"信号恢复中"角标） |

优先级建议：**NACK > RR 统计 > `a=rtcp` > FIR**。
局域网内的丢包多是单包丢失，NACK 重传一下就好，比等 2 秒 IDR 体验好一个量级。
