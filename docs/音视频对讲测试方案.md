# 音视频对讲测试方案：手机当对端，点对点直连

> 适用：带屏可视对讲室内机（RK3308）开发阶段。
> 目标：**不架 SIP 服务器、不做注册、不写平台**，只让两台设备直连对讲，
> 把音视频功能验证到位。手机扮演门外机（音视频源），室内机扮演接收方。

---

## 0. 一句话方案

**手机装 Linphone，和板子连同一个 Wi-Fi，拨号盘直接输 `sip:1001@<板子IP>:5062`。**

不需要 miniSIPServer，不需要 Asterisk，不需要账号密码。SIP 的"点对点直呼"
（direct IP call）本身就是协议允许的合法形态，而真实的门口机 ↔ 室内机局域网部署
也常常就是这么直连的 —— 换句话说，这个测试环境**比走服务器更接近最终产品形态**。

分三段推进，每段都有独立验收点，不要跳：

| 阶段 | 目标 | 要不要写代码 | 预计 |
|---|---|---|---|
| **P0** | 双向语音通 | 不要（已具备） | 半天 |
| **P1** | 视频"收得到、解得出" | 不要（用外部工具 ffplay 验流） | 半天 ~ 1 天 |
| **P2** | 视频解到屏上 | 要（约 400~600 行） | 2~3 天 |

## 1. 为什么选 Linphone（选型对比）

| 方案 | 视频 | 点对点直呼 | 成本 | 结论 |
|---|---|---|---|---|
| **Linphone**（Android/iOS） | ✅ H.264 走 MediaCodec 硬编 | ✅ 无需账号 | 免费开源 | **选它** |
| Zoiper | ❌ 视频要付费版 | ✅ | 收费 | 放弃 |
| Grandstream GS Wave | ✅ | ✅ | 免费 | 备选，配置项少、黑盒难查 |
| MicroSIP（PC） | ❌ 只有语音 | ✅ | 免费 | 语音回归主力，留给 PC |
| 我们自己编的 `sip_echo` | ❌ | ✅ | — | 无人值守回归，留给 CI |
| WebRTC 网页对端 | ✅ | — | — | **不通**，WebRTC 和 SIP 是两套信令，中间必须加 Janus/Kamailio 网关，太重 |

> Linphone 的 H.264 是**手机硬件编码器**（Android MediaCodec / iOS VideoToolbox），
> 这带来一个额外好处：你不必关心手机性能，它发的流一定符合标准，出问题必然是
> 板子侧的问题 —— 排错范围直接减半。

## 2. 网络拓扑：三种，按阶段选

### A. PC 开热点（**开发期首选**）

```
   手机 ──Wi-Fi──┐
                 ├── PC（Windows 移动热点 + Wireshark + 客户端）
   板子 ──Wi-Fi──┘
```

**为什么开发期用这个**：所有流量都从 PC 的虚拟网卡过，**Wireshark 能抓到完整的
SIP + RTP**。调视频阶段没有抓包能力就是在盲修。

做法：Windows 设置 → 网络和 Internet → 移动热点 → 打开，记下网段（通常 `192.168.137.x`，PC 自己 `.1`）。

### B. 手机开热点（**现场演示首选**）

```
   板子 ──Wi-Fi──> 手机（既是 AP，又是对端）
```

板子连上手机热点后，手机自己的地址是**网关地址**（`192.168.43.1` / `192.168.137.1`，
各厂商不同，在手机"热点设置"里能看到），板子就往这个地址打。

> 少数机型开了 AP 隔离，客户端访问不到网关上的服务。若"能 ping 通网关但 SIP 不通"，
> 换路由器验证，别怀疑代码。

### C. 家用/公司路由器（最稳，适合长时间跑稳定性）

两边都连同一个 SSID。注意 **2.4G 在人多时抖得厉害**，视频 1 Mbps 都会花屏；优先 5G 或网线。

**三条铁律**（违反任何一条都是"现象诡异但代码无辜"）：

1. **必须同网段**（前三位一致），跨网段直呼必然不通；
2. **AP 隔离必须关**（很多商用 Wi-Fi 默认开，客户端之间不能互访）；
3. **板子的 IP 要固定**（静态 IP 或 DHCP 保留），否则每次重启都要改手机里的拨号地址。

## 3. 手机端配置清单（踩坑最密集的地方，逐项照做）

装 **Linphone**（Google Play / App Store，官方开源版）。

### 3.1 建立直呼（**不需要服务器注册**）

先按 §3.5 建一个"假账号"（Username 随便、Domain 填板子 IP、**Registration expire = 0**），
然后用拨号盘输地址：

```
sip:1001@192.168.137.50:5062
```

`1001` 是任意用户名（我们客户端不看这个字段），`192.168.137.50:5062` 是板子的 IP 和
`SIP_LOCAL_PORT`。

### 3.2 必改的 7 项（**每一项不改都有一个对应的故障现象**）

| # | 位置 | 设置 | 不改会怎样 |
|---|---|---|---|
| 1 | 设置 → 音频 | **只勾 PCMA、PCMU**，取消 Opus / Speex / G722 / GSM | Linphone 默认 Opus 排第一，我们只支持 G.711 → **信令全通、两边全静音**（最常见的一个坑） |
| 2 | 设置 → 音频 | 取消 **Adaptive rate control**（自适应码率） | 手机侧看到一点点丢包就狂降码率/降采样，声音断续，你还以为是板子卡 |
| 3 | 设置 → 视频 | 勾 **Initiate video calls** + **Accept incoming video requests** | 手机不发视频，P1/P2 永远测不起来 |
| 4 | 设置 → 视频 | 编码**只勾 H264**，取消 VP8 / AV1 / H265 | 手机默认偏好 AV1/H265，我们只解 H.264 → 协商出 AV1，板子无从下手 |
| 5 | 设置 → 视频 | 分辨率 `640×480`，帧率 `15`，带宽限 `1000 kbps` | 默认可能是 720p@30/2Mbps，RK3308 软解直接丢帧，你会误判成"解码器写错了" |
| 6 | 设置 → 网络 | 取消 **Use random port**，SIP 端口填 `5062` | 端口随机，板子回的应答到不了；且 **Android 部分机型占用了 5060** |
| 7 | 设置 → 高级 → 加密 | 媒体加密 = **None** | 默认可能协商 SRTP，板子收到的包**解出来是噪声**；抓包能看到包、但内容全错，极难判断 |

**额外一项（Android 必做）**：设置 → 应用 → Linphone → 电池 → **无限制 / 关闭省电优化**。
否则锁屏后 30 秒内 UDP socket 被回收，通话直接断，日志上什么都没有。

### 3.3 排错第一步：手机 ↔ 手机

**在动板子之前，先用两台手机互打一次**（第二台手机装同款 Linphone，拨
`sip:<第一台IP>:5062`）。

两台手机能通 = 网络、AP 隔离、App 配置全部正确，之后所有问题都在我们代码里。
这一步能省掉一半以上的排查时间。

### 3.4 鸿蒙（HarmonyOS）手机上装 APK：能装≠能跑

先分清两个鸿蒙：

| 系统 | 版本 | 能不能跑 Linphone APK |
|---|---|---|
| HarmonyOS 4.x 及更早 | 过渡兼容版，**带 AOSP 兼容层** | **能**，APK 直接装，和安卓机一样 |
| **HarmonyOS NEXT（5.0 / 6.x，即"纯血鸿蒙"）** | 已彻底移除 AOSP，只认 `.hap` | **系统本身不能**。只能靠第三方容器（卓易通、出境易等）跑 APK |

你说"装的是 apk"，说明要么是 4.x，要么在 NEXT 上走的是容器。这两条路要防的坑不一样：

**A. HarmonyOS 4.x（原生兼容层）** —— 基本等同于安卓机，只多一件事：
设置 → 应用 → Linphone → 权限里把**麦克风、相机、本地网络**都打开。
鸿蒙对"本地网络访问"管得比安卓严，不给的话表现是**能注册能呼出，但对方听不到你**。

**B. HarmonyOS NEXT + 容器（卓易通类）** —— 这是**测试可用、不能当验收基准**的环境：

| 风险 | 表现 | 处理 |
|---|---|---|
| 权限是"两层"的 | 应用里给了权限，系统没给容器 | 系统设置 → 应用 → 容器 → 权限，单独再开麦克风/相机 |
| 硬件编解码大概率降级 | H.264 硬编不可用 → 软编，CPU 高、发热、可能只有 5~8fps | 接受它，或直接换设备。**别用它的帧率去判断板子性能** |
| 容器进程易被回收 | 锁屏 30 秒后 socket 断，日志无任何异常 | 保持前台、关省电优化、插电测试 |
| 音频通路延迟偏大 | 声音"有但闷"、回声更明显 | 戴耳机，别用免提 |
| UDP 出站可能被代理 | 抓包看得到 SIP，但没有 RTP | 关掉系统级 VPN / 私有 DNS 再试 |

**结论：鸿蒙 NEXT 上如果非要跑，只用来验 P0（能不能通）和 P1（有没有画面），
不要用它的数据做性能结论。** 真要做视频验收，借一台安卓机/平板更省时间。

### 3.5 Linphone 到底要不要注册？

**不需要服务器，但需要一个"身份"。** 两件事分开：

- **注册（REGISTER）** 是"告诉服务器我在线"，没有服务器就没有这一步；
- **身份（SIP 地址）** 是"我叫什么"，呼出时必须带 `From`，所以必须有。

Linphone 的做法是建一个**假账号**：

| 字段 | 填什么 |
|---|---|
| Username | `1002`（随便，板子不看） |
| Password | 随便（或空） |
| Domain / SIP domain | **板子的 IP**，如 `192.168.137.50` |
| Proxy / Server address | **留空**（留不空就填板子 IP） |
| Registration expire | **`0`**（= 关闭注册；找不到这一项就填 0 秒） |

然后拨号盘输入 `sip:1001@192.168.137.50:5062`。

**如果 Linphone 界面一直显示"注册失败"，是正常的** —— 那个 REGISTER 被发到了板子上，
而板子不是 registrar，会回 `405 Method Not Allowed`（本版已实现，之前是**静默丢弃**，
后果是手机按 Timer E/G 每秒重传一次，看着像"板子不响应"）。405 不影响呼出。

> 这一条是实测出来的坑：UAS 对不支持的方法**必须**回终态响应（RFC 3261 §8.2.1），
> 不回不是"省事"，是把对端变成重传风暴。

### 3.6 手机这条路彻底走不通时的兜底（**不装任何 SIP 客户端**）

只要能证明"板子收得到 RTP、解得开"，P1 就不需要手机：

```bash
# PC 上，把一段 H.264 循环推给板子的视频端口（不需要 SIP、不需要 Linphone）
ffmpeg -re -stream_loop -1 -i test.h264 -c copy \
       -f rtp rtp://192.168.137.50:5004 -sdp_file video.sdp

# 板子侧照常 ffplay 拉流验收
ffplay -protocol_whitelist file,udp,rtp video.sdp
```

这条路的价值：把"信令协商"和"媒体解码"**彻底解耦**。手机端配不出来时，
先用它把 P1 的板子侧验完，回头再单独解决手机配置。

## 4. 板端/PC 端启动命令

```bash
# 板子上（或 PC 上先验证）
SIP_NO_REGISTER=1 \
SIP_LOCAL_PORT=5062 \
SIP_LOCAL_IP=192.168.137.50 \
SIP_AUTOANSWER=1 \
./bin/main
```

| 变量 | 作用 | 备注 |
|---|---|---|
| `SIP_NO_REGISTER=1` | 不注册，直接在线 | 直呼模式必须 |
| `SIP_LOCAL_PORT=5062` | SIP 监听端口 | 和手机拨号地址里的端口一致 |
| `SIP_LOCAL_IP=<IP>` | **强制指定 SDP 里通告的地址** | **板子多网卡（eth0+wlan0）必填**，否则可能通告成另一张网卡的 IP，手机拿到的地址根本到不了 |
| `SIP_AUTOANSWER=1` | 来电自动接听 200 | 测视频时不用每次点屏幕 |
| `SIP_NO_AUDIO=1` | 不开声卡（纯信令） | 只在排查"是不是声卡初始化卡住了"时用 |
| `SIP_DEBUG=1` | 打印 ACK / SDP 原文 | 排查协商问题 |

反向（板子打给手机）：

```bash
SIP_NO_REGISTER=1 SIP_LOCAL_PORT=5062 SIP_LOCAL_IP=192.168.137.50 \
  SIP_AUTOCALL=sip:1001@192.168.137.66:5062 SIP_AUTOHANGUP=30 ./bin/main
```

> ⚠️ **本轮已修复的一个隐藏坑**：`SIP_NO_REGISTER=1` 且没填 `SIP_SERVER` 时，
> 原来探测本机 IP 的函数没有目标地址，`s_local_ip` 会停在 `127.0.0.1`，
> 于是 SDP 的 `c=IN IP4 127.0.0.1` 发给手机 → 手机把音频**往自己身上发**。
> 现象是"信令全对、双方静音"。现在无服务器时会朝 `8.8.8.8:53` 探测默认路由选卡，
> 且支持 `SIP_LOCAL_IP` 人工覆盖。

## 5. P0 —— 双向语音（今天就能做）

### 5.1 验收标准

| 项 | 指标 | 怎么看 |
|---|---|---|
| 信令 | `INVITE → 100/180/200 → ACK` 无重传 | 双方日志 |
| 媒体 | 双向 50 pps / 64 kbps | 挂断时打 `[rtp] stats rx=.. tx=.. pps=..` |
| 听觉 | 双向可懂、无断续 | 手机插耳机 |
| 无泄漏 | 挂断后 `rx/tx` 停增 | 日志 |

### 5.2 故障对照表

| 现象 | 最可能原因 | 查法 |
|---|---|---|
| 手机点了就叫、立刻断 | SDP answer 缺 `m=video` 行（本轮已修） | 开 `SIP_DEBUG=1` 看 answer 原文 |
| 信令全通、双方静音 | ① 手机编 Opus ② `c=` 是 `127.0.0.1` ③ 媒体加密协商成 SRTP | Wireshark 看 RTP 的 PT 值：111=Opus（错），8=PCMA（对） |
| 只有一边有声 | 对称 RTP 没跟上（NAT/ICE） | 看日志有没有 `[rtp] peer learned` |
| 声音断续 | 手机自适应码率开着 / Wi-Fi 2.4G 拥塞 | 关自适应码率、换 5G |
| **啸叫刺耳** | 手机和板子同房间，喇叭↔麦克正反馈 | **手机插耳机**（工程侧 AEC 属 M6） |
| 通话 3 秒后自己断 | `SIP_AUTOHANGUP` 还留着 | 去掉该变量 |

## 6. P1 —— 视频"收得到、解得出"（**这一阶段不写产品代码**）

这是整个方案里最省时间的一步：**先证明视频流本身是好的，再谈怎么解、怎么显示。**
用 PC 端的 `ffplay` 直接把 RTP 拉出来播，绕开我们自己的一切代码。

### 6.1 改一行 SDP，让手机开始发视频

`src/app/app_sip.c` 的 `build_sdp()` 末尾原本是拒绝视频：

```c
"m=video 0 RTP/AVP 0\r\n"
"a=inactive\r\n"
```

P1 临时改成（`pt` 用 offer 里给 H.264 的那个号，见 §7.1）：

```c
"m=video %u RTP/AVP 102\r\n"
"a=rtpmap:102 H.264/90000\r\n"
"a=recvonly\r\n"
```

`a=recvonly` 很重要：室内机**只看不发**，省掉整个 H.264 编码器 ——
RK3308 编 720p 是跑不动的，而产品形态本来也只需要看门口机。

### 6.2 用 ffplay 验证（**外部验收工具，不是产品组件**）

> **ffplay 是什么**：FFmpeg 项目自带的**示例播放器程序**，属于应用层，PC 上要单独安装。
> 产品链接的是它下面那一层的 **libavcodec 库**（类似 `sqlite3` 命令行之于 SQLite 库、
> `curl.exe` 之于 libcurl）。这里只是借它当"可信第三方"证明手机发出来的流是好的，
> **产品二进制里没有 ffplay 的任何代码** —— 交叉编译时 `--disable-programs` 根本不编它。
> C/C++ 里怎么写解码，见 [`音视频编解码实现方案.md`](音视频编解码实现方案.md)。

在 PC 上建一个 sdp 文件 `video.sdp`（端口填板子的视频 RTP 端口）：

```
v=0
o=- 0 0 IN IP4 127.0.0.1
s=probe
c=IN IP4 127.0.0.1
t=0 0
m=video 6062 RTP/AVP 102
a=rtpmap:102 H.264/90000
a=fmtp:102 packetization-mode=1
```

```bash
ffplay -protocol_whitelist file,udp,rtp -fflags nobuffer -flags low_delay video.sdp
```

**出画面 = 手机编码、SDP 协商、网络、H.264 打包全部正确。**
之后所有工作就只剩"把 ffplay 干的事用 C 重写一遍"。

### 6.3 同时做的两件事

1. **Wireshark 抓包**：过滤 `rtp`，看视频流每秒包数。
   480p@15fps / 1Mbps 大约 **70~150 包/秒**；如果只有几十个包还抖动，是网络问题不是解码问题。
2. **存一份素材**：让手机录一段 H.264 文件（或从抓包导出裸流），存成 `.h264`。
   后续调解码器时用 `ffmpeg -i phone.h264 ...` 反复喂，**不用每次都真机呼叫**，
   调试速度能快 10 倍。

## 7. 视频协商的三个致命细节

### 7.1 payload type 绝对不能写死 96

Linphone（Android）给 H.264 常用 **102**，iOS 常用 **98/99**，每次都可能不同。
必须在 offer 里找到 `a=rtpmap:<pt> H.264/90000`，把那个 `<pt>` **原样回显**。

写死 96 的后果：手机按 102 发、我们按 96 收 —— 包都收到了，`payload` 字段对不上，
解码器喂进去的是错的，表现为**花屏或黑屏**，而且日志完全正常。

### 7.2 `profile-level-id` 要原样带回

offer 里 H.264 常带：

```
a=fmtp:102 packetization-mode=1;profile-level-id=42e01f;level-asymmetry-allowed=1
```

`42e01f` = Constrained Baseline Level 3.1。**把它抄进 answer**。
不回显的话，手机可能按自己的上限发 High Profile 8×8 变换 —— 板子的硬解器
（MPP）不支持，同样表现为花屏。

### 7.3 RTP 解包要处理分片

一个 480p 关键帧约 15~40 KB，而以太网 MTU 只有 1500，**必然分片**：

| 打包模式 | 结构 | 要不要处理 |
|---|---|---|
| 单 NAL（STAP-A 少见于视频） | 一个 NAL 一个包 | 基础 |
| **FU-A**（最常见） | `0x7C` 起始片 / `0x7C` 中间片 / `0x7C` 结束片 + 原 NAL 头 | **必须** |
| STAP-A | 多个小 NAL 打包 | 建议 |

漏了 FU-A 的典型现象：**只出第一帧，然后永远静止**（因为只有 I 帧的第一个分片被当成完整 NAL）。

## 8. P2 —— 解码上屏（要写代码）

### 8.1 管线

```
RTP 收包 → H.264 depacketizer(FU-A/STAP-A) → Annex-B 缓冲
        → 解码（PC: libavcodec 软解 / 板子: Rockchip MPP 硬解）
        → NV12 帧 → RGB565 转换 → lv_image 刷新
```

### 8.2 分两步走，别一起调

**第一步（PC 上）**：用 libavcodec 软解，把解码结果直接塞进 `lv_image`。
此时能验证"上屏路径"对不对（缩放、YUV→RGB 的色彩、撕裂、帧率）。

**第二步（板子上）**：换成 MPP 硬解，接口层抽象成同一个函数：

```c
typedef struct vdec vdec_t;
vdec_t *vdec_open(int w, int h);
int     vdec_feed(vdec_t *d, const uint8_t *nal, size_t len);   /* Annex-B */
int     vdec_get_frame(vdec_t *d, uint8_t **yuv, int *w, int *h); /* 取一帧 NV12 */
void    vdec_close(vdec_t *d);
```

软解和硬解各实现一份，上层（RTP → depacketizer → vdec → lv_image）完全不动。
**这也是面试里能讲的东西**：为"同一个能力两种后端"留接口，跟 OEM 那层是同一个设计思路。

### 8.3 上屏的坑

| 坑 | 现象 | 做法 |
|---|---|---|
| 每帧 `lv_image_set_src` 新建对象 | 内存池爆、掉帧 | 复用同一个 `lv_image_dsc_t`，只改 `data` 指针，再 `lv_obj_invalidate` |
| 在 LVGL 任务里直接解码 | UI 卡死（软解 480p 一帧几十 ms） | **独立线程解码**，只把"最新一帧"交给 UI（丢帧优于积压） |
| YUV→RGB 用浮点 | RK3308 没 FPU 优势，跑满 CPU | 查表或定点，最差也要每 2×2 只算一次色度 |
| 缓冲区没对齐 | 花屏、色块 | NV12 的 stride 要按 16 对齐 |
| 音视频不同步 | 口型对不上 | 视频跟音频时钟走，音频是主时钟（对讲场景 200ms 内可接受） |

### 8.4 P2 验收指标

| 项 | 目标 | 备注 |
|---|---|---|
| 端到端延迟 | ≤ 300 ms | 手机拍秒表 → 板子屏上看，差值即延迟 |
| 帧率 | 480p ≥ 12 fps / 720p ≥ 10 fps | RK3308 软解 720p 会掉，硬解能到 25+ |
| CPU 占用 | ≤ 60%（单核） | `top` 看 |
| 连续 1 小时 | 内存不涨、无花屏 | 看 M5 的池统计 |

## 9. 分层诊断表（出问题先判断"坏在哪一层"）

| 层 | 看什么 | 正常样子 | 坏了说明 |
|---|---|---|---|
| 网络 | `ping <对端>` | 通、延迟 < 5ms | 先解决网络，别往下看 |
| 信令 | 客户端日志 | `INVITE→100/180/200→ACK` 无重传 | SIP 层问题 |

| 媒体 | Wireshark → RTP | 音频 50pps；视频 70~150pps | 网络/发送端问题 |
| 解包 | 打印 NAL 类型 | 有 SPS(7)/PPS(8)/IDR(5) | depacketizer 问题 |
| 解码 | 解码器返回码 + 输出尺寸 | 每帧 w/h 正确 | 解码器问题 |
| 显示 | 屏上画面 | 不花、不撕、不卡 | lv_image / 转换问题 |

## 10. 手机当对端的 5 个固定陷阱

1. **锁屏掉线** —— Android Doze 回收 socket。关电池优化，或测试时保持亮屏。
2. **声音进了听筒** —— Linphone 通话界面有扬声器/听筒切换，默认可能是听筒，听不清别以为没声音。
3. **画面是歪的/倒的** —— 手机竖持时摄像头方向参数不同，Linphone 有 rotation 设置；
   室内机上屏前必须处理，否则竖屏录出来在横屏上就是躺着的。
4. **同房间啸叫** —— 手机插耳机。这不是 bug，是物理规律，AEC 属于 M6。
5. **Android 占用 5060** —— 所以全程统一用 **5062**。
