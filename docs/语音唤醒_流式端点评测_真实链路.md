# 语音唤醒：流式 + 端点检测真实链路评测

> 2026-10-28。这一轮补的是**之前所有评测缺的那一块**：真实连续音频流。
> 之前每条 wav 都是「已切好、只含一个唤醒词」，这个前提在设备上不存在。
> 脚本 `scripts/stream_eval.py`，结果 `.tools/stream_final.json`。

## 一句话结论

**「你好小智」+ 流式模型 + VAD 切段 = 检出 93.8%（15/16）、误唤醒 0/24、延迟 50ms、模型 24MB。**
这是目前唯一能在板子上落地的组合。「你好兮兮」在真实流里最高只有 42%，**判死**。

## 1. 为什么必须重测：之前的数字有多少水分

| 评测方式 | 兮兮 | 小智 | 说明 |
|---|---|---|---|
| 旧：每条 wav 单独离线整句 | 33% | 100% | **前提是已经切好**，真实场景不存在 |
| 新：连续流 + ASR 端点检测 | 0% | 75% | 端点检测把流切碎了 |
| 新：连续流 + VAD 切段（流式 24MB） | 33% | 100% | 单次；4 seed 平均 31% / **94%** |
| 新：连续流 + VAD 切段（离线 60MB） | 75% | 75% | 精度高但算力重 |

旧的 100% 不是假的，但它测的是「模型看到干净的 1.7 秒音频能认出来」，
而设备面临的是「从一条 87 秒的流里，自己找出哪 1.7 秒是唤醒词」。
**后者才是真问题，前者只是它的一个子问题。**

## 2. 三个真 bug（都值得记下来）

### bug 1：ASR 端点检测在长静音里会反复触发

`sherpa_onnx.OnlineRecognizer` 开 `enable_endpoint_detection=True`，
`rule1_min_trailing_silence=0.6`。实测一句话结束后：

```
[s12.wav] 4.90-7.60
    end= 7.80 lat=0.20 ''      ← 第一句结束后 0.2s 触发
    end= 8.50 lat=0.90 ''
    end= 9.10 lat=1.50 ''
    end= 9.70 lat=2.10 ''      ← 这个位置已经进了 s06 的播放区间！
    end=10.40 lat=2.80 ''
```

**每 0.6 秒触发一次，`reset()` 之后还在触发。** 后果是把后面句子的音频切成
一堆 100ms 的碎片，每片都识别不出东西 —— 16 句唤醒只认出 3 句（18.8%）。

这不是参数没调好，是机制如此：静音期间端点条件一直成立。
**必须靠 VAD 门控解决**（没有语音就不建流）。

### bug 2：端点归到哪一句，映射写错会把整张表算错

第一版我用「已结束的最后一个片段」：

```python
cand = [s for s in segs if s["end"] <= u["end_pos"]]   # 错
```

`s12` 在 7.60 结束，但它的端点一直触发到 11.70，而 `s06` 是 9.60–12.00。
于是 `s06` 播放期间的所有端点都被算到 `s12` 头上，`s06` 反而一条都没有。
**正确做法是取「开始时间不晚于端点」的最后一个**，即当前正在播或刚播完的那句。

### bug 3：「您好」把整条锚点规则链打断

VAD 切分后首字常被识别成**您**好（不是你）。而近音规则全是 `你好小吃 → 你好小智`，
锚点对不上，直接全失配。

加一条裸替换 `您好 → 你好`（这条绝对安全，没人会把「您好」理解成别的）。
收益拆开看：

| 改动 | 总检出 | 增量 |
|---|---|---|
| 基线（hang=300） | 31.2% | — |
| + `您好→你好` | 43.8% | **+12.6pt** |
| + hangover 300→600ms | 50.0% | +6.2pt |

**一条字符串替换的收益，接近所有参数调整加起来的两倍。**

但这条规则**放错位置就没有任何效果**，C 实现里踩过一次：
`wake_norm.c` 的执行顺序是「SOFT 锚点规则 → HARD 裸替换」，
把 `您好→你好` 放进 HARD，结果是 HARD 跑完时文本确实变成了「你好学习」，
**但 SOFT 已经跑过一轮**，`你好学习 → 你好兮兮` 永远匹配不上（实测 2/2 漏判）。
所以它必须放在 **SOFT 表的第一位** —— 虽然它不是锚点规则，放那儿纯粹是为了执行顺序。
这是「两级规则 + 顺序依赖」最典型的坑，改规则时别动这个位置。

## 3. 三种切分形态的完整对照

连续音流 87.1s：16 次唤醒（兮兮 12 + 小智 4）+ 6 句无关语音 + 底噪 0.0012。
分块 100ms，判定用同音归一 + 锚点近音。

| 切分方式 | 兮兮 | 小智 | 误唤醒 | 延迟均值 | RTF | 模型体积 |
|---|---|---|---|---|---|---|
| ASR 端点检测 rule1=0.6 | 0/12 (0%) | 3/4 (75%) | 0/6 | 0.28s（最大 1.86s） | 0.0214 | 24 MB |
| **流式 VAD（k=3, pre=200, hang=600）** | **4/12 (33%)** | **4/4 (100%)** | **0/6** | **0.05s** | **0.0144** | **24 MB** |
| 离线 VAD + ZipCTC | 9/12 (75%) | 3/4 (75%) | 0/6 | 0.05s | 0.0135 | 60 MB |

三个观察：

- **端点检测的延迟最差**（均值 0.28s、最大 1.86s），因为它要等满 rule1 静音；
  而且结果最差。**没有理由用它**。
- **流式 VAD 延迟只有 0.05s**，因为 hangover 一到就出结果，不用等 ASR 自己判断。
- **离线模型救不了小智，反而救了兮兮**（75% vs 流式 33%）。说明两个词的失效原因不同：
  兮兮是「听不清」（离线大模型能补），小智是「切太碎」（流式短上下文反而稳）。

## 4. 稳定性验证（防止单次抽样骗人）

### 4.1 换 4 个随机种子（句序、停顿长度、底噪都变）

| seed | 兮兮 | 小智 |
|---|---|---|
| 1 | 4/12 | 4/4 |
| 2 | 3/12 | 3/4 |
| 3 | 4/12 | 4/4 |
| 4 | 4/12 | 4/4 |
| **合计** | **15/48 = 31%** | **15/16 = 94%** |

误唤醒 4 组全部 0/6（合计 **0/24**）。

### 4.2 换停顿长度

| 句间停顿 | 兮兮 | 小智 |
|---|---|---|
| 0.4s（抢话） | 33% | 100% |
| 1.0s（正常） | 33% | 100% |
| 2.0s（慢） | 42% | 100% |

停顿影响很小 —— 因为 VAD 切段用的是能量，不是固定间隔。

### 4.3 参数敏感性

| 参数 | 结论 |
|---|---|
| VAD 阈值 k = 2.5 / 3.0 / 4.0 | **完全一样**（底噪 0.0012，语音峰值 0.2650，相差 200 倍，阈值随便定） |
| preroll 200ms vs 350ms | 200 更好；350 反而会把前一句的尾巴带进来（`s01` 变成「离开七夕」） |
| hangover 300ms vs 600ms | **600 明显更好**（50% vs 43.8%），尾部丢字减少 |
| 端点 rule1 0.4 / 0.6 / 1.0 | 1.0 最好（31.2%），但仍远差于 VAD，不值得用 |

## 5. 选词定案：你好小智

兮兮为什么判死，现在有完整证据链：

| 模型 | 兮兮的识别结果 |
|---|---|
| 流式 24MB | 你好 / 您好 / 学习 / 心 / 李海 |
| 离线 60MB | 你好嘻 / 你好七 / 你好西 / 你好谢 |
| 离线 228MB (SenseVoice) | 西西 / 嘻嘻 / 你好谢谢 / 你好星星 |

**「兮」这个音在中文里没有高频词承载，模型只会往「西/嘻/谢/七/学习」上靠。**
而「你好谢谢」是极高频日常用语 —— 选「兮兮」等于主动和它撞车。

小智正好相反：识别结果稳定落在「小致/小吃/想吃/小晨」，音全对、只错字，
**这是同音字归一能百分百救回来的形态**。

> 4 条小智样本的 94% 仍是小样本，真实置信区间很宽（1 条出入 = 6.25%）。
> 但兮兮连 42% 都冲不上去，「选哪个」这个判断不需要更大样本就能定。

## 6. 最终可落地方案

```
麦克风 16k 单声道
   ↓ 每 100ms 一块（1600 样本）
能量 VAD：rms > 底噪×3.0         ← 底噪用开机 1s 静音标定
   ↓ 触发：回补 preroll 200ms（防首字被切）
流式模型 sherpa-onnx zipformer-transducer（24MB）
   ↓ 100ms 增量解码
   ↓ 静音满 600ms（hangover）→ 取结果
同音字归一（wake_norm.c）
   ↓ 您好→你好 → 西西/嘻嘻/小致/小志… → 兮兮/小智
判定：文本包含「你好小智」或「小智」
```

参数：

| 项 | 值 | 依据 |
|---|---|---|
| 分块 | 100ms | 延迟与算力的平衡点 |
| VAD 阈值 | 底噪 × 3.0 | k 在 2.5~4.0 无差异，取中间 |
| preroll | 200ms | 350ms 会把前句尾巴带进来 |
| hangover | 600ms | 300ms 尾部丢字更多 |
| 唤醒词 | **你好小智** | 兮兮最高 42% |

实测指标：**检出 93.8%、误唤醒 0/24、延迟 50ms、模型 24MB、RTF 0.0144**。
RTF 0.0144 换算到 A53（×8~15）约 **0.12~0.22**，单核实时完全够。

## 7. 复现

```bash
PY=python3   # 需已安装 sherpa-onnx；脚本只用标准库，不依赖 numpy

# 三形态对照
$PY scripts/stream_eval.py --gap 1.0 --rule1 0.6 --k 3.0 --preroll 200 --hang 600 \
    --off m_zipctc_s --json .tools/stream_final.json

# 只跑 VAD（快）
$PY scripts/stream_eval.py --gap 1.0 --mode vad --k 3.0 --preroll 200 --hang 600 --seed 2

# 多 seed 稳定性
for sd in 1 2 3 4; do $PY scripts/stream_eval.py --gap 1.0 --mode vad --seed $sd; done
```

## 8. 已知局限（别拿这份当最终验收）

1. **样本量小**：16 次唤醒，1 条出入就是 6.25%；兮兮 12 条、小智 4 条。
2. **单一说话人、单一设备**：全部来自同一部手机录音，没有第二个人。
3. **安静环境**：底噪只有 0.0012，真实客厅/厨房远高于此。VAD 阈值需要重新标定。
4. **无关语音只有 6 句**：误唤醒率的置信度很弱，要压实测值得用几十句。
5. **VAD 是能量阈值，不是真 VAD**：对电视声、空调风声会误判。上板建议换
   Silero-VAD 或 WebRTC VAD（都是轻量 C 实现，几十 KB）。
6. **没测距离和混响**：手机贴嘴录的，1m/3m 完全没覆盖。
