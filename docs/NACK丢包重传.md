# NACK 丢包重传验证

> 结论先看：**局域网单包丢失从"2 秒冻结/花屏"降到"20ms 内无感恢复"**。
> 实测（8s 推流，注入 2 段共 14 包）：重传 14/14 全部补上、0 脏帧、0 跳帧、
> resync 慢路径全程零惊动（PLI 0 次）。对照组（对端不响应 NACK）自动退回
> 原有 PLI 路径，行为与 `make loss` 完全一致。

---

## 1. 为什么需要 NACK（而不是只有 PLI）

| | PLI（已有） | NACK（本次新增） |
|---|---|---|
| 说什么 | "参考链断了，给我编个 I 帧" | "序号 N 那个包没到，重发一下" |
| 对端代价 | **编一个 IDR**（P 帧的 5~10 倍大小） | 从重传缓冲捞一个包重发 |
| 恢复耗时 | 一个 RTT + 一帧编码时间，且要等 IDR 传完 | 一个 RTT（局域网 ≈ 1~5ms） |
| 适用 | 丢太多、重传救不回来 | **单包/少包丢失（局域网的绝对主流）** |

丢包恢复（resync，见《丢包恢复验证.md》）的策略是"丢一包 → 整帧丢 → 等 IDR"，
实测最坏等 1.5 秒（冻结在最后一帧好帧上）。但局域网里 90% 以上的丢失是
零星单包 —— 为一两个包冻结 1.5 秒，体验不成比例。NACK 把这类丢失的恢复
成本从"一个 GOP"降到"一个 RTT"。

## 2. 关键设计：为什么必须先加"按序交付缓冲"

NACK 重传的包**一定迟到**（比正常序号晚一个 RTT）。而 `h264_depack` 是
"见洞即毒"的按序状态机（FU-A 分片必须按序重组）—— 迟到的包直接塞回去
会被当成**新的**序号断档，把后面好好的帧也毒掉，越补越花。

所以重传要发挥作用，必须有一个"等它一下"的按序交付点：

```
RTP 收包 → rtp_reorder（hold 20ms + NACK 请求）→ h264_depack → resync
              ↑ 加速层：把能救的丢包在下游察觉之前救掉
              ↓ 救不回来的（20ms 没等到）放行成 gap
                 走老路：整帧丢弃 → PLI → 等 IDR（一行未改）
```

分层原则：**NACK 是 resync 之下的加速层，不是替代**。resync 代码零改动，
对端不支持 NACK 时行为与之前逐字节一致 —— 这也是回归测试敢直接跑的原因。

### rtp_reorder 的语义（src/media/rtp_reorder.h）

- 洞出现 → 当场发 NACK，之后每 8ms 重发、最多 3 次（正好铺满 20ms 窗口）；
- 重传在窗口内到 → 无缝续上，**根本不产生 gap**；
- 20ms 没等到 → 洞判丢（`gap_pkts`），放行后面的包，depack 看到序号跳变
  走它既有的 poison → resync → PLI 慢路径；
- 16 位序号回绕走差值比较；0x4000~0xBFFF 的大跳变视为流重启（SSRC 换了），
  清空重来，绝不发 NACK 风暴；
- 缓冲满（cap=64 包）是断流保险丝：强弃最老的洞腾位置，绝不静默丢。

## 3. RTCP 报文（手拼，不引库）

- Generic NACK：RFC 4585 §6.2.1，PT=205（RTPFB）、FMT=1、FCI = PID + BLP。
  固定 16 字节，`rtcp_build_nack()`（src/media/rtcp.c）。
- 本实现一次报一个序号（BLP=0），连洞靠多次调用 —— 字节多点、逻辑简单，
  对 8 包以内的局域网丢失完全够用（`tests/ut_rtcp.c` 逐字节核对过）。
- 发送端口 = 视频 RTP 端口 +1（RFC 3550 §11），与 PLI 相同。
- **回程地址靠对称 RTP 校正**（见下面第 6 节的坑）。

## 4. 配置（环境变量）

| 变量 | 默认 | 说明 |
|---|---|---|
| `SIP_VIDEO_REORDER_MS` | 20 | 重排缓冲 hold 时长；0 = 关掉按序化（旧行为，A/B 对照用） |
| `SIP_VIDEO_NACK` | 开 | 设 0 关掉重传请求（重排照常，只是不请求） |
| `SIP_VIDEO_NACK_MS` | 8 | 重传请求多久没补上就重发 |
| `SIP_VIDEO_NACK_RETRY` | 3 | 每个洞最多请求几次 |

注意 **hold 必须 > retry × 次数**，重发才有发生的余地（UT 里有专门用例钉死节奏）。

统计行（挂断时打印，`[video] ro stats(...)`）：
`filled`=重传救回的包数，`gap`=判丢交给慢路径的包数 —— 这两个数的比例就是 NACK 的价值。

## 5. 怎么验（make loss-nack）

`make loss-nack` = 在 `make loss` 两遍之上加第三遍：

```
ffmpeg → nack_proxy.py（按规则丢包 + 扮演支持 RTX 的门口机）→ 室内机
                      ↑ 室内机发 RTCP NACK，代理从缓存重发缺的包
```

`scripts/nack_proxy.py` = 一个支持 NACK 的发送端的**最小替身**：
缓存收到的每个包，收到 Generic NACK 就按 PID 重发。不碰 SDP、不碰编解码。

三遍判据（loss_analyze.py `--mode off/on/nack`）：

| 遍 | 模式 | 判据 |
|---|---|---|
| 1 | off（关恢复） | 脏帧 > 0 —— 证明注入有效，不是假绿 |
| 2 | on（PLI 慢路径） | 0 脏帧 + 有跳帧 + 全部等到 IDR |
| 3 | nack（重传闭环） | **0 脏帧 + 0 跳帧 + filled ≥ 注入数 + gap=0 + resync 零触发** |

第三遍是关键：帧号**连续无跳**说明用户全程无感 —— 这是 NACK 与 PLI 路径
的本质区别（PLI 路径必然跳过等待期的帧）。

### 实测（8s 推流 640×480，注入 `60:6 690:8` 两段共 14 包）

```
关恢复:  写出 222 帧，脏 77                     ← 不恢复就是要花屏
开恢复:  写出 145 帧，脏 0，跳 88 帧，最坏等 1485ms，PLI 6 次
NACK:    写出 240 帧，脏 0，跳 0 帧，filled=14 gap=0，resync 事件 0，PLI 0
```

（NACK 行的"写出 240 帧" = 全部帧一个不少；代理侧 `resent=14` 与 `filled=14` 对上，
闭环两端账目一致。）

### UT（tests/ut_rtp_reorder.c，13 用例 + ut_rtcp.c 3 用例）

时序全部用脚本化 now_ms 钉死。压着的边界（都是实现时真出过/差点出的）：

1. `seq == next_seq` 的重传包不能被判成"流重启"（否则洞永远补不上）；
2. push 连发时不给已缓冲的序号虚报洞（否则给自己手里的包发 NACK）；
3. 缓冲满走保险丝而不是静默丢；
4. 洞超时后迟到的重传包只能弃（喂下去会毒 AU）；
5. 回绕 65534→65535→0→1 按序交付；大跳变（0x4000~0xBFFF）= 流重启。

## 6. 踩坑记录（每一坑都付出了 一轮 测试的代价）

1. **视频回程没做对称 RTP 校正** —— 视频只收不发，平时没有任何包从这边
   出去，回程只有 RTCP。不校正的话 PLI/NACK 永远发往 SDP 里写的地址：
   实测 app 发了 8 个 NACK，代理一个没收到（`nack=8` vs `nacks=0` 的假闭环）。
   之前 PLI 也是发错的，恰好靠 GOP 里的自然 IDR 恢复，一直没暴露。
   修：`rtp_video_on_readable` 里按实际源地址校正 `rtp_remote_v`（对齐音频路径）。
2. **丢的包没进重传缓存** —— 代理第一版"先判丢再缓存"，NACK 来查缓存必然
   落空（`resent=0`）。真实发送端是"包已发出 + 重传缓冲里留着"，必须先缓存再丢。
3. **reorder 批量交付冲垮 depack 的 done 槽** —— drain 一次突发出 2 个以上
   AU 边界时，先完成的 AU 被后完成的顶掉（`drop_slow`），静默丢帧，
   参考链从丢包点一直烂到 IDR（46 个脏帧）。修：每交付一个包就 pump 一次 AU，
   不攒批。教训：**下游"一次只吐一格"的接口，上游的批量化必须逐格对齐**。
4. **ffmpeg 每次推流初始 seq 随机** —— 丢包规则按绝对 RTP 序号写时，
   同一段规则一轮丢 14 包、一轮丢 8 包（`300:8 打死 IDR` 事故的真正根源）。
   两个代理统一按**接收顺序**（第 N 个收到的包）解释规则，测试才可复现。
5. **Windows CRT 忽略 `_IOLBF`** —— 重定向后实际是全缓冲，统计行没显式
   fflush 就会在进程被 kill -9 时丢失，分析器误判"重排没开"。

## 7. 还没做的

- NACK 响应端（收 NACK → 从重传缓冲重发）：室内机只收不发视频，没有对象；
  音频方向如果要做，同样套 rtp_reorder + 缓存即可（接口都是现成的）。
- `a=rtcp:` 属性解析、RTCP RR/SR 周期发送（当前只在有抱怨时发包）。
- BLP 位图打包（连洞 >8 个时省包）—— 局域网场景收益小，先不做。
