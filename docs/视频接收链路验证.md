# 视频接收链路验证 —— 用落盘 YUV 证明"解码是对的"

> 结论先说：**299/300 帧逐字节完全相同（bit-exact）**。
> 室内机通过 RTP 收到的视频，解包 → 解码 → 落盘，与参考解码结果一字节不差。
> 复跑一条命令：`make duo-video`。

---

## 1 为什么不能靠"看着差不多"

视频链路的错误形态和人眼判断力严重不匹配：

| 故障 | 屏幕上的表现 | 人眼判断 |
|---|---|---|
| FU-A 少拼一个字节 | 局部花屏 | "好像有点糊" |
| AU 边界切错 | 每帧偏移一点，画面抖动 | "摄像头就这样吧" |
| 落盘没按 linesize 逐行拷 | 画面整体斜切 | "角度没调好？" |
| 色彩空间错（YUV↔RGB） | 颜色发灰/发紫 | "屏幕色域不行" |
| 真的完全不通 | 黑屏 | 一眼看出 |

只有最后一行能靠眼睛。前四种在 7 寸屏上"都挺像"，而 PSNR 会从 40dB 直接掉到 12dB。

所以这里的判据是**数字**，不是观感。

---

## 2 为什么推流方用 ffmpeg，而不是自己发

音频那边做过"两个实例对打"（`make duo`），视频这边换成 ffmpeg 推流，理由不同：

| | 用我方实例发 | 用 ffmpeg 发 |
|---|---|---|
| 验的是什么 | 我方发送 + 我方接收 | **只验我方接收/解码** |
| 出问题时的责任边界 | 两端都自己写的，说不清是哪边 | 推流侧是成熟第三方，**一定是我方的问题** |
| 额外价值 | 顺带测了打包逻辑 | 提供一个**独立的实现参照** |

这轮的目标是"证明室内机的视频解码正确"，所以让 ffmpeg 承担编码和打包，我方只负责收、解包、解码、落盘。责任边界干净。

> 发送方向（板子把摄像头画面推给门口机）尚未实现，属于 M6 上板之后的事 —— 要等 MPP 编码器可用。现在写个空壳只会让人误以为它能用。

## 3 链路

```
ffmpeg                       室内机（被测）
  │
  ├─ H.264 裸流（640×480 / 30fps / 每帧叠帧号）
  ├─ RTP 打包（FU-A 分片，MTU 1400）
  │
  └── UDP ──────────────►  视频 RTP socket（udp/local+1002）
                                │
                                ├─ pt 校验（不匹配就丢，防止把 G.711 当 H.264 解）
                                ├─ h264_depack   单 NAL / STAP-A / FU-A 重组 → 访问单元
                                ├─ vdec          抽象层（PC=libavcodec 软解，板子=MPP 硬解）
                                └─ app_video     按 SIP_VIDEO_SINK 决定落盘 / 上屏 / 丢弃
                                        │
                                        └─► YUV420P 裸流落盘
                                                │
                                                └─ 与 ffmpeg 解码出的参考 YUV 逐帧比对
```

SIP 侧的视频协商是真的：`m=video <port> RTP/AVP <pt>` + `a=rtpmap` + `a=fmtp` + `a=recvonly`，
pt 回显对端 offer 的号（软电话常用 96 / Linphone Android 常用 102）。

## 4 两档判据

**PC 端：bit-exact（逐字节相同）**

同一个解码器（libavcodec）解同一段码流，H.264 解码是**确定性**的 —— 输出必须一字节不差。
不相同就说明链路里确实有问题（重组错、丢包、AU 边界不对），不存在"正常误差"这种解释。

**板端：PSNR ≥ 35 dB**

RK3308 用 MPP 硬解，运动补偿实现和软解不同，逐字节不可能相同。
35dB 以上人眼看不出差别；掉到 30dB 以下要怀疑色彩空间或 stride 处理。

> 这条区分很重要：如果 PC 端也用 PSNR 判，就会放过"差一两个像素"的错误 ——
> 而那种错误正是"FU-A 少拼一个字节"的典型症状。

## 5 怎么跑

```bash
make duo-video          # 默认推 8 秒
make duo-video SEC=10   # 推满素材全长
```

脚本自动完成：起两个实例 → SIP 呼叫 + 视频协商 → ffmpeg 推 RTP → 等挂断 → 比对。

素材第一次跑会自动生成（需要 `C:/msys64/mingw64/bin/ffmpeg.exe`）：

```bash
# 640×480 / 30fps / 10s，testsrc2 提供运动与色块
# drawtext 叠帧号：丢帧、重复帧、帧序错乱靠它一眼看出
ffmpeg -f lavfi -i "testsrc2=size=640x480:rate=30:duration=10" \
  -vf "drawtext=text='%{n}':fontsize=64:fontcolor=white:x=16:y=16" \
  -c:v libx264 -profile:v baseline -level 3.1 -pix_fmt yuv420p \
  -g 60 -keyint_min 60 -sc_threshold 0 -bf 0 -crf 20 \
  -f h264 bin/test_640x480.h264

# 参考解码结果（逐帧基准，138MB）
ffmpeg -i bin/test_640x480.h264 -pix_fmt yuv420p -f rawvideo bin/ref_640x480.yuv
```

用 `baseline` + `-bf 0` 是刻意的：不要 B 帧，就没有重排延迟，帧序和时间戳一一对应，
出问题时不会混淆"解码器重排"和"网络乱序"。

想肉眼看画面：

```bash
ffplay -f rawvideo -pixel_format yuv420p -video_size 640x480 bin/duo_b_video.yuv
```

## 6 实测结果（2026-10-22，10 秒素材）

```
[video] stats(hangup) pkt=1463 au=299 nal=311 stap=5 fu=300
        drop{type=0,big=0,slow=0} fu_broken=0
        dec{fed=299,frame=299,err=0} 640x480 sink_frames=299
```

| 指标 | 值 | 说明 |
|---|---|---|
| RTP 包 | 1463 | 平均每帧约 4.9 个包（FU-A 分片） |
| 访问单元 | 299 | 少 1 个是最后一帧：挂断时没等到下一个时间戳触发收尾 |
| 完整 NAL | 311 | 299 个 slice + SPS/PPS/SEI |
| STAP-A | 5 | 编码器把 SPS+PPS 聚合着发 |
| FU-A 序列 | 300 | 每帧都被切成 FU-A（640×480 一帧 > MTU） |
| **fu_broken** | **0** | 没有丢片、没有乱序断裂 |
| 解码 | fed=299 frame=299 **err=0** | 喂多少解多少，无错误 |
| **比对** | **299/299 bit-exact** | 逐字节完全相同 |

`au=299` 而 `sink_frames=299`、`nal=311`、`fu=300` 这几个数互相能对上，说明没有隐藏的丢弃。

## 7 踩到的坑

### 7.1 视频端口 = 音频端口 + 2，且必须在生成 SDP **之前**绑好

端口是 `local_port + 1000`（音频）起往上找偶数，视频取音频端口 +2。
同机跑两个实例时，SIP 段和 RTP 段必须整块错开（见《音频通路自测方案》第 9 节）。

真正的坑在时序：`rtp_open()` 在进程启动时就会跑一次，那时视频路由还没解析，
`app_video_wants_rx()` 返回 false，视频端口没绑 —— 而 `rtp_open()` 有
`if (s_rtp != SOCK_INVALID) return 0;` 的早退，第二次调用直接返回。

结果：**INVITE 里 m=video 一直是 0**，对端以为我们不支持视频。
修法是把视频端口单独拆成 `rtp_open_video()`，在 `app_sip_call()`（生成 offer 前）
和收到 INVITE（生成 answer 前）各调一次。

一句话：**SDP 里写什么，取决于生成 SDP 那一刻端口有没有绑上。**

### 7.2 `strstr` 找 rtpmap 会跨行

`m=video 5006 RTP/AVP 96 102` + `a=rtpmap:96 VP8/90000` + `a=rtpmap:102 H264/90000`
这种真实 offer 里，`strstr(当前行, "H264/90000")` 会一路搜到下一行，
把 VP8 的 96 当成 H.264 的 pt。然后所有视频包被 pt 校验丢掉。

必须把搜索限制在当前行内（到 `\r\n` 为止）。**这个 bug 是 `ut_sdp` 抓出来的**，
不是跑端到端能发现的 —— 因为用 ffmpeg 推流时 pt 恰好就是 96，撞对了。

### 7.3 落盘必须按 linesize 逐行拷

解码器的 `linesize` 通常大于 `width`（内存对齐）。直接 `fwrite(data[0], w*h)`
会把每行末尾的对齐垃圾也写进去，结果是画面斜切。

### 7.4 链接 libavcodec 后运行要能找到 DLL

PC 版会依赖 `avcodec-63.dll` / `avutil-61.dll`。`dev.sh` 里已经把
`/c/msys64/mingw64/bin` 加进 PATH，但单独跑脚本（`make duo` / `make duo-video`）
也要加，否则报 `avutil-61.dll: cannot open shared object file`。

板子上用 MPP 硬解，不链接 ffmpeg，没有这个问题 —— 这也是 `vdec` 抽象层存在的意义。

## 8 板端怎么复用同一套

`vdec.h` 是纯接口，接 MPP 只需新增一个实现文件：

```
src/media/vdec_mpp.c     ← vdec_open/feed/get 用 rockchip_mpp 实现
```

`app_video.c`、`h264_depack.c`、SDP 协商、AV 时钟全都不用动。
在 `CMakeLists.txt` 里把 `vdec_ffmpeg.c` 换成 `vdec_mpp.c` 即可。

判据从 bit-exact 换成 PSNR ≥ 35dB（硬解和软解不可能逐字节相同）：

```bash
python scripts/video_compare.py ref.yuv rx.yuv --size 640x480 --align
```

脚本两档判据都支持：全部 bit-exact 时报"完全正确"，否则报平均/最差 PSNR 和低于阈值的帧号。

## 9 还没做的

- **发送方向**：板子把摄像头（V4L2 → MPP 编码）推给门口机。等 M6。
- **上屏**：`SIP_VIDEO_SINK=disp` 已留分支，需要 `yuv → RGB565 → lv_image`。LVGL 非线程安全，
  必须走 `lv_async_call` 或事件总线，不能在 RTP 线程里碰 UI —— 见《产品规划》里的约定。
- **丢包恢复**：`vdec_flush()` 已实现，但"等下一个 IDR"的策略还没在 `app_video` 里接上。
  当前是 `fu_broken` 计数 + 继续解，花屏会持续到下一个 I 帧（GOP 60 = 2 秒）。
