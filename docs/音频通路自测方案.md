# 音频通路自测方案：不碰声卡、不碰手机

> 目标：在**没有麦克风、没有喇叭、没有手机**的机器上，把室内机的音频收发两条通路
> 各自验证清楚，并且给出可复算的数字，而不是"我听着像是对的"。

---

## 0 一句话方案

把"房间"换成"文件"：

```
发：室内机 src=file ──RTP──► 对端 sink=spk    （人耳听）
收：对端   src=file ──RTP──► 室内机 sink=file （存盘 + 逐样本比对）
```

两端都用**同一个二进制**，只是开关不同。所以不需要新写客户端，也不需要手机。

---

## 1 为什么这条路比手机方案靠谱

| | 手机 + Linphone | 文件 ↔ 文件 |
|---|---|---|
| 依赖 | 手机、同网段、7 项配置不能错 | 一个 wav |
| 可重复 | 每次说的话不一样，出问题没法复现 | **逐样本可比** |
| 能定位 | "听起来有点怪" | SNR / 分段 SNR / 丢包率三个数 |
| 受设备影响 | 手机编码器、容器权限、省电策略 | 无 |
| 覆盖真实设备 | 是（真实麦克风/摄像头） | 否 |

**结论：文件方案负责把 90% 的问题在无声卡环境里解决掉，手机方案只在最后做"真实设备"验收。**
两者不是替代关系，顺序应该是先文件、后手机。

本机实测 WASAPI **连采集设备都没有** —— 在这种情况下，任何依赖真实麦克风的方案都跑不起来，
而文件方案照样能把编码、打包、RTP、抖动缓冲、解码、落盘整条链路验完。

## 2 四个开关

| 变量 | 取值 | 含义 |
|---|---|---|
| `SIP_AUDIO_SRC` | `mic` | 真实麦克风（默认） |
| | `file` | 从 WAV 循环读，按 20ms/帧 匀速吐 |
| | `tone` | 合成 1kHz（等价于老开关 `SIP_TONE=1`） |
| | `none` | **关掉上行**：只收不发 |
| `SIP_AUDIO_SRC_FILE` | 路径 | 音源文件，默认 `test_8k.wav` |
| `SIP_AUDIO_SINK` | `spk` | 真实喇叭（默认） |
| | `file` | 写成 WAV 落盘，一次通话一个文件 |
| | `drop` | **关掉下行**：只发不收 |
| `SIP_AUDIO_SINK_FILE` | 路径 | 落盘文件名，默认 `rx.wav` |

`file` / `tone` / `none` / `drop` 模式下**不打开任何声卡设备**。这不只是省事：
板子在 M6 之前根本没配好 ALSA，靠这个开关**音频通路的验证可以完全不依赖 M6**。

配套两个开关还是原来那两个：

| 变量 | 作用 |
|---|---|
| `SIP_AUTOANSWER=1` | 来电自动 200 接听（免点屏幕） |
| `SIP_AUTOCALL=<uri>` + `SIP_AUTOHANGUP=<秒>` | 自动呼出、到点挂断（全脚本化） |

## 3 两条命令，两个方向

准备（PC 侧工具，只用标准库）：

```bash
python scripts/gen_test_wav.py bin/test_8k.wav     # 10 秒确定性音源
```

### 方向 A：室内机 → 对端（验证**发送**）

```bash
# 终端 1 —— 扮演对端（客户端）：只收、落盘
SIP_NO_REGISTER=1 SIP_LOCAL_PORT=5066 SIP_LOCAL_IP=127.0.0.1 SIP_AUTOANSWER=1 \
SIP_AUDIO_SRC=none SIP_AUDIO_SINK=file SIP_AUDIO_SINK_FILE=rx.wav \
  ./bin/main

# 终端 2 —— 扮演室内机：文件当麦克风，关掉喇叭
SIP_NO_REGISTER=1 SIP_LOCAL_PORT=5062 SIP_LOCAL_IP=127.0.0.1 \
SIP_AUTOCALL=sip:1000@127.0.0.1:5066 SIP_AUTOHANGUP=12 \
SIP_AUDIO_SRC=file SIP_AUDIO_SRC_FILE=test_8k.wav SIP_AUDIO_SINK=drop \
  ./bin/main
```

想用耳朵听，就把终端 1 的 `SIP_AUDIO_SINK=file` 换成 `spk` —— 这就是你说的
"客户端播放收到的音频"，PC 有喇叭就行。

### 方向 B：对端 → 室内机（验证**接收**）

把两个进程的开关对调即可（谁发谁收换了，代码路径完全不同的一组：一个走
`app_audio_read` → G.711 编码 → RTP，另一个走 RTP → 解码 → `app_audio_write` → 落盘）。

```bash
# 室内机侧：关麦、只收、落盘
SIP_AUDIO_SRC=none SIP_AUDIO_SINK=file SIP_AUDIO_SINK_FILE=board_rx.wav

# 对端侧：文件当音源、主动呼叫
SIP_AUTOCALL=sip:1001@<板子IP>:5062
SIP_AUDIO_SRC=file SIP_AUDIO_SRC_FILE=test_8k.wav SIP_AUDIO_SINK=drop
```

**两个方向都跑一遍才算验完。** 只跑一个方向，另一半的 bug 不会被发现 ——
发送是"读文件→编码→发包"，接收是"收包→解码→写文件"，没有任何一行是共用的。

## 4 三层验收：数量、波形、耳朵

### 第一层：数量（日志已有）

```
[rtp] stats(hangup) rx=0 tx=600 lost=0 ooo=0 loss=0.00% dur=12s pps=50.0
[audio] 落盘完成: rx.wav  96000 采样 (12.00 秒)  峰值=12032
```

看四个东西：

| 看什么 | 正常值 | 不正常说明什么 |
|---|---|---|
| `pps` | 50.0 | 不是 50 就是发送节奏错了（32kbps 而不是 64kbps） |
| `loss` | 0.00%（局域网直连） | 有丢包 → 网卡/交换机/对端缓冲 |
| `采样数` | ≈ 通话秒数 × 8000 | 少了 → 有帧没落盘；多了 → 重复 |
| `峰值` | 非 0 | 0 = 收到的全是静音（SDP 地址错/加密/编码不匹配） |

`lost` / `ooo` 是这一轮新加的：**只看 rx 计数会被骗**。发 250 个、收 250 个，
也可能丢了 5 个又重复 5 个 —— 计数一样，声音是断的。

### 第二层：波形（客观）

```bash
python scripts/audio_compare.py bin/test_8k.wav bin/rx.wav
```

```text
对齐: 实测比参考延后 0 采样 = 0.0 ms
增益: 0.999（1.000 表示电平没被改）
SNR: 43.1 dB  →  通路正确（差异是 G.711 正常量化噪声）

分段（每 1.0s）:
    0.0-  1.0s     37.5 dB
    1.0-  2.0s   （静音段）
    2.0-  3.0s     49.0 dB
    ...
```

判读标准（G.711 是 8bit 对数压扩，理论上限约 38dB）：

| SNR | 结论 |
|---|---|
| ≥ 30dB | 通路正确，差异就是量化噪声 |
| 20~30dB | 有明显失真：削顶、增益错、偶发丢帧 |
| < 15dB | 基本不通：字节序 / 编码 / 加密 / 采样率错 |
| ≈ 0dB | 两块完全不同的信号（根本没收对） |

**分段 SNR 的价值**：它能直接告诉你"第 7 秒开始坏的"，比听十遍快得多。
比如 6~8s 是通断音，那一段掉到 20dB 以下，就是丢包/抖动缓冲的问题。

### 第三层：耳朵（主观）

`SIP_AUDIO_SINK=spk` 直接播，或者把 `rx.wav` 拷到 PC 上放。
音源设计成每段对应一个故障：静音段能听出噪声/回声、通断段能听出丢帧、
音量阶梯能听出量化台阶。

## 5 本机实测（2026-10-22，Windows + MSYS2）

| 项 | 结果 |
|---|---|
| 通话时长 | 12s（故意跨过 10s 音源的循环点） |
| 发送 | `tx=600 pps=50.0` |
| 接收 | `rx=600 lost=0 ooo=0 loss=0.00%` |
| 落盘 | 96000 采样 = **12.00 秒**（一点不差） |
| 与源文件 SNR | **43.1 dB**，增益 0.999，时延 0 采样 |
| 喇叭通路 | `sink=spk` 收 40000 采样/5s，`underrun=0` |

12.00 秒这个数字是有意义的：源文件正好 10 秒，通话 12 秒，说明**回绕逻辑没有丢也没有多**。

## 6 这一轮踩到的三个坑

### 6.1 音源首尾不接零 → 每 10 秒一个假的"咔哒"

第一版音源结尾停在大幅值、开头从 0 起，循环时有一个跳变（实测相邻采样跳 4104）。
而**丢包的症状也是"咔哒"** —— 不处理这一点，会去查一个根本不存在的问题。
现在生成脚本对首尾各做 10ms 淡入淡出，循环点最大跳变降到 208（正常波形内）。

> 推广一句：**测试信号自己的毛病，会被当成被测对象的毛病。**

### 6.2 两端同源，对称的 bug 会互相掩盖

两端都跑同一份 G.711，如果编码器有错，会"错得一模一样"，SNR 照样 43dB。

所以必须有一个**独立实现**做参照。ffmpeg 就是现成的：

```bash
ffmpeg -i test_8k.wav -c:a pcm_alaw -f alaw ff.alaw     # 独立实现的编码结果
```

实测：65536 个输入值里，我们有 **964 个**码字与 ffmpeg 不同（1.5%），
差别只有 **1 个量化级**，且集中在段边界（如 −8214 附近）。

结论是**不是 bug**：这是两种同样合法的取整策略（Sun 参考实现 vs ffmpeg 的
就近取整）。我们保留 Sun 那套 —— 网关/IPPBX 里跑的是它。这条写进注释了，
免得下次有人"为了跟 ffmpeg 完全一致"去改它。

> 这个坑的真正价值不是"改哪里"，而是**方法**：凡是两端跑同一份代码的测试，
> 都要单独验证那份代码；否则"自己跟自己比"永远是对的。

### 6.3 落盘 WAV 的头必须边写边回填

WAV 头里的 `data` 长度在开始时是未知的。只在关闭时回填，进程被 kill 就是
一个打不开的文件 —— 而测试恰恰经常 kill 进程。

现在每秒回填一次头 + `fflush`，所以**任何时刻中断，文件都是能播放的**（截断到断点）。

## 7 上板之后怎么用同一套

开关不动，只换音源/音宿：

| 场景 | 配置 |
|---|---|
| 板子跑真实麦克风，PC 听 | 板 `src=mic sink=drop`，PC `sink=spk` |
| 板子收、落盘，PC 发文件 | 板 `src=none sink=file`，PC `src=file` |
| 板子自检（不接网） | `src=tone sink=spk`，喇叭里应有"嘟——" |
| 无 ALSA 驱动时 | `src=file sink=file`，完全不碰声卡 |

M6 换 ALSA 后端时，只改 `app_audio.c` 的设备分支（`SDL_OpenAudioDevice` → `snd_pcm_open`），
`src/sink` 这层策略和上层一行不用动。

## 8 和视频的关系

音频这条路走通之后，视频侧仍然按《音视频对讲测试方案》走（手机或 `ffmpeg` 推流）。
顺序上建议：**先把音频自证清白**，再做视频 —— 否则"画面不动、声音也没有"的时候，
你连是哪一半坏了都说不清。

## 9 双端互通：单实例自环证明不了的那一半

前面几节都是**一个进程自己发、自己收**。它有力，但有明确的天花板：

| 能证明 | 证明不了 |
|---|---|
| G.711 编解码对得上（SNR 43dB） | INVITE/SDP 协商出来的是不是同一套参数 |
| RTP 分片/时序对得上（50pps） | 对称 RTP 回填对不对（对面地址是不是真收到包的那个） |
| 不丢包、不重排 | 两端的序号/时间戳基准能不能各自独立、互不干扰 |
| 落盘可播 | 真实的"主叫/被叫"状态机（100/180/200/ACK/BYE） |

自环本质是**同一套内部状态**在跟自己对账，它天然不会暴露"我从没看过对面"这类错。
要暴露，就必须有**第二个进程**。

### 9.1 做法：一台机器两个实例 = 两台设备

不需要第二台电脑、不需要手机、不需要服务器、不需要声卡。
两个 `main.exe`，一个演室内机，一个演 PC 客户端，走 `SIP_NO_REGISTER=1` 点对点直呼。

```
bash scripts/duo_test.sh 12       # = make duo
```

两个方向各跑一次，全程自动（`SIP_AUTOCALL` 主叫、`SIP_AUTOANSWER` 自动接、`SIP_AUTOHANGUP` 定时挂）：

| 方向 | 室内机 | 客户端 | 验证的是 |
|---|---|---|---|
| 1 | `src=file sink=drop`（关扬声器） | `src=none sink=file` | **室内机上行**发送链路 |
| 2 | `src=none sink=file`（关 mic） | `src=file sink=drop` | **室内机下行**接收链路 |

落盘文件按方向命名，不会混：`bin/duo_a_rx.wav` = 客户端收到的，`bin/duo_b_rx.wav` = 室内机收到的。

### 9.2 端口必须手动错开（这里踩过）

程序里 RTP 端口是 **`local_port + 1000`** 起往上找偶数口。所以：

| 实例 | local_port | SIP | RTP |
|---|---|---|---|
| 室内机 | 5062 | 5062 | 6062 |
| 客户端 | **7062** | 7062 | 8062 |

第一版把客户端 `local_port` 填成 6062，结果它的 **SIP 端口正好压在室内机的 RTP 段上**，
第二个实例直接 `bind 6062 failed` 起不来。两个实例同机时，SIP 段和 RTP 段必须整块错开
（相邻的 1000 号段不能互相覆盖）。

### 9.3 实测结果（2026-10-22，各 12 秒）

| 方向 | 发送端 | 接收端 | 落盘 | SNR |
|---|---|---|---|---|
| 室内机 → 客户端 | tx=600 `50.0pps` lost=0 | rx=600 lost=0 ooo=0 loss=0.00% | 96000 采样 = 12.00s | **43.1 dB** |
| 客户端 → 室内机 | tx=599 `49.9pps` lost=0 | rx=599 lost=0 ooo=0 loss=0.00% | 95840 采样 = 11.98s | **43.1 dB** |

增益 0.999、时延 0 采样，两方向一致。落盘秒数 − 通话秒数 ≈ 0.02s，就是挂断那一刻的收尾。

### 9.4 为什么 SNR 卡在 43dB 上不去

G.711 是 8bit 对数压扩，理论 SNR 上限 ≈ 38dB（满量程正弦）；实测 43dB 已超过这个经验值，
因为测试信号并非全程满量程。**43dB 就是这条通路的天花板**，不是"还差一点"。
换 16bit PCM（`pt=0` 之外的 L16/711 之外编码）才会更高，那不是当前要验的东西。

### 9.5 什么时候该跑这个而不是自环

- 改过 `app_sip.c` 里 SDP 拼装、RTP 对端地址、ACK/BYE 时序 → **必须跑 duo**，自环测不出来
- 只改 `g711.c`、音频重采样 → 自环够用，快
- 上板前最后一关 → duo + 板端 `tools/sip_echo` 各一遍
