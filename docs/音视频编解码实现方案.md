# 音视频编解码实现方案（C / C++）

> 本文回答两个问题：
> **① 室内机端的音视频到底是从哪一行代码开始跑起来的？**
> **② 解码用什么库、在 C 里长什么样、板子上怎么落地？**
>
> 与《音视频对讲测试方案.md》的分工：那份讲**怎么测**（手机当对端、三段验收），

## 0. 先把 ffplay 说清楚

**ffplay 不是我们要写的东西，也不是产品的一部分。** 它是 FFmpeg 项目自带的**示例播放器**，
属于"应用层"。产品链接的是它下面那一层**库**。

| 层 | 具体东西 | 我们的关系 |
|---|---|---|
| 应用层 | `ffplay.exe`、`ffmpeg.exe` | **只在 P1 验收时用一次**，产品二进制里一行都没有 |
| 库层 | `libavcodec`（编解码）、`libswscale`（像素转换）、`libavutil` | **这就是产品链接的东西** |

一个常见的类比：

- 你用了 **SQLite 库**，不需要在产品里塞一个 `sqlite3` 命令行 → 同理，用 `libavcodec` 不需要 `ffplay`；
- 你用了 **libcurl**，不需要 `curl.exe`；
- 你用了 **libavcodec**，不需要 `ffplay`。

**为什么还是让 ffplay 出场**：P1 阶段要回答的是"手机发出来的 H.264 流本身对不对"。
这个问题跟我们自己写的解码代码无关。用 ffplay 一播就知道 —— 播放器是"可信第三方"，
出画面说明上游全对，之后只剩"把 ffplay 干的事用 C 写一遍"。这是**减少同时排查的变量数**，
不是把工具塞进产品。

> 顺便说：这台机器刚才为了跑 P1 才 `pacman -S mingw-w64-x86_64-ffmpeg` ——
> 说明 ffplay 是个需要单独安装的外部工具，跟产品构建毫无关系。

## 1. 室内机端的音视频是怎么起来的

### 1.1 现在的真实调用链（音频已通，视频待加）

```
main()                                                  src/main.c:93
 ├─ oem_init()                     OEM profile
 ├─ ui_theme_init / ui_home_init / ui_call_init / app_mock_init
 ├─ app_sip_init_from_env()                              src/app/app_sip.c
 │   ├─ detect_local_ip()          探测本机出口 IP
 │   └─ rtp_open()                 RTP socket，local_port+1000 起找偶数口
 ├─ app_sip_start()                ← 起【线程 1：SIP】
 │    └─ recv_loop()
 │         ├─ select() 同时等 SIP socket 和 RTP socket
 │         ├─ handle_response()     收到 200 OK
 │         │    ├─ parse_remote_sdp()   拿对端 IP/端口/payload
 │         │    ├─ 发 ACK
 │         │    ├─ set_state(SIP_INCALL)
 │         │    └─ rtp_start_media()  ★ 媒体通路就是从这里开的
 │         │         ├─ app_audio_open()   开声卡（SDL，板子上换 ALSA）
 │         │         └─ 标记 s_rtp_echo=false
 │         └─ rtp_on_readable()     ★ 每个 RTP 包进来
 │              └─ G.711 解码 → app_audio_write() → 环形缓冲
 │
 ├─ [线程 2：声卡] SDL/ALSA 回调，20ms 一次，从环形缓冲取 160 样本播放
 │
 └─ [主线程] while(1) lv_timer_handler()   ← UI，约 30fps
```

**三个线程，各管一段，靠环形缓冲解耦**。这是必须的，不是设计洁癖：

| 线程 | 周期 | 为什么不能合并 |
|---|---|---|
| SIP | 事件驱动（包到就处理） | 阻塞在 select，不能碰 UI |
| 声卡回调 | **硬实时 20ms** | 晚 20ms 就爆音/欠载，UI 一次 flush 可能几十 ms |
| UI | ~33ms | LVGL 不是线程安全的，只能在主线程 |

### 1.2 加了视频之后，链路变成什么样

```
[线程 1：SIP]  ─── 只负责信令 + 音频 RTP
[线程 2：声卡]  ─── 不变
[线程 3：视频收包]  select 视频端口 → depacketizer → 攒完整 NAL → 丢进队列（满了丢最旧）
[线程 4：解码]    从队列取 NAL → 解码 → NV12 → RGB565 → 写入"待显示缓冲"
[主线程：UI]      取最新一帧的指针 → lv_image 刷新
```

**为什么要单独一个解码线程**：软解 480p 一帧 8~12ms（推算值，见 §3），
720p 一帧 35ms 以上。放在 UI 线程里就是**明显的卡顿**；放在 SIP 线程里会让
SIP 事务超时（手机那边看着像"对方没响应"）。

**为什么要"丢了最旧"而不是排队**：视频不是文件，晚到的帧没有价值。队列积压
= 延迟越滚越大。实时视频的正确策略是**宁可丢帧，不可延迟**。

### 1.3 视频这段的时序（从 INVITE 到屏上有画面）

```
手机                        室内机
 │  INVITE (m=audio + m=video)  │
 │─────────────────────────────>│  parse offer：记住 video 的端口和 pt
 │  100 / 180                   │
 │<─────────────────────────────│
 │  200 OK (SDP answer)         │
 │<─────────────────────────────│  m=video <端口> RTP/AVP 102
 │                              │  a=recvonly        ← 只收，不发
 │  ACK                         │  a=fmtp:102 packetization-mode=1;profile-level-id=...
 │─────────────────────────────>│
 │                              │  ★ rtp_start_media()：开音频 + 开视频端口
 │  RTP 音频 (PT=8)  20ms/包     │
 │─────────────────────────────>│  G.711 解码 → 声卡
 │  RTP 视频 (PT=102) 33~66ms/包 │
 │─────────────────────────────>│  每个包可能是 FU-A 的一个分片
 │                              │  ── 攒够一个完整 NAL ──>
 │                              │  解码线程 → RGB565 → lv_image
 │  RTP 音频（我们回过去）        │
 │<─────────────────────────────│  G.711 编码 → RTP
```

## 2. 三条通道分别由谁负责

| 通道 | 编码格式 | 用什么实现 | 跑在哪 | 现状 |
|---|---|---|---|---|
| 音频 上行 | G.711 A-law（PT=8） | `src/app/g711.c`，**自研，256 项查表** | SIP 线程 | ✅ 已通 |
| 音频 下行 | G.711 | 同上 | SIP 线程 | ✅ 已通 |
| 视频 下行 | H.264 | `libavcodec`（PC）/ `MPP`（板子） | 独立解码线程 | ❌ 待做 |
| 视频 上行 | —— | **不做**（室内机不需要发视频） | —— | —— |
| 显示 | RGB565 | 自研定点 YUV→RGB | 解码线程 | ❌ 待做 |

### 关键认知：G.711 没有"编解码库"这回事

G.711 是**波形直接量化**：16 bit 线性 PCM → 8 bit 对数量化，一个样本对一次 256 项查表。
不需要任何第三方库，100 行 C 就写完：

```c
/* 编码：线性 → A-law，全部是位运算 + 查表 */
int g711_encode_alaw(const int16_t *pcm, uint8_t *out, int n);

/* 解码：A-law → 线性，本质就是 256 项的查表 */
int g711_decode_alaw(const uint8_t *in, int16_t *pcm, int n);
```

这是**对讲/门禁行业的标配做法**（大华、海思的门口机全是 PCMA/PCMU），
不是"为了省事不做压缩"。G.711 的优点是**零延迟、零状态、丢包不影响后续**
——对讲场景里比 Opus 更合适，Opus 有前瞻延迟和丢包扩散。

> 以后要做宽带语音（16kHz）再考虑 G.722 或 Opus，那是另一个决策。

### 但 H.264 必须用库

H.264 解码器包含：CABAC/CAVLC 熵解码、反量化、反整数变换、9 种帧内预测、
1/4 像素精度的运动补偿、去块滤波、多参考帧管理……**没有人手写这个**，
FFmpeg 里这部分是十几万行经过十年优化的 C + SIMD。

所以问题不是"要不要用库"，而是**用哪个库**。

## 3. H.264 解码的三条路（板子上怎么落地）

| 方案 | 原理 | 480p@15 成本 | 720p@15 | 依赖体积 | 结论 |
|---|---|---|---|---|---|
| **libavcodec 软解** | 纯 CPU 跑 C/NEON | 实测 PC 0.39ms/帧，推算 A35 约 **8~12ms**，占 15~20% 单核 | 35~55ms/帧，**会掉帧** | 可裁到 ~1MB | PC 阶段 + 480p 可用 |
| **Rockchip MPP 硬解** | 走 VPU（`/dev/mpp_service`） | **<2ms，几乎不占 CPU** | 轻松 30fps | `librockchip_mpp.so` ~500KB | **量产方案** |
| FFmpeg + rkmpp | libavcodec 内部转调 MPP | 同硬解 | 同硬解 | 要 `--enable-rkmpp`，交叉编译麻烦 | 想一套代码通吃时 |

### 实测数据（本机 x86_64，单线程，刚跑出来的）

用 `tools/h264_probe`，输入是 `ffmpeg` 合成的 5 秒 480p / 3 秒 720p 码流：

```
480p baseline 15fps   解码 74 帧   单帧 min 0.31 / avg 0.39 / max 0.83 ms
720p main     15fps   解码 44 帧   单帧 min 1.54 / avg 1.78 / max 2.88 ms
```

> ⚠️ 这是 **x86 台式机**的数字，不是板子的。RK3308 是 Cortex-A35 @1.3GHz，
> 单核整数性能大约是本机的 **1/20 ~ 1/30**，且 FFmpeg 的 H.264 解码分支密集、
> ARM 上比 x86 更吃亏。所以：
> - **480p 软解：8~12ms/帧 → 15fps 占 15~20% 单核，可行**
> - **720p 软解：35~55ms/帧 → 15fps 要 50~80% 单核，必然掉帧，必须硬解**
>
> 这两个数字是**推算**，上板后第一件事就是用同一个 probe 复核（见 §7）。

### 为什么推荐"抽象层 + 双后端"

跟 OEM 那层完全同一个思路：**接口固定，后端可换**。

```c
vdec_t *vdec_open(vdec_backend_t be, int w, int h);   /* BE_AUTO / BE_FFMPEG / BE_MPP */
int     vdec_feed(vdec_t *d, const uint8_t *nal, size_t len);   /* Annex-B 输入 */
int     vdec_get_frame(vdec_t *d, const uint8_t **yuv, size_t *stride, int *w, int *h);
void    vdec_close(vdec_t *d);
```

PC 上用 `vdec_ffmpeg.c`，板子上用 `vdec_mpp.c`，**上层（收包 → 解包 → 解码 → 上屏）一行不改**。
好处很实际：**视频上屏的逻辑可以在 PC 上全部调完**，上板只换一个 `.c` 文件。

## 4. 代码骨架

### 4.1 RTP → Annex-B：depacketizer（**最容易写错的一步**）

H.264 的 RTP 负载有三种打包方式，**FU-A 的分片必须重组，否则只出第一帧**：

```c
/* 每个 RTP 包的负载第一个字节是 NAL 头 */
#define NAL_TYPE(b)        ((b) & 0x1F)
#define NAL_IS_FU_A(b)     (NAL_TYPE(b) == 28)
#define NAL_IS_STAP_A(b)   (NAL_TYPE(b) == 24)

/* FU-A 的三个关键位 */
#define FU_START(b)        ((b) & 0x80)
#define FU_END(b)          ((b) & 0x40)

void h264_depack_feed(h264_depack_t *d, const uint8_t *rtp_payload, int len)
{
    if (len < 1) return;
    uint8_t b0 = rtp_payload[0];

    if (NAL_IS_FU_A(b0)) {
        if (len < 3) return;
        uint8_t fu_hdr = rtp_payload[1];

        if (FU_START(fu_hdr)) {
            /* 起始片：用 FU indicator 的 F/NRI + FU header 的 type 还原出原 NAL 头 */
            d->nal[0] = (uint8_t)((b0 & 0xE0) | (fu_hdr & 0x1F));
            d->len = 1;
            memcpy(d->nal + d->len, rtp_payload + 2, (size_t)(len - 2));
            d->len += (size_t)(len - 2);
        } else {
            /* 中间片 / 结束片：直接续在后面 */
            memcpy(d->nal + d->len, rtp_payload + 2, (size_t)(len - 2));
            d->len += (size_t)(len - 2);
        }

        if (FU_END(fu_hdr)) {
            vdec_feed(d->dec, d->nal, d->len);   /* 一个完整 NAL 攒好了 → 送解码 */
            d->len = 0;
        }
        return;
    }

    /* 单 NAL（含 SPS/PPS/IDR）：整个负载就是一个 NAL */
    vdec_feed(d->dec, rtp_payload, (size_t)len);
}
```

**踩坑清单**：

| 坑 | 现象 | 原因 |
|---|---|---|
| 漏了 FU-A | **只出第一帧，然后永远静止** | 只有 I 帧起始片被当完整 NAL 送解码 |
| 忘了还原 NAL 头 | 花屏 / 解码器报 "no frame" | FU-A 的原 NAL 头要由 `indicator&0xE0 \| fu_hdr&0x1F` 拼回来 |
| 没丢掉 SPS/PPS 之外的 SEI | 解码器偶尔报错 | 可以送，但要注意 buffer 长度 |
| 缓冲区不够大 | 大 I 帧被截断 → 花屏 | 480p 关键帧实测 **15~40 KB**，留 256 KB 安全 |

### 4.2 解码后端：libavcodec

```c
/* src/media/vdec_ffmpeg.c —— 只用一个解码器，不要 libavformat */
#include <libavcodec/avcodec.h>

struct vdec {
    AVCodecContext *ctx;
    AVFrame        *frm;
    AVPacket       *pkt;
};

vdec_t *vdec_ffmpeg_open(int w, int h)
{
    const AVCodec *c = avcodec_find_decoder(AV_CODEC_ID_H264);
    if (!c) return NULL;

    vdec_t *d = calloc(1, sizeof(*d));
    d->ctx = avcodec_alloc_context3(c);
    d->ctx->thread_count = 1;          /* A35 四核，留给 UI 和音频 */
    d->ctx->flags |= AV_CODEC_FLAG_LOW_DELAY;   /* 对讲要低延迟，不要 B 帧重排 */
    if (avcodec_open2(d->ctx, c, NULL) < 0) { free(d); return NULL; }

    d->frm = av_frame_alloc();
    d->pkt = av_packet_alloc();
    return d;
}

/* 输入是 Annex-B 的一个完整 NAL（可能只是一个 slice，解码器自己会缓） */
int vdec_ffmpeg_feed(vdec_t *d, const uint8_t *nal, size_t len)
{
    av_packet_unref(d->pkt);
    /* 注意：不解码器自己的 buffer，avcodec_send_packet 会拷贝 */
    if (av_new_packet(d->pkt, (int)len) < 0) return -1;
    memcpy(d->pkt->data, nal, len);
    return avcodec_send_packet(d->ctx, d->pkt);
}

/* 取一帧（YUV420P）。返回值：1=有帧，0=还没解出来，<0=错误 */
int vdec_ffmpeg_get(vdec_t *d, const uint8_t **yuv, size_t *stride, int *w, int *h)
{
    int rc = avcodec_receive_frame(d->ctx, d->frm);
    if (rc == AVERROR(EAGAIN) || rc == AVERROR_EOF) return 0;
    if (rc < 0) return rc;

    yuv[0] = d->frm->data[0];  yuv[1] = d->frm->data[1];  yuv[2] = d->frm->data[2];
    stride[0] = (size_t)d->frm->linesize[0];
    stride[1] = (size_t)d->frm->linesize[1];
    stride[2] = (size_t)d->frm->linesize[2];
    *w = d->frm->width;
    *h = d->frm->height;
    return 1;
}
```

> **为什么不要 libavformat**：RTP 的会话状态（对端地址、端口、payload type、
> SSRC、序列号）在 SIP 层已经全部知道了。再让 libavformat 去解析一遍 SDP、
> 重建一次会话，等于**把已知的东西丢掉再问一遍**，还会多出几十 KB 和一堆
> 难以控制的缓冲。**自己做 RTP 解包 + 只用 libavcodec 解裸 NAL 是更干净的架构。**

### 4.3 解码线程：只交最新帧

```c
static void video_thread(void *arg)
{
    media_t *m = arg;
    while (m->running) {
        uint8_t *nal; size_t len;
        if (!nalq_pop(&m->q, &nal, &len, 50 /*ms*/)) continue;  /* 超时就空转一圈，好退出 */

        if (vdec_feed(m->dec, nal, len) < 0) { free(nal); continue; }
        free(nal);

        const uint8_t *yuv[3]; size_t stride[3]; int w, h;
        while (vdec_get_frame(m->dec, yuv, stride, &w, &h) == 1) {
            uint16_t *dst = m->fb[m->fb_w];          /* 双缓冲：写另一块 */
            yuv420_to_rgb565(yuv, stride, w, h, dst, m->fb_stride);
            m->fb_r = m->fb_w;                        /* 原子切换"可显示"下标 */
            m->fb_w ^= 1;
            m->has_new = 1;                           /* UI 线程来取 */
        }
    }
}
```

**三个设计点**：

1. **队列满了丢最旧**（`nalq_push` 里判满就 pop 一个丢掉），绝不无限积压；
2. **双缓冲**：解码写 A，UI 读 B，避免撕裂；
3. **只在有帧时置 `has_new`**，UI 线程不需要知道解码细节。

### 4.4 上屏：lv_image 千万别每帧新建

```c
/* 初始化一次 */
static uint8_t  s_fb[2][640 * 480 * 2];       /* 双缓冲，静态分配，不走 lv_mem */
static lv_image_dsc_t s_dsc = {
    .header.magic  = LV_IMAGE_HEADER_MAGIC,
    .header.cf     = LV_COLOR_FORMAT_RGB565,
    .header.w      = 640,
    .header.h      = 480,
    .data_size     = 640 * 480 * 2,
};
lv_obj_t *img = lv_image_create(ui_call_screen());
lv_image_set_src(img, &s_dsc);

/* 每帧只改指针 + 重绘 */
s_dsc.data = s_fb[ready_idx];
lv_obj_invalidate(img);
```

| 错误写法 | 后果 |
|---|---|
| 每帧 `lv_image_set_src` 新建对象 | LVGL 对象泄漏、内存池爆、掉帧 |
| 用 `lv_canvas` 每帧 `lv_canvas_set_buffer` | 走 lv_mem 分配，600KB 直接失败（池默认 64KB） |
| 在解码线程里 `lv_*` 调用 | **LVGL 不是线程安全的**，随机崩溃 |

> **内存账**：640×480 RGB565 = **600 KB/帧**，双缓冲 1.2 MB。
> LVGL 的内存池只有 64KB~1MB，**绝对不能放进去** —— 必须静态分配或 `malloc`。
> 720p 是 1.84 MB/帧，双缓冲 3.7 MB，RK3308 的 128MB DDR 扛得住。

## 5. 交叉编译（板子上要什么）

### 5.1 FFmpeg 软解：裁到 1MB 以内

```bash
./configure \
  --enable-cross-compile --arch=arm --target-os=linux \
  --cross-prefix=arm-linux-gnueabihf- \
  --disable-everything --disable-programs \
  --enable-decoder=h264 --enable-parser=h264 --enable-swscale \
  --disable-avformat --disable-avdevice --disable-avfilter \
  --disable-encoders --disable-muxers --disable-demuxers --disable-protocols \
  --enable-shared --disable-static
```

两个关键开关：

- **`--disable-programs`**：不编 `ffplay`/`ffmpeg`/`ffprobe`。这就是"ffplay 不进产品"在
  构建系统上的具体落实 —— **代码层面它根本不会被编译出来**。
- **`--disable-avformat --disable-protocols`**：我们自己做 RTP 收包，不需要 FFmpeg 的
  协议栈和容器解析。这一条能省掉一半以上的体积和依赖。

默认编译的 FFmpeg 是 60~80 MB；按上面裁完，`libavcodec.so` + `libavutil.so` + `libswscale.so`
大约 **1~1.5 MB**。

### 5.2 MPP 硬解

```bash
# Rockchip 官方 mpp 仓库
git clone https://github.com/rockchip-linux/mpp
cmake -DCMAKE_C_COMPILER=arm-linux-gnueabihf-gcc \
      -DCMAKE_SYSTEM_NAME=Linux -DCMAKE_SYSTEM_PROCESSOR=arm \
      -DHAVE_DRM=OFF -DCMAKE_INSTALL_PREFIX=/opt/mpp ..
make -j && make install
```

产出 `librockchip_mpp.so`（约 500 KB）+ 头文件。板子上确认：

```bash
ls /dev/mpp_service          # 或 /dev/rkvdec
cat /proc/mpp_service/session_summary
```

## 6. 性能预算（RK3308，四核 A35 @1.3GHz）

| 任务 | 单核占用 | 说明 |
|---|---|---|
| LVGL UI（480×480 屏，30fps） | 25~35% | 已有实测（`LVGL_STATS=1`） |
| G.711 编解码 + 声卡 | <2% | 查表，可忽略 |
| H.264 软解 480p@15 | 15~20% | **推算**，需上板复核 |
| H.264 软解 720p@15 | 50~80% | **推算**，基本不可用 |
| H.264 硬解 720p@30 | <5%（VPU 独立） | 大幅减轻 CPU |
| YUV→RGB565 640×480 | 8~15% | 用定点 + 每 2×2 只算一次色度 |

**结论：480p 阶段软解够用（PC 上能全调通），量产上 720p 必须切 MPP 硬解。**

## 7. 怎么验证板子的解码能力（上板第一件事）

`tools/h264_probe` 可以**直接交叉编译到板子上跑**（它只依赖 libavcodec）：

```bash
# PC 上跑（已有数据）
./h264_probe test480p.h264 --rgb565 frame.raw

# 板子上跑（交叉编译后，用同一份码流）
./h264_probe test480p.h264
```

对比两个 `单帧耗时 avg`，就能得出**真实的换算系数**，之后所有性能判断都有依据，
不用猜。同时 `--rgb565` 导出的 `frame.raw` 可以直接 `lv_image` 显示 —— 这就是
"上屏通不通"的最小验证，跟 RTP 无关。

**这一步做在接 RTP 之前**，能把"解码器对不对"和"收包对不对"彻底分开。

## 8. 面试可以这么讲

> "音视频这块，音频用的是 G.711，PT=8，就是 PCM 查表量化，对讲行业标配，
> 零延迟、丢包不扩散；我们自己实现的 256 项查表编解码，没有引入库。
>
> 视频是 H.264 解码，用 libavcodec，但**没有用 libavformat** —— RTP 的会话状态
> 在 SIP 那层已经知道了，再用 avformat 把 SDP 重新解析一遍是多一层，还会带进
> 一堆缓冲。我就自己做 RTP 解包，处理 FU-A 分片，攒成 Annex-B 的 NAL 喂给
> avcodec。FFmpeg 编译时 `--disable-programs`、`--disable-avformat`，
> 最后只留 1.5MB 的库。
>
> 板子上换成 Rockchip MPP 硬解走 VPU，但我在上面留了一层 vdec 抽象，
> 上层收包、解包、上屏的代码一行不动 —— 跟 OEM 的 profile 那层是同一个思路。
>
> 解码跑在独立线程，队列满了丢最旧的帧，因为实时视频宁可丢帧不能延迟。"

这段话的价值在于：**知道每个库解决什么问题、为什么不用它**，
比"我用了 FFmpeg"高一个层级。
